## 제1장 생일 특별휴가와 포인트의 구분 [BD]

### 제1절 적용 기준 [BD-S1]

#### BD-01 적용 대상과 부여 일수

<!-- kind: preserved -->
입사 후 3개월이 지난 재직자는 매년 생일 특별휴가 1일을 신청할 수 있다. 수습 중인 직원은 대상에서 제외한다.

<!-- kind: added_fictional -->
담당자는 신청 내역에 표시된 재직 기간과 수습 구분을 각각 확인한다. 두 정보의 표시가 서로 맞지 않으면 차이가 난 항목을 남기고 인사 기록의 정정을 확인하며, 단순한 화면 표시 오류를 새로운 제외 사유로 처리하지 않는다.

#### BD-02 사용 범위와 다른 제도

<!-- kind: preserved -->
생일 특별휴가는 생일이 속한 달의 근무일에 사용한다. 해당 월을 넘겨 이월하거나 현금으로 지급하지 않는다. 생일 특별휴가는 분할할 수 없다.

<!-- kind: added_fictional -->
신청서에는 사용하려는 날짜를 생일과 구별해 기록한다. 오전 또는 오후만 선택된 경우에는 임의로 연차로 바꾸지 않고 선택 오류인지 신청 의도인지 확인하여 해당 요청의 정정 이력을 남긴다.

#### BD-03 신청 기한과 승인

<!-- kind: preserved -->
생일 특별휴가는 사용 3영업일 전까지 휴가 시스템에서 신청하고 팀장의 승인을 받아야 한다.

<!-- kind: added_fictional -->
접수 확인과 승인 통지를 별도 상태로 표시한다. 신청 내용을 확인했다는 안내에는 승인 여부가 아직 확인되지 않았는지를 함께 적는다. 담당자는 팀장의 판단을 대신하는 문구로 접수 메시지를 작성하지 않는다. 신청한 날짜와 승인 내역의 날짜가 다르면 어느 요청에 대한 통지인지 연결 관계부터 확인하고, 같은 이름의 다른 휴가 기록을 승인 근거로 붙이지 않는다.

### 제2절 신청 정보의 처리 [BD-S2]

#### BD-04 접수부터 결과 통지까지

<!-- kind: added_fictional -->
휴가 시스템에서 접수한 생일 특별휴가 신청에는 신청자를 식별하는 정보, 사용 예정일, 신청을 구분하는 기록 번호를 연결한다. 이미 입력되어 있는 생일이나 입사 정보를 신청자에게 다시 증명하도록 요구하지 않고, 신청 화면과 인사 기록 사이에 차이가 있는 항목만 확인 대상으로 표시한다. 신청자가 설명을 덧붙인 경우에는 설명의 내용과 원래 시스템 값을 구별해 보관한다. 내용이 비어 있는 칸이 있더라도 어떤 정보가 필요한지 확인하기 전에 자격이 없다고 표시하지 않는다. 담당자는 접수된 요청을 찾을 수 있도록 신청자에게 기록 번호나 식별 가능한 제목을 안내하고, 접수 확인이 팀장 승인과는 다른 단계임을 알린다. 사용 예정일이 잘못 입력된 것으로 보이면 임의로 생일 당일이나 다음 근무일로 바꾸지 않고 원래 희망일을 확인한다. 신청자가 여러 날짜를 검토하다가 남긴 임시 입력과 최종 제출 기록이 함께 보이는 경우에는 제출 상태와 작성 시간을 비교하여 어떤 기록이 검토 대상인지 먼저 정리한다.

담당자는 BD-01@v4의 적용 기준과 BD-02@v4의 사용 범위를 확인한 후, 요청의 식별 정보와 현재 내용을 팀장이 확인할 수 있는 상태로 정리한다. 이때 재직 기간 확인, 수습 구분 확인, 날짜 확인은 각각의 점검 항목으로 남기며 어느 하나의 확인이 다른 항목을 대신한 것으로 기록하지 않는다. 팀장에게 전달한 뒤 신청자가 날짜의 오입력을 알린 경우에는 기존 전달본과 정정 요청을 함께 연결한다. 정정 전 요청이 검토 중인지 이미 통지되었는지에 따라 현재 상태를 표시하되, 담당자가 상태 이름을 바꾸었다는 이유만으로 승인 내용까지 변경되었다고 보지 않는다. 보완을 문의할 때에는 확인이 필요한 정보와 이미 확인된 정보를 나누어 설명하고, 일반적인 접수 양식을 따르지 못했다는 이유만으로 BD-03@v4의 신청 기회를 제한하지 않는다. 신청자의 표현이 불명확하여 서로 다른 해석이 가능하면 확인 질문과 그에 대한 답을 같은 요청에 남겨 이후 담당자가 처음부터 다시 묻지 않도록 한다.

팀장의 승인 내용이 확인되면 신청자에게 사용 날짜와 처리 대상 요청을 식별할 수 있는 정보를 함께 통지한다. 여러 요청 중 하나에 관한 결과라면 다른 요청까지 같은 결과로 처리된 것처럼 표시하지 않는다. 통지 이후 신청자가 화면에서 다른 날짜를 보았다고 알린 경우에는 통지문, 승인 기록, 현재 표시값을 대조하고 차이가 생긴 위치를 확인한다. 전달 오류가 확인되면 오류가 있었던 안내와 바로잡은 안내를 연결하여 남기며, 과거 메시지를 지워 처음부터 정확했던 것처럼 기록하지 않는다. 신청 내용이 유지된 상태에서 안내만 정정한 경우와 신청 날짜 자체를 바꾸는 경우를 구별한다. 전자는 기록 전달의 정정이고 후자는 신청 내용의 변경으로 다룬다. 처리 중인 요청을 다른 담당자에게 넘길 때에는 확인을 마친 항목, 답변을 기다리는 항목, 팀장의 결과가 필요한 항목을 구분하여 전달한다. 신청자에게는 담당자가 바뀌었다는 이유로 동일 신청을 새로 제출하게 하지 않고 기존 기록을 이어서 확인할 수 있게 한다.

#### BD-05 시스템 장애와 중복 접수

<!-- kind: added_fictional -->
통상적인 접수는 BD-04@v4의 시스템 기록을 기준으로 정리한다. 다만 시스템에 접속할 수 없거나 제출 후 접수 화면이 표시되지 않아 기록 존재를 확인할 수 없는 경우에는 담당자가 신청자가 알린 시점, 사용 희망일, 장애 상황을 임시 기록으로 남기고 이를 접수 확인용으로 안내한다. 임시 기록은 새로운 휴가 자격이나 승인 면제가 아니며, 원래 신청 시점과 이후 복구 입력 시점을 구별하기 위한 자료로 사용한다. 시스템이 복구되면 기존 기록이 실제로 생성되어 있는지를 먼저 찾아보고, 존재하지 않는 경우에만 임시 기록과 연결하여 입력한다. 임시 기록의 작성만을 이유로 신청 기한이 연장되었다고 안내하거나 팀장 승인 없이 사용이 확정되었다고 통지하지 않는다. 기한 또는 승인 여부의 판단이 필요한 항목은 원래 사실관계가 보이도록 남겨 BD-03@v4의 절차에서 확인한다. 동일 내용을 반복 제출한 흔적이 있을 때에는 신청자에게 대표 요청을 확인하고 나머지 기록을 중복으로 연결하되, 중복 표시가 휴가 일수의 추가 사용이나 신청 취소를 뜻하지 않도록 처리 상태를 설명한다.

#### BD-06 날짜 변경과 취소 의사 확인

<!-- kind: added_fictional -->
신청자가 사용 날짜를 바꾸려는 경우에는 어느 요청을 어떤 날짜로 바꾸려는지 확인하고 변경 전후 값을 함께 남긴다. 원래 날짜를 유지한 채 설명만 바로잡는 것인지, 실제 사용 날짜를 변경하는 것인지 구분한다. 다만 신청자가 문의 과정에서 여러 날짜를 예로 들었을 뿐 변경 의사를 확정하지 않은 경우에는 문의 내용을 새 신청으로 등록하지 않는다. 변경이 확정된 요청은 BD-04@v4의 현재 처리 상태와 연결하여 검토·통지하며, 승인 여부를 문의했다는 이유만으로 승인 완료 표시를 붙이지 않는다. 취소 의사가 전달되면 대상 요청을 식별하여 현재 사용 기록과 대조하고, 이미 기록이 반영된 경우에는 어떤 기록을 바로잡아야 하는지 확인한다. 취소 요청을 받았다는 사실과 실제 기록 정리가 끝났다는 사실을 분리해 안내하고, 담당자의 확인이 끝나지 않은 값을 개인별 잔여 일수로 단정하지 않는다.

#### BD-07 생일 축하 포인트의 관계

<!-- kind: added_fictional -->
생일 축하 포인트 지급 내역은 생일 특별휴가의 신청 번호와 별개로 식별한다. 포인트를 받았다는 문의가 휴가 승인 확인으로 접수되면 문의 목적을 먼저 구분하고, 휴가에 관한 내용은 BD-03@v4의 승인 기록에서 확인한다. 지급 내역 화면을 휴가 승인서 대신 첨부하거나 두 상태를 같은 항목으로 합치지 않는다.

## 제2장 연차의 사용과 기록 관리 [AN]

### 제1절 발생과 사용 단위 [AN-S1]

#### AN-01 발생 기준

<!-- kind: preserved -->
1년 미만 재직자는 한 달 개근 시 연차 1일이 발생한다. 1년 이상 재직자의 연차는 매년 15일을 기준으로 별도 산정한다.

<!-- kind: added_fictional -->
연차 내역을 확인할 때에는 발생 기준에 관한 정보와 실제 사용 기록을 구분하여 표시한다. 특정 직원의 계산 결과를 안내할 경우에는 적용한 재직 기간과 확인한 기록의 범위를 함께 남긴다.

#### AN-02 발생 내역의 확인과 정정

<!-- kind: added_fictional -->
연차 발생 내역을 문의받은 담당자는 먼저 문의가 발생 일수에 관한 것인지 사용 후 남은 일수에 관한 것인지 확인한다. 발생 일수 문의에는 적용된 재직 기간과 개근 여부가 어떻게 기록되어 있는지 살피고, 잔여 일수 문의에는 발생 내역과 차감 내역을 나누어 대조한다. 한 화면에 합계만 표시되어 있을 때에는 그 합계가 어느 시점의 자료인지 확인하며, 최근에 접수한 휴가가 아직 반영되지 않은 상태인지도 함께 기록한다. 자료가 서로 다른 날짜에 조회되어 차이가 나는 경우에는 즉시 계산 오류로 단정하지 않고 같은 기준 시점으로 비교할 수 있는지를 확인한다. 담당자가 조회한 시점과 신청자가 보았다고 설명한 시점은 별도 항목으로 남겨, 이후 값이 달라져도 처음 문의의 이유를 확인할 수 있게 한다. 이 과정에서 담당자는 AN-01@v4에 없는 발생 조건이나 개인별 가산 일수를 임의로 입력하지 않고, 원자료가 확인되지 않는 부분을 미확인 항목으로 표시한다.

확인에 사용한 인사 기록 중 입사 정보나 근무 정보가 잘못 연결되어 있으면 오류가 의심되는 값, 확인에 사용한 출처, 정정 요청의 진행 상태를 기록한다. 단순히 계산 결과가 예상보다 작다는 이유로 발생 내역을 직접 늘리거나, 예상보다 크다는 이유로 근거 없이 줄이지 않는다. 원자료가 정정되면 정정 전 계산에 사용한 값과 정정 후 값을 구분하여 다시 대조한다. 동일한 원자료를 여러 화면에서 참조하고 있을 경우에는 어느 화면까지 새 값이 반영되었는지 확인하고, 아직 반영되지 않은 화면의 수치를 최종 결과로 안내하지 않는다. 원자료의 오류 확인과 계산 결과의 반영이 서로 다른 담당 업무이면 양쪽의 확인 내용을 연결하되, 담당자 사이에서 자료를 넘겼다는 사실만으로 정정 완료 상태를 표시하지 않는다. 문의자에게는 확인된 사항과 추가 확인 중인 사항을 나누어 안내하며, 아직 확인하지 못한 출근 기록을 개근 사실로 가정하여 결과를 설명하지 않는다.

발생 내역과 사용 내역이 함께 달라진 문의에서는 두 차이를 따로 정리한다. 예를 들어 발생 기록의 정정이 필요한 상황에서 동시에 중복 차감이 발견되면, 하나의 합계 수정으로 두 사유를 덮지 않고 각각의 변경 근거를 연결한다. 이미 안내한 합계가 잠정 값이었다면 새 안내에도 이전 안내와 비교할 수 있는 기준 시점을 표시한다. 정정 결과를 전달한 뒤 다시 문의가 들어오면 과거 문의 번호와 현재 문의 번호를 연결하고, 새롭게 제기된 차이가 무엇인지 먼저 확인한다. 동일한 설명을 다시 요구하는 대신 기존 대조 자료에서 확인할 수 있는 항목은 재사용한다. 다만 이전 문의가 다른 기간이나 다른 신청 건에 관한 것이었다면 그 결과를 그대로 적용하지 않고 대상 기간을 구분한다. 관련 자료에 없는 보상이나 소멸 여부가 함께 질문된 경우에는 발생·사용 수치 확인과 별도 항목으로 남기고, 확인 중인 계산 값을 그러한 처리의 근거로 사용하지 않는다.

#### AN-03 반차의 사용 단위

<!-- kind: preserved -->
연차는 오전 또는 오후 반차로 나누어 사용할 수 있다. 반차 1회는 연차 0.5일로 차감한다.

<!-- kind: added_fictional -->
반차 신청 내역에는 오전과 오후 중 선택한 구분을 기록한다. 하루 사용과 반차 사용이 같은 날 함께 표시되면 담당자는 실제 신청 의도를 확인하여 중복 여부를 정리하며, 선택 오류를 다른 휴가 제도의 분할 허용으로 해석하지 않는다.

### 제2절 신청과 사용 기록 [AN-S2]

#### AN-04 통상 신청과 확인 정보

<!-- kind: preserved -->
연차는 사용 2영업일 전까지 휴가 시스템에서 신청한다. 긴급 사유가 있으면 당일 팀장에게 알린 후 신청할 수 있다.

<!-- kind: added_fictional -->
연차 신청을 접수하면 사용 예정일, 하루 또는 반차 구분, 원래 제출 기록을 식별할 수 있는 정보를 연결한다. 신청자가 작성한 자유 서술의 개인 사유를 사용 일수 계산 항목과 혼합하지 않는다. 시스템에 기재된 기간과 신청자가 설명한 기간이 다르면 달력상 시작일과 종료일, 실제 사용하려는 날짜를 먼저 확인한다. 표시된 기간 전체를 임의로 근무일로 가정하여 차감 일수를 계산하지 않으며, 이 규정집에 없는 개인 근무표를 추정해 입력하지 않는다. 작성 도중 남은 임시 저장본은 최종 제출본과 구분하고, 임시 저장 화면을 확인했다는 안내가 제출 완료로 오인되지 않도록 기록 상태를 함께 적는다. 신청자가 같은 요청의 제목만 바꾸어 다시 제출했다면 제목의 차이만으로 별도 사용 건으로 계산하지 않고 날짜와 사용 단위를 대조한다. 담당자가 요청을 찾기 위해 추가 설명을 문의할 때에는 이미 시스템에서 확인되는 정보를 반복 제출하도록 요구하지 않으며, 필요한 정정 내용만 신청자가 확인할 수 있게 제시한다.

#### AN-05 검토 내용의 연결과 처리 통지

<!-- kind: added_fictional -->
담당자는 접수된 연차 신청을 해당 직원의 사용 기록과 연결할 때 기록 번호, 사용 날짜, 사용 단위를 차례로 대조한다. 같은 직원이 같은 날 다른 종류의 휴가를 문의한 경우에도 문의 기록을 곧바로 사용 기록으로 옮기지 않는다. 이미 반영된 신청과 새 요청이 겹치면 중복 제출인지 날짜 변경인지 구분하기 위해 신청자에게 현재 의사를 확인한다. 확인 과정에서는 어떤 기록을 비교하고 있는지 신청자가 알 수 있도록 대상 날짜와 요청의 식별 정보를 제시하며, 개인 사유의 상세한 설명을 새 자격 조건으로 요구하지 않는다. 요청에 누락된 정보가 발견되면 누락 항목과 확인 방법을 안내하고, 내용 확인을 기다리는 상태와 신청이 없었던 상태를 구분한다. 최초 제출 사실이 남아 있는데 단순 보완을 이유로 그 시점을 지우거나, 보완 입력 날짜를 원래 신청 날짜처럼 바꾸지 않는다. AN-04@v4의 통상 기한과 긴급 신청 규칙은 이러한 내부 기록 정리 과정과 별개로 유지한다.

검토 중에는 확인이 끝난 정보와 아직 문의 중인 정보를 분리하여 표시한다. 사용 기록의 수치가 서로 다르면 담당자는 어느 자료에서 차이가 생겼는지를 찾고, 신청자의 정정 요청과 원래 기록을 함께 남긴다. 시스템의 상태 코드가 다른 화면과 다르게 보이는 경우에는 코드 이름만 보고 사용이 확정되었거나 취소되었다고 단정하지 않는다. 해당 상태가 접수, 정보 확인, 사용 기록 반영 중 어느 과정을 나타내는지 확인하고 그 의미를 안내한다. 이미 팀장에게 알린 긴급 신청이라면 그 통지 사실이 접수 기록에 연결되어 있는지 별도로 살핀다. 다만 통지 내용을 담당자가 열람하지 못했다는 이유만으로 통지 자체가 없었다고 기록하지 않고 확인되지 않은 항목으로 남긴다. 여러 담당자가 같은 신청을 순차적으로 확인할 때에는 앞서 확인한 원자료의 위치와 미확인 사항을 전달하여 동일 문의가 반복되지 않도록 한다. 담당자 변경은 신청의 새로운 발생이나 별도 휴가 사용을 뜻하지 않는다.

신청 관련 기록이 정리되면 신청자에게 현재 처리 상태, 반영된 날짜와 사용 단위, 남아 있는 확인 사항을 구분하여 전달한다. 기록에 대한 안내에는 그것이 접수 확인인지 정보 정정 완료인지 실제 사용 내역 반영인지 드러나야 한다. 이 장에 명시하지 않은 별도 승인권자를 추가하거나 담당자의 내부 대조를 새로운 사용 자격 심사로 표시하지 않는다. 신청자가 통지 내용이 원래 요청과 다르다고 알리면 통지문과 원래 제출본을 먼저 대조한다. 잘못 안내한 항목이 발견되면 정정 안내에 변경한 항목과 변경하지 않은 항목을 함께 표시하여 전체 요청이 바뀐 것처럼 보이지 않게 한다. 결과를 확인했다는 신청자의 회신은 기록의 내용 확인으로 남기며, 다른 기간에 대한 권리 포기나 향후 모든 정정 요청의 철회로 확대해 해석하지 않는다. 문의가 끝난 뒤에도 정정이 필요할 수 있으므로 관련 기록의 식별 관계를 유지하고, 새로운 문의가 들어오면 어느 이전 기록과 이어지는지를 확인하여 처리한다.

#### AN-06 긴급 신청의 접수 예외

<!-- kind: added_fictional -->
통상적인 신청 경로와 달리 긴급 사유로 당일 팀장에게 알린 후 신청한 경우에는 통지에 관한 정보와 시스템 신청 기록을 연결한다. 담당자는 신청자가 전달한 긴급 사유의 존재와 통지 내용을 확인할 수 있는 범위에서 정리하되, 이 규정집에 없는 긴급 사유의 목록을 만들어 일률적으로 제외하지 않는다. 통지 사실에 대한 확인과 연차 사용 단위의 확인은 별도로 처리하며, 통지된 날짜가 사용 날짜와 어떻게 연결되는지 표시한다. 시스템 입력이 뒤이어 이루어졌다면 입력 시각만으로 앞선 통지를 없었던 것으로 취급하지 않고 두 사건의 순서를 남긴다. 긴급 신청으로 처리한 기록은 AN-05@v4의 검토·통지 과정에서도 그 구분을 유지한다. 당일 접수가 가능하다는 안내를 모든 연차 신청의 일반 기한으로 바꾸지 않으며, 긴급성이 확인되지 않은 문의에는 통상 기한과 확인 중인 사항을 나누어 설명한다. 같은 직원의 다른 날짜 신청까지 긴급 신청으로 일괄 변경하거나, 긴급 신청을 했다는 이유로 차감 단위를 다르게 적용하지 않는다.

### 제3절 이월과 변경 이력 [AN-S3]

#### AN-07 미사용 연차의 이월 기준

<!-- kind: preserved -->
해당 연도에 사용하지 않은 연차 중 최대 5일분을 다음 해로 이월할 수 있다. 이월한 연차의 사용 기한은 다음 해 3월 31일이다. 생일 특별휴가에는 이 규정을 적용하지 않는다.

<!-- kind: added_fictional -->
이월 기록에는 원래 연도와 사용 기한을 구별하여 표시한다. 다른 휴가 종류의 잔여 표시를 이월할 연차에 포함하지 않고, 종류가 불분명한 내역은 합산하기 전에 확인 대상으로 남긴다.

#### AN-08 연도를 넘긴 내역의 대조

<!-- kind: added_fictional -->
전년도에서 넘어온 연차와 해당 연도에 발생한 연차가 같은 화면에 표시되면 담당자는 각각의 출처 연도와 반영 내용을 확인할 수 있도록 기록을 구분한다. 합계 수치만 전달되어 원래 연도를 알 수 없는 경우에는 가능한 자료에서 원래 발생·사용 내역을 확인하고, 확인되지 않은 부분을 임의로 전년도분이나 당년도분으로 배정하지 않는다. 이월 가능한 양과 이월분의 사용 기한은 AN-07@v4의 서로 다른 조건이므로 별도 항목으로 안내한다. 달력의 특정 날짜에 해당하는 숫자와 일수에 해당하는 숫자를 같은 값으로 변환하지 않으며, 기간 안내를 작성할 때에는 어느 해에서 어느 해로 넘어온 내역인지 함께 표시한다. 담당자가 화면에 붙인 설명이나 합계의 정정은 그 자체로 새로운 발생·소멸 규칙을 만드는 행위가 아니며, 근거가 없는 잔여분 처리 결과를 자동으로 입력하지 않는다. 기록의 구분만으로 사용 순서를 새로 정하거나 특정 출처의 연차부터 사용해야 한다고 안내하지 않는다.

연도 경계에 걸친 기록 오류를 정정할 때에는 최초 이월 표시, 이후 사용 기록, 정정을 요청한 이유를 함께 살핀다. 이전 화면이 이미 갱신되어 최초 표시를 직접 볼 수 없으면 조회 가능한 이력의 범위와 확인하지 못한 부분을 구분해 남긴다. 신청자가 보관한 내역을 참고하는 경우에도 그 자료의 기준 시점과 시스템 기록의 기준 시점을 먼저 맞춘다. 확인되지 않은 숫자를 맞추기 위해 다른 휴가의 사용 내역을 옮겨 적거나, 수치를 일치시키는 데 필요한 일수를 임의로 발생시켜 넣지 않는다. 잘못 연결된 신청이 발견되면 원래 신청과 올바른 출처를 대조하여 연결 오류를 정정한다. 변경된 합계를 안내할 때에는 어느 기록이 정정되어 차이가 생겼는지 설명하며, 다른 항목은 아직 확인 중이라면 그 사실을 별도로 알린다. 이월하지 못한 나머지 연차의 보상이나 소멸 처리는 이 규정집에서 정하지 않으므로, 단순히 화면에 값이 없다는 이유로 보상 완료 또는 소멸 완료라고 통지하지 않는다.

#### AN-09 사용 날짜와 반차 구분의 변경

<!-- kind: added_fictional -->
사용 날짜를 바꾸려는 요청에서는 원래 날짜, 변경하려는 날짜, 유지하려는 사용 단위를 서로 구분한다. 반차를 오전에서 오후로 바꾸는 요청은 날짜 변경과 다른 항목으로 표시하고, 동일 날짜의 다른 신청이 이미 있는지도 대조한다. 하루 사용을 반차로 바꾸거나 반차를 하루 사용으로 바꾸려는 경우에는 AN-03@v4의 단위에 맞게 현재 신청 내용을 확인하되, 신청자의 의사가 확인되지 않은 상태에서 차감량을 먼저 바꾸지 않는다. 화면의 오전·오후 선택값이 뒤바뀌어 보이는 오류와 실제 희망 시간이 바뀐 요청은 처리 이유를 구별하여 남긴다. 신청자가 날짜를 잘못 말한 뒤 바로 정정한 경우에는 최신 의사를 확인할 수 있는 회신을 연결하고, 이전 표현만을 근거로 추가 휴가를 사용한 것으로 표시하지 않는다. 변경 요청이 여러 번 이어지더라도 최초 신청과 각 변경의 관계를 유지하여 마지막 값만 남겨 중간 확인 과정을 알 수 없게 만들지 않는다.

변경 과정에서 당일 긴급 사유가 새로 전달되면 AN-06@v4의 접수 예외와 연결하여 확인한다. 다만 날짜를 바꾸었다는 사실만으로 모든 변경을 긴급 신청으로 처리하지 않는다. 변경 후 기록과 원래 기록이 동시에 표시되는 경우에는 어떤 기록이 현재 확인 대상인지 신청자에게 알려 중복 사용으로 오인되지 않게 한다. 반영이 끝나지 않은 화면을 보고 추가 변경을 요청한 경우에는 그 화면의 기준 시점과 최신 요청을 대조한 뒤 처리 순서를 정리한다.

#### AN-10 취소 요청과 사용 기록 정리

<!-- kind: added_fictional -->
취소 요청을 받으면 대상 신청의 기록 번호와 사용 날짜를 확인하여 신청자가 철회하려는 범위를 분명히 한다. 여러 날짜의 요청 중 일부만 취소하려는 경우에는 유지하는 날짜와 취소하는 날짜를 나누어 기록하고, 전체 신청을 일괄 삭제하지 않는다. 실제 사용 여부가 아직 확인되지 않았거나 사용 내역 반영이 지연되고 있으면 담당자는 신청 취소 의사와 기존 사용 사실의 확인을 구분해 처리한다. 취소 요청이 접수되었다는 이유만으로 모든 차감이 이미 복구되었다고 안내하지 않으며, 반영된 수치와 아직 대조 중인 수치를 구분한다. 중복 입력된 기록 하나를 정리하는 경우에는 동일 신청의 다른 정상 기록이 남아 있는지를 먼저 확인하여 정상 사용까지 취소되지 않게 한다. 정리 후에는 대상 기록과 현재 상태를 신청자가 식별할 수 있도록 안내하고, 정리 사유가 취소인지 중복 입력의 수정인지 표시한다.

취소라는 표현 없이 일정 문의만 들어온 경우에는 문의 내용을 즉시 철회 의사로 기록하지 않는다. 반대로 신청자가 취소 의사를 분명하게 밝혔지만 기록 번호를 기억하지 못하는 경우에는 확인 가능한 날짜와 기존 내역으로 대상 요청을 찾는다. 기록 번호를 다시 제출하지 못했다는 사유를 새로운 취소 제한으로 만들지 않고, 어떤 신청을 대상으로 처리했는지 확인 내용을 남긴다.

#### AN-11 접속 장애와 자료 불일치의 분리 처리

<!-- kind: added_fictional -->
시스템 장애로 신청 내용이나 접수 결과를 볼 수 없는 경우에는 담당자가 사용 희망일, 사용 단위, 신청자가 알린 상황과 시점을 임시 기록으로 남긴다. 이는 AN-04@v4의 통상 신청 방식이 정상 작동하지 않을 때 기록의 연속성을 유지하기 위한 예외이며, 원래 신청 기한이나 긴급 사유 조건을 없애는 절차가 아니다. 복구 후에는 이미 생성된 신청을 먼저 찾아 중복 입력을 피하고, 임시 기록으로만 남아 있는 경우에는 최초 전달 시점과 복구 입력 시점을 함께 보존한다. 장애 중 화면에 보인 합계가 복구 후 값과 다르면 담당자는 장애 당시 화면의 정보와 실제 원장 반영을 분리해 대조한다. 화면이 열리지 않았다는 사실만으로 사용 기록이 삭제되었다고 보거나, 복구 뒤 표시되는 내역을 모두 새로운 신청으로 간주하지 않는다. 확인되지 않은 부분은 자료 불일치로 표시하여 AN-02@v4의 대조 과정으로 연결한다.

신청자가 다른 종류의 휴가와 비교해 문의한 경우에는 해당 제도의 규칙과 연차 규칙을 구별해 답할 수 있도록 문의 항목을 나눈다. 생일 특별휴가의 날짜 범위와 분할 여부는 BD-02@v4에서 확인하며, 연차 이월이나 반차 규칙을 그대로 옮겨 적용하지 않는다. 처리 안내를 정정할 때에도 어느 제도에 대한 설명을 바꾼 것인지 표시하여 다른 신청 기록이 영향을 받은 것으로 오인되지 않게 한다.

## 제3장 재택근무의 신청과 운영 [RM]

### 제1절 신청 범위와 기본 조건 [RM-S1]

#### RM-01 신청 대상

<!-- kind: preserved -->
입사 후 1개월이 지난 직원은 보안 교육을 이수하면 재택근무를 신청할 수 있다. 현장 장비 운영 직무는 재택 대상에서 제외한다.

<!-- kind: added_fictional -->
대상 확인에서는 재직 기간, 교육 이수 정보, 직무 구분을 각각 확인한다. 교육 이수 화면에 표시 오류가 있으면 확인이 필요한 항목을 기록하고, 그 오류를 새로운 자격 요건이나 교육 재수강 의무로 바꾸지 않는다.

#### RM-02 횟수와 승인 기한

<!-- kind: preserved -->
재택근무는 매주 최대 2일이며 전주 금요일까지 팀장 승인을 받는다. 재택근무는 휴가가 아닌 근무일로 집계한다.

<!-- kind: added_fictional -->
신청 내역에는 대상 주와 희망 날짜를 구분해 표시한다. 여러 날짜가 함께 제시되면 최종적으로 어떤 날짜를 신청한 것인지 확인하며, 일정 문의에 적힌 모든 후보 날짜를 승인된 근무일로 등록하지 않는다.

#### RM-03 기기와 내부 문서 접근

<!-- kind: preserved -->
재택근무 시 회사 지급 기기와 회사 VPN을 사용한다. 공용 컴퓨터로 내부 문서에 접근할 수 없다.

<!-- kind: added_fictional -->
기기 정보의 확인은 회사 지급 기기와 신청자의 현재 사용 기기가 연결되어 있는지를 대조하는 과정으로 기록한다. 연결 정보가 잘못 표시되었다는 문의를 받으면 오류가 있는 항목과 실제 확인 결과를 구별해 남기고, 단순한 정보 정정 문의를 개인 기기 사용 허용 요청으로 처리하지 않는다.

### 제2절 접수와 장소 정보 [RM-S2]

#### RM-04 근무 신청의 검토와 통지

<!-- kind: added_fictional -->
재택근무 신청을 접수하면 담당자는 신청자, 대상 주, 희망 날짜와 원래 제출본을 서로 연결한다. 대상 주와 날짜가 맞지 않거나 날짜가 여러 주에 걸쳐 있으면 표시된 기간을 임의로 하나의 주로 묶지 않고 신청 의도를 확인한다. 이미 접수된 다른 신청과 날짜가 겹치면 최초 요청, 정정 요청, 단순 조회를 구분하여 정리한다. 신청자가 이전 주의 내용을 복사해 작성한 경우에는 복사된 주소나 날짜가 현재 요청에 맞는지 확인할 수 있게 안내하고, 이전 승인 번호가 새 요청의 승인 번호로 잘못 붙지 않도록 한다. 담당자는 RM-01@v4의 적용 조건과 RM-02@v4의 주간 한도 및 승인 기한을 각각 점검 항목으로 남긴다. 어느 하나의 조건이 충족되었다는 사실로 다른 조건까지 확인된 것으로 표시하지 않는다. 신청 화면에 교육 이수 정보가 아직 반영되지 않았으면 실제 확인이 끝난 항목과 시스템 반영을 기다리는 항목을 나누어 기록하고, 신청자에게는 무엇을 확인하고 있는지 알 수 있도록 안내한다.

확인 자료를 정리할 때에는 등록된 근무 장소, 사용 기기의 연결 정보, 대상 날짜를 한 요청 안에서 서로 구분한다. 장소의 표기가 달라졌다는 이유로 기기 정보까지 변경된 것으로 처리하거나, 기기를 교체했다는 이유로 근무 날짜를 새로 생성하지 않는다. 팀장이 확인할 내용에는 신청자가 처음 제출한 정보와 이후 정정한 정보를 함께 연결하되, 현재 판단 대상이 어느 값인지 분명히 표시한다. 신청자의 설명이 담당자의 요약과 다르다고 확인되면 요약을 바로잡고 원래 설명을 확인할 수 있게 남긴다. 주소나 기기 정보의 단순 표기 정정이 있었던 경우에는 그 정정이 실제 장소 변경이나 승인 날짜 변경을 뜻하는지 별도로 확인한다. 담당자는 기록을 정리하는 내부 검토를 팀장의 승인과 혼합하지 않으며, 접수 화면에서 처리 단계가 이동했다는 사실만으로 승인 완료 통지를 보내지 않는다. 여러 담당자가 일부 항목씩 확인하는 경우에는 확인한 항목의 범위와 남은 확인 사항을 같은 요청에 모아 중복 문의를 줄인다.

승인 내용이 확인되면 신청자에게 대상 날짜, 해당 주, 처리 대상 신청을 식별할 수 있는 정보를 안내한다. 일부 날짜만 확인된 경우에는 나머지 날짜도 같은 상태라고 보이도록 묶어 통지하지 않는다. 신청자가 받은 메시지와 화면에 나타난 날짜가 다르다고 알리면 승인 기록, 통지 내용, 화면 표시를 차례로 대조한다. 통지의 오입력이라면 올바른 안내와 정정 사유를 원래 메시지에 연결하고, 신청 자체의 변경이라면 기존 승인 내역과 변경 요청을 구분해 기록한다. 재택근무가 근무일로 집계된다는 설명은 식대 지원의 별도 조건을 결정하지 않으므로, 근무 상태와 복지 내역을 같은 확인 결과로 묶지 않는다. 처리 도중 담당자가 바뀌어도 처음 접수한 신청의 식별 관계는 유지하고, 신청자에게 동일 내용을 새 신청으로 다시 작성하도록 안내하지 않는다. 이전 담당자의 검토가 어디까지 진행되었는지 확인할 수 없는 경우에는 미확인 범위를 명시하여 이어서 확인하며, 추정으로 빈 항목을 채우지 않는다.

#### RM-05 등록 자택과 주소 변경 요청

<!-- kind: preserved -->
재택근무 장소는 등록한 자택으로 제한한다. 주소 변경 시 근무 시작 전에 인사 담당자에게 등록 주소 변경을 요청한다.

<!-- kind: added_fictional -->
주소 변경 요청에는 기존 등록 주소를 식별할 수 있는 정보와 변경하려는 주소를 연결하여 남긴다. 주소 전체를 여러 기록에 반복 복사하기보다 어느 등록 정보에 대한 변경인지 확인할 수 있는 연결 관계를 유지한다. 변경 사유를 문의받았을 때에는 신청자가 알린 내용과 담당자가 확인한 등록 상태를 구별하며, 주소 표기 오입력의 수정과 실제 거주 장소 변경을 같은 항목으로 처리하지 않는다. 건물명이나 호수의 표시가 빠진 경우에는 이미 등록된 내용과 비교해 필요한 정정만 확인하고, 단순한 표기 차이를 등록 장소 밖의 근무로 단정하지 않는다. 반대로 장소가 실제로 바뀌었는데 주소 이름만 같아 보인다는 이유로 변경 요청이 필요하지 않다고 안내하지 않는다. 담당자는 근무 시작 전 변경 요청이라는 조건에 관한 기록과 주소 정보의 실제 반영 상태를 따로 남겨, 반영 화면만으로 요청 시점을 추정하지 않게 한다.

통상적으로는 등록 정보와 변경 요청을 시스템에서 확인하여 처리하지만, 주소 변경 화면이 열리지 않는 경우에는 인사 담당자가 변경을 알린 시점과 대상 주소 정보의 위치를 임시 기록으로 연결한다. 복구 후에는 이미 반영된 변경이 있는지 대조하고, 임시 요청이 정식 기록에 이어졌는지 확인한다. 이 예외는 변경 요청의 흔적을 유지하기 위한 것으로, 등록하지 않은 장소에서의 근무를 허용하는 별도 조건이 아니다. 재택 신청과 주소 변경 요청이 동시에 진행되면 RM-04@v4의 근무 신청에 주소 확인 상태를 연결하여 같은 요청이 중복 처리되지 않게 한다. 주소를 정정했다는 통지를 받았다는 이유로 근무 날짜에 대한 팀장 승인까지 완료된 것으로 표시하지 않는다. 변경 내용을 안내할 때에도 등록 정보 정정의 결과인지 근무 신청의 결과인지 구분한다.

#### RM-06 기기 정보의 정정과 확인 기록

<!-- kind: added_fictional -->
신청자와 회사 지급 기기의 연결 정보가 잘못 표시되었다는 문의가 있으면 담당자는 화면의 기기 식별 정보와 확인 가능한 지급 내역을 비교한다. 같은 직원에게 연결된 예전 기기가 표시되는 경우에는 현재 사용하는 기기와 과거 기록을 구분하고, 예전 기록을 단순히 지워 지급 이력을 알 수 없게 하지 않는다. 기기 교체가 있었는지, 표시 이름만 달라졌는지, 다른 직원의 항목이 잘못 연결되었는지를 확인한 뒤 정정 범위를 정한다. 정보 확인을 위해 문의한 내용은 재택 신청의 해당 항목과 연결하되, 기기의 비밀번호나 내부 문서 내용을 신청 설명에 적게 하지 않는다. RM-03@v4의 회사 지급 기기 사용 조건은 정보 정정 과정에서도 유지하며, 지급 여부를 확인하지 못한 기기를 임의로 확인 완료 상태로 바꾸지 않는다. 문의자가 기기 정보의 정정만 요청한 경우에는 이를 새로운 재택 날짜 신청이나 기존 승인 취소로 처리하지 않는다.

기기 정보가 바로잡힌 뒤에는 어느 항목을 수정했는지와 그 정정이 어떤 신청에 연결되는지를 기록한다. 화면에 반영되기 전에 안내가 먼저 전달된 경우에는 실제 반영 상태를 확인하여 안내와 화면의 차이를 설명한다. 동일 오류가 다른 날짜의 신청에도 나타나면 관련 기록을 찾아 연결하되, 각 신청의 승인 내용을 한꺼번에 변경하지 않는다. 사용 가능한 회사 기기가 확인되었다는 사실만으로 VPN 사용 여부도 확인된 것으로 기록하지 않고 두 항목을 분리한다. 기기 확인이 끝났다는 안내에 근무 장소나 날짜까지 승인되었다는 의미를 덧붙이지 않는다.

### 제3절 변경과 장애의 기록 [RM-S3]

#### RM-07 VPN 연결 확인과 장애 접수

<!-- kind: added_fictional -->
VPN 사용에 문제가 있다는 연락을 받으면 담당자는 연결이 되지 않는 상황인지, 연결 상태가 화면에 잘못 표시되는 상황인지, 접속하려는 문서를 찾지 못하는 상황인지 구분하여 기록한다. 서로 다른 문제를 하나의 장애로 묶으면 회사 지급 기기의 확인과 VPN 연결 확인이 뒤섞일 수 있으므로 어떤 항목을 확인했는지 남긴다. 통상적인 상태 확인으로 문제를 파악할 수 없을 때에는 발생 시점과 화면에 나타난 현상을 확인 가능한 범위에서 기록하고 관련 담당 업무로 연결한다. 다만 장애를 알렸다는 이유로 RM-03@v4의 회사 VPN 사용 조건이 면제되었다고 안내하지 않으며, 공용 컴퓨터를 이용해 내부 문서에 접근하도록 임시 우회 방법을 제시하지 않는다. 확인 과정에 필요한 기기 구분은 RM-06@v4의 기기 정보와 연결하고, 신청자에게 비밀번호나 업무 문서의 실제 내용을 재택 신청란에 옮겨 적도록 요구하지 않는다. 장애 접수는 기술적인 상태 확인에 관한 기록이며 팀장 승인이나 근무 장소 등록을 대신하지 않는다.

연결이 복구되었다는 연락을 받으면 복구 확인 시점과 최초 장애 접수 시점을 구분하고, 어느 문제가 해결되었는지 기록한다. 다른 문제가 남아 있다면 전체 장애가 해소된 것처럼 표시하지 않는다. 재택 신청 화면의 오류와 VPN 연결 장애가 동시에 발생했을 때에는 각각의 처리 내역을 서로 연결하되 하나의 완료 표시로 합치지 않는다. 기기 연결 정보의 정정만 끝난 상태에서 실제 접속까지 확인했다고 안내하거나, 접속이 되었다는 사실만으로 예정된 재택 날짜가 승인되었다고 알리지 않는다.

#### RM-08 승인 날짜의 변경과 신청 철회

<!-- kind: added_fictional -->
재택 날짜 변경 요청을 받으면 원래 승인 또는 검토 대상 날짜와 변경하려는 날짜를 연결한다. 같은 주 안의 날짜 변경인지 대상 주 자체가 달라진 것인지 먼저 구분하고, RM-02@v4의 주간 횟수와 승인 기한을 각각 확인할 수 있도록 기록한다. 이미 다른 재택 신청이 있는 주로 날짜를 옮기려는 경우에는 관련 신청들을 찾아 중복 여부를 대조하되, 서로 다른 주의 일수를 임의로 합산하여 하나의 주간 한도로 안내하지 않는다. 신청자가 후보 날짜를 문의한 단계에서는 문의와 실제 변경 의사를 구별한다. 변경 의사가 확인되면 원래 요청을 유지한 채 변경 요청을 연결하여 팀장에게 전달할 내용을 정리하고, 담당자의 연결 작업이 끝났다는 사실을 변경 승인으로 표시하지 않는다. 날짜 변경과 함께 주소 변경을 알렸다면 RM-05@v4의 등록 정보 처리와 별도로 연결하여 두 변경의 현재 상태가 각각 보이게 한다.

신청 철회를 요청한 경우에는 대상 날짜와 요청을 확인하고, 다른 날짜의 승인을 함께 취소하지 않도록 범위를 구분한다. 철회가 접수되었지만 화면에 반영되지 않은 상태와 실제 기록 정리가 끝난 상태를 따로 안내한다. 단순 중복 신청을 정리하려는 경우에는 정상 신청이 어느 기록인지 확인한 뒤 중복 표시를 붙이며, 중복을 제거했다는 안내가 모든 재택근무 신청의 철회를 뜻하지 않도록 설명한다. 이전 주의 철회 처리를 현재 주의 승인 여부에 자동으로 적용하지 않는다.

#### RM-09 알림 누락과 담당 업무의 인계

<!-- kind: added_fictional -->
팀장의 결과가 기록되어 있으나 신청자가 알림을 받지 못했다고 문의하면 담당자는 요청의 식별 정보, 기록된 결과, 발송된 알림의 대상을 비교한다. 알림의 수신 여부를 확인하는 과정에서 승인 결과 자체를 새로 작성하지 않고, 기존 결과가 어떤 요청에 관한 것인지 먼저 확인한다. 통상적으로는 확인된 기록을 같은 요청에 연결하여 안내하지만 알림 시스템 장애로 발송 이력이 확인되지 않는 경우에는 현재 확인할 수 있는 결과와 알림 확인의 한계를 구별해 전달한다. 이 경우에도 새 안내가 원래 승인 시점을 대신하지 않도록 원래 기록과 연결한다. 다른 사람의 요청에 관한 메시지가 잘못 연결된 것으로 보이면 해당 신청의 결과를 그대로 적용하지 않고 잘못된 연결을 정정한다. 기록의 전달 오류와 날짜 변경은 RM-08@v4의 변경 처리와 구별하여 안내하고, 메시지를 다시 보냈다는 이유로 별도 재택근무일을 생성하지 않는다.

담당자가 자리를 비우거나 업무를 인계하는 경우에는 현재 신청 목록과 미확인 항목을 함께 넘긴다. 접수된 신청을 단순히 새 담당자 이름으로 다시 등록하지 않고 원래 요청의 식별 관계를 유지한다. 신청자가 이미 답한 기기·주소 관련 질문은 확인된 기록을 인계하여 반복 문의를 줄이고, 실제로 확인하지 않은 값은 이전 담당자가 확인했다고 추정해 완료 표시를 붙이지 않는다. 새 담당자가 설명을 보완할 때에는 추가 확인한 부분과 기존 확인 사항을 구별해 남긴다.

#### RM-10 근무 기록에 관한 이견 확인

<!-- kind: added_fictional -->
재택근무 신청 상태와 실제 근무 기록이 다르게 보인다는 문의에서는 어느 날짜의 어떤 값이 다른지를 먼저 특정한다. 신청자에게 표시된 근무일, 승인 내역의 날짜, 집계 화면의 기준 시점을 구별하여 기록하고, 합계 수치만 비교해 오류 여부를 정하지 않는다. 조회 시점 차이로 최근 변경이 아직 반영되지 않은 것인지, 서로 다른 신청이 연결된 것인지, 날짜 자체가 잘못 입력된 것인지를 살핀다. 담당자는 확인할 수 있는 원자료와 신청자의 설명을 구별하여 보관하며, 자료가 없다는 이유로 근무 사실이나 부재 사실을 추정하지 않는다. 재택근무는 근무일로 집계한다는 RM-02@v4의 규칙을 유지하고, 복지 내역에서 식대가 보이지 않는다는 사유를 근무일 기록이 없다는 근거로 사용하지 않는다. 정정이 필요한 항목을 찾으면 변경 전후 값과 그 근거를 남겨 다음 조회에서 같은 차이가 반복되는지 확인할 수 있게 한다.

문의가 여러 날짜에 걸쳐 있으면 각각의 날짜와 관련 요청을 나누어 정리한다. 일부 날짜의 오류만 확인된 경우에는 확인된 부분을 먼저 설명하고 나머지 날짜까지 같은 원인이라고 단정하지 않는다. 내부 확인이 끝나면 정정한 항목과 그대로인 항목, 아직 자료가 부족한 항목을 구분하여 안내한다. 이러한 기록 확인은 새로운 재택 허용 장소나 추가 가능 일수를 설정하는 절차가 아니며, 신청 범위가 달라지는 내용은 기존 신청과 구분해 확인한다.

## 제4장 복지 지원 내역의 확인 [WF]

### 제1절 지급 기준과 문의 구분 [WF-S1]

#### WF-01 식대 지원 기준

<!-- kind: preserved -->
사무실 출근일에는 식대 1만 원을 지원한다. 재택근무일과 휴가일에는 이 식대를 지원하지 않는다.

<!-- kind: added_fictional -->
식대 내역에 대한 문의는 해당 날짜의 근무 형태와 지급 표시를 연결해 확인한다. 지급 화면의 항목 이름만으로 사무실 출근 여부를 판단하지 않고, 날짜나 근무 형태가 불명확한 항목은 별도로 확인한다.

#### WF-02 생일 축하 포인트

<!-- kind: preserved -->
재직자에게 생일 축하 포인트 3만 점을 지급한다. 이 포인트는 휴가 신청 자격이나 승인 여부와 별개다.

<!-- kind: added_fictional -->
생일 포인트의 지급 내역을 휴가 승인 기록으로 사용하지 않는다. 휴가 승인 여부에 관한 문의는 BD-03@v4의 신청·승인 기록과 구분하여 확인하며, 포인트 확인 화면에 휴가 승인 상태를 함께 확정해 표시하지 않는다.

#### WF-03 문의 접수와 대상 내역의 식별

<!-- kind: added_fictional -->
복지 내역 문의를 받으면 담당자는 식대와 생일 축하 포인트 중 어느 항목에 관한 문의인지 먼저 구분한다. 문의자가 금액과 점수를 혼용하여 설명한 경우에는 지급 단위를 확인한 뒤 원래 내역과 대조한다. 문의 내용에는 확인하려는 날짜나 내역의 제목, 화면에 표시된 값, 문의자가 차이가 있다고 설명한 부분을 연결한다. 이미 확인 가능한 지급 기록을 찾을 수 있는데도 같은 화면을 다시 제출해야만 문의를 접수하는 방식으로 처리하지 않는다. 설명만으로 대상 항목을 특정하기 어려우면 어느 기간이나 어떤 표시를 확인하려는지 문의하고, 확인되지 않은 값을 임의로 채우지 않는다. 재택근무가 근무일로 집계된다는 RM-02@v4의 내용과 식대 지원 여부는 서로 다른 기준이므로, 근무일이라는 표시만으로 식대가 누락되었다고 판단하지 않는다. 대상 내역의 식별은 지급 기준의 변경이나 새 복지 항목의 등록과 구별해 처리한다.

### 제2절 대조와 정정의 진행 [WF-S2]

#### WF-04 지급 표시의 확인부터 정정 통지까지

<!-- kind: added_fictional -->
담당자는 문의 대상 내역을 찾은 뒤 그 항목의 지급 종류, 대상 날짜, 표시된 단위와 값을 대조한다. 조회 화면이 합계만 제공하는 경우에는 합계에 포함된 항목의 범위를 확인하고, 문의한 내역과 다른 기간의 내역이 섞여 있는지 살핀다. 생일 축하 포인트의 점수와 식대의 원화 금액은 같은 합계로 더하지 않으며, 둘을 함께 묻는 문의라도 확인 결과는 항목별로 구분한다. 확인한 자료가 어느 시점에 생성되었는지 기록하여 이후 값이 갱신되었을 때 이전 안내와 차이가 나는 이유를 확인할 수 있게 한다. 지급 내역과 근무 형태의 자료가 서로 다른 시점에 조회된 경우에는 그 차이를 먼저 기록하고, 가능한 범위에서 같은 기준 시점으로 대조한다. 담당자가 확인할 수 없는 원자료가 있으면 해당 항목을 미확인으로 남기며, 화면의 빈칸을 지급 없음이나 지원 대상 제외로 곧바로 해석하지 않는다. 문의자가 알린 내용은 원자료와 구별하여 보관하되 그 설명이 실제로 어떤 차이를 가리키는지 확인하는 데 사용한다.

내역의 오입력이나 잘못된 연결이 확인되면 담당자는 수정할 항목, 원래 값, 확인한 근거를 정리한다. 근무 형태 정보가 정정되어야 하는 경우와 지급 화면의 표시만 정정하면 되는 경우를 나누어 해당 기록에 연결한다. 원자료가 바로잡히기 전에 지급 내역만 임의로 바꾸어 두 자료가 우연히 같은 숫자가 되게 하지 않는다. 어떤 자료를 먼저 확인해야 하는지 내부 처리 순서를 정할 수는 있으나, 그 순서를 새로운 지급 자격이나 추가 서류 제출 의무로 사용하지 않는다. 여러 담당 업무가 관련되어 있으면 확인을 요청한 항목과 회신한 항목을 연결하여 누가 무엇을 확인했는지 알 수 있게 한다. 담당 업무에 전달했다는 사실은 정정 완료와 다르므로 접수, 확인 중, 반영 확인의 상태를 구분해 안내한다. 다른 날짜에 같은 이름의 지급 내역이 있더라도 문의한 항목과 동일한 오류인지 확인하지 않고 한꺼번에 수정하지 않는다. 정정 대상의 범위는 실제로 확인된 항목을 기준으로 정한다.

정정이 반영되면 담당자는 변경된 항목과 그 결과를 문의자가 식별할 수 있게 안내한다. 단순한 표시 정정인지, 잘못 연결된 원자료의 정정이 반영된 것인지, 아직 다른 부분을 확인하고 있는지를 구분한다. 확인 과정에서 지급 기준과 무관한 화면 오류가 발견되었으면 그 오류를 해결했다는 사실과 실제 지급 내역 확인 결과를 나누어 설명한다. 문의자가 정정 안내를 받은 뒤에도 화면에서 이전 값을 본다고 알리면 화면 갱신 시점과 실제 반영 상태를 다시 비교하고, 확인하지 않은 새로운 값을 재차 통지하지 않는다. 과거에 잘못 안내한 내용이 있으면 그 안내와 정정 안내의 연결을 남겨 이후 문의에서 어떤 정보를 기준으로 삼아야 하는지 알 수 있게 한다. 이 과정에서 이 규정집에 없는 지급일, 지급 수단, 포인트 환전 또는 세금 처리 기준을 임의로 추가하지 않는다. 내역 확인이 완료되었다는 사실은 해당 항목에 관한 기록 대조의 결과이며 다른 복지 문의의 내용까지 결정하는 것으로 표시하지 않는다.

#### WF-05 근무 형태 기록이 다른 경우

<!-- kind: added_fictional -->
식대 문의의 통상 대조 자료는 WF-01@v4의 날짜별 근무 형태와 지급 표시다. 다만 신청 화면과 집계 화면에서 같은 날짜의 근무 형태가 서로 다르면 어느 값이 먼저 등록되었고 어떤 정정이 진행 중인지 확인한 뒤 지급 내역과 연결한다. 담당자는 서로 다른 화면 중 지급액이 기대와 일치하는 화면만 골라 근거로 사용하지 않는다. 사무실 출근, 재택근무, 휴가의 구분이 바뀐 이유를 확인할 수 있으면 그 정정 근거를 남기고, 아직 확인할 수 없으면 어느 자료가 미확인인지 표시한다. 재택 신청이 승인되었다는 사실과 실제 근무 기록의 반영은 서로 구분하여 살피며, 신청 내역만으로 근무 사실을 임의 추정하지 않는다. 날짜가 잘못 연결된 경우에는 대상 날짜를 바로잡고 다른 날짜의 정상 내역이 영향을 받지 않았는지도 대조한다. 정정 요청이 있다는 이유만으로 식대 지원 범위를 확대하거나, 원자료 확인이 진행 중이라는 사실을 새로운 지급 제외 조건으로 만들지 않는다.

<!-- kind: explanatory -->
같은 날짜에 사무실 출근으로 표시된 조회본과 재택근무로 표시된 조회본이 있는 상황에서는 두 조회본의 생성 시각과 관련 정정 기록이 차이를 설명하는 단서가 된다. 이후 화면에서 값이 같아졌다는 사실만으로 최초 문의가 잘못되었다고 할 수는 없다. 반영 전 화면과 반영 후 화면은 서로 다른 시점의 상태를 담고 있을 수 있기 때문이다. 이 사례의 쟁점은 근무일인지 여부 하나가 아니라 어떤 근무 형태와 어느 시점의 내역을 비교했는지에 있다. 이 설명은 WF-04@v4의 대조 과정에 관한 예시이며 별도의 지급 예외를 두는 내용이 아니다.

#### WF-06 중복으로 보이는 지급 항목

<!-- kind: added_fictional -->
동일한 이름과 값의 항목이 여러 번 보인다는 문의에서는 항목의 이름뿐 아니라 대상 날짜, 종류, 관련 기록 번호를 비교한다. 서로 다른 기간의 내역이 같은 제목을 사용할 수 있으므로 제목만 같다는 이유로 중복 지급으로 처리하지 않는다. 실제로 하나의 항목이 화면에 두 번 표시된 것인지, 각각 다른 내역을 나타내는지, 정정 전후 이력이 동시에 보이는 것인지 구분한다. 정정 이력을 별도 항목으로 보여 주는 화면이라면 그 항목이 새로운 지급을 뜻하는지 이력 표시를 뜻하는지 확인하여 안내한다. 중복 표시가 확인되면 정상 내역과 중복 표시를 연결하고, 삭제·정정된 표시가 어느 내역에 관한 것인지 남긴다. 이 규정집에 없는 반환 의무나 제재를 중복 확인 절차에 덧붙이지 않으며, 확인되지 않은 상태에서 지급액을 임의로 회수한 것으로 기록하지 않는다. 같은 유형의 표시가 다른 직원의 내역에 보인다는 설명이 있더라도 현재 문의자의 기록과 섞지 않고 문의 대상 항목만 식별하여 처리한다.

#### WF-07 조회 장애 시 임시 문의 기록

<!-- kind: added_fictional -->
지급 내역 화면에 접속할 수 없어 WF-03@v4의 대상 정보를 직접 확인할 수 없는 경우에는 문의자가 기억하는 항목과 확인하려는 내용을 임시 문의로 남긴다. 이때 기억에 따른 설명과 실제 화면에서 확인한 값을 같은 확정 정보로 저장하지 않는다. 접속 장애로 내역이 보이지 않는다는 사실을 곧바로 미지급의 증거로 취급하지 않고, 화면이 복구되면 실제 내역과 대조할 항목을 정리한다. 복구 후 기존 문의 기록이 생성되어 있는지 먼저 확인하여 같은 문의를 중복 접수하지 않으며, 임시 기록과 정식 문의의 연결을 남긴다. 문의 중 생일 특별휴가 승인에 관한 질문이 함께 들어오면 포인트 내역의 조회 장애와 휴가 승인 여부를 분리해 안내한다. WF-02@v4의 포인트와 휴가의 구분은 화면 장애 상황에서도 유지된다. 담당자는 조회 장애를 이유로 새로운 지급 방법을 약속하거나 기존 포인트를 다른 종류의 금액으로 바꾸어 안내하지 않는다.

#### WF-08 안내 내용에 관한 이견과 인계

<!-- kind: added_fictional -->
문의자가 받은 설명과 현재 표시되는 내역이 다르다고 알리면 담당자는 어느 안내의 어떤 부분에 이견이 있는지 확인한다. 설명 문구, 대상 날짜, 단위, 확인한 자료의 시점을 각각 대조하여 단순한 표현 오류인지 실제 내역의 차이인지 구분한다. 문의자가 예상한 금액과 다르다는 사정만으로 지급 기준을 바꾸지 않으며, 담당자의 이전 설명이 잘못되었다면 그 부분을 명확히 바로잡는다. 안내를 정정하면서 문의자의 원래 설명을 삭제하거나 다른 의미로 요약하지 않는다. 담당 업무를 인계할 때에는 최초 문의의 대상, 확인된 자료, 아직 답을 받지 못한 항목을 함께 전달하고, 앞선 확인 결과 중 현재도 유효한 부분을 구분한다. 새 담당자는 과거 안내를 그대로 반복하기 전에 관련 기록을 확인하고, 미확인 사항을 완료로 바꾸지 않는다. 문의 종료 안내에는 확인을 마친 범위를 적어 다른 지급 항목이나 향후 기간까지 확인이 끝난 것으로 오인되지 않게 한다.

#### WF-09 여러 항목을 함께 확인하는 문의

<!-- kind: added_fictional -->
식대와 생일 축하 포인트를 하나의 문의에서 함께 확인하려는 경우에는 문의 자체를 나눠 다시 제출하게 하기보다 내부 확인 항목을 분리하여 연결한다. 문의자가 적은 총액이 여러 종류의 단위를 섞은 값이면 그 총액을 지급 원장의 값으로 옮기지 않고 각 항목의 원래 단위를 확인한다. 날짜가 같은 내역끼리 묶었을 때와 지급 종류별로 묶었을 때의 표시 범위가 다를 수 있으므로, 어떤 기준으로 정리한 자료인지 안내에 남긴다. 담당자가 다른 업무로 확인을 요청할 때에는 필요한 항목만 특정하고, 문의 전체가 새 지급 요청으로 전달되지 않도록 목적을 표시한다. 한 항목의 대조가 끝나고 다른 항목은 아직 확인 중이면 각각의 진행 상태를 구분해 통지한다. 먼저 확인된 내역의 결과를 나머지 항목의 결과로 복사하지 않으며, 보완 안내에는 이미 확인한 정보를 다시 요구하지 않도록 한다. WF-04@v4의 정정 통지를 작성할 때에는 항목별 확인 결과를 원래 문의에 모아 연결하고, 문의자가 어느 항목에 대해 추가 질문하는지 식별할 수 있게 한다.

<!-- kind: explanatory -->
포인트 화면에 표시된 점수와 식대 화면에 표시된 원화 금액이 동시에 문의된 사례에서는 두 화면의 수치가 같거나 다르다는 사실 자체가 오류를 뜻하지 않는다. 각 항목은 지급 대상과 단위가 다르며 조회 시점도 다를 수 있다. 하나의 문의 번호로 접수되었더라도 확인 결과가 항목별로 나뉘는 이유가 여기에 있다. 이 사례는 서로 다른 지급 내역을 대조할 때 필요한 구분을 설명하며 새 지원 항목이나 환산 비율을 제시하지 않는다.

## 제5장 교육휴가의 신청과 변경 [ED]

### 제1절 대상과 신청 정보 [ED-S1]

#### ED-01 신청 대상과 일수

<!-- kind: preserved -->
직무 관련 자격시험 응시자는 연 1일 교육 휴가를 신청할 수 있다.

신청 정보에는 어떤 자격시험 응시를 위한 요청인지 식별할 수 있는 설명을 연결한다. 이미 전달된 설명으로 대상을 확인할 수 있으면 같은 내용을 반복 제출하도록 요구하지 않고, 시험 이름이 비슷해 구별이 필요한 부분만 확인한다.

#### ED-02 다른 휴가와의 관리 구분

<!-- kind: preserved -->

<!-- kind: added_fictional -->
교육휴가 내역을 연차 차감 기록이나 생일 특별휴가 기록으로 자동 전환하지 않는다. 다른 제도에 관한 문의가 함께 들어오면 해당 휴가 종류를 구분하고, 연차 사용 단위는 AN-03@v4에서 확인하되 그 규칙을 교육휴가의 분할 기준으로 적용하지 않는다.

#### ED-03 시험 일정과 사용 희망일의 표시

<!-- kind: added_fictional -->
교육휴가 신청에는 시험을 식별할 수 있는 정보와 사용 희망일, 해당 신청을 구분하는 기록을 연결한다. 시험의 이름과 일정이 함께 적혀 있으면 원래 작성된 내용 그대로 확인하고, 신청자가 설명한 일정과 시스템 선택 날짜가 다를 때에는 어느 값이 희망일인지 문의한다. 여러 시험 일정이 같은 설명에 적혀 있으면 각각을 별도 휴가 신청으로 계산하지 않고 문의인지 실제 신청인지 먼저 구분한다. 응시하려는 시험이 변경되었다는 설명과 시험 명칭의 오입력을 바로잡는 설명은 다른 변경 사유로 남긴다. 신청자가 자발적으로 전달한 안내 자료가 있으면 어떤 내용을 확인하는 데 사용했는지 연결하되, 이 규정집에서 정하지 않은 추가 증빙을 제출하지 않았다는 이유로 새로운 자격 제한을 만들지 않는다. 담당자는 시험 접수 번호나 개인 결과처럼 휴가 내역 확인과 직접 관계가 없는 정보가 과도하게 반복 입력되지 않도록 확인 항목을 구체적으로 안내한다. 이 절차에서 시험 비용이나 응시료의 지원 여부를 추정하여 함께 등록하지 않는다.

### 제2절 접수와 처리 결과의 확인 [ED-S2]

#### ED-04 신청 내용을 검토하고 안내하는 절차

<!-- kind: added_fictional -->
교육휴가 신청을 접수한 담당자는 ED-01@v4의 대상에 관한 설명과 사용 희망일을 확인하고 원래 제출 기록을 찾을 수 있도록 연결한다. 설명이 짧거나 시스템의 선택 항목만으로 의미를 알기 어려우면 어느 시험 응시를 위한 요청인지 확인하되, 담당자가 시험 자격이나 합격 가능성을 별도로 평가하는 절차로 넓히지 않는다. 직무 관련 여부에 관한 설명이 기록에서 누락되었으면 확인 중인 항목으로 표시하고, 확인하지 못한 사실을 임의로 충족 또는 미충족으로 입력하지 않는다. 신청자가 앞선 문의에서 이미 설명한 내용을 찾을 수 있으면 그 문의를 현재 요청과 연결하여 반복 질문을 줄인다. 같은 이름의 시험에 관한 과거 기록이 있어도 현재 신청의 날짜나 내용을 자동으로 복사하지 않고 이번 요청을 기준으로 확인한다. 시스템에 다른 휴가 종류가 잘못 선택되어 있으면 신청자의 의도를 확인한 뒤 종류의 정정과 원래 기록을 연결하며, 단순한 선택 오류를 휴가를 추가 사용한 사실로 처리하지 않는다.

내용 확인이 진행되는 동안에는 접수된 사실, 정보 확인 중인 항목, 기록 반영이 끝난 항목을 구분한다. 담당 업무 사이에서 자료를 전달할 때에는 어떤 부분의 확인을 요청하는지 명확히 표시하고, 전달 자체가 신청 내용의 승인이나 거절을 뜻하는 것처럼 안내하지 않는다. 이 규정집에 명시되지 않은 승인권자를 새로 지정하거나 추가 내부 결재를 신청 자격의 조건으로 요구하지 않는다. 별도 승인 정보가 문의에 포함되어 있는 경우에는 그 정보가 어떤 요청에 관한 것인지 확인 가능한 범위에서 연결하고, 확인되지 않은 승인 상태는 그대로 미확인으로 표시한다. 신청자가 희망일을 정정하면 기존 확인 자료와 새 요청의 관계를 남겨 현재 어떤 날짜를 대상으로 확인하고 있는지 알 수 있게 한다. 검토 중에 담당자가 변경되더라도 신청을 처음부터 다시 접수한 것으로 처리하지 않고, 확인이 끝난 내용과 남아 있는 질문을 함께 인계한다. 다른 종류의 휴가 기록과 혼동될 수 있는 항목은 ED-02@v4의 관리 구분에 따라 식별한다.

정보 확인과 기록 반영이 끝나면 신청자에게 처리한 범위를 안내한다. 안내에는 대상 시험을 식별할 수 있는 설명, 사용 희망일에 대한 현재 기록, 추가로 확인 중인 사항이 있는지를 구분하여 적는다. 접수 확인만 이루어진 상황에서 사용이 확정되었다는 표현을 사용하지 않고, 단순히 화면의 오류를 수정한 경우에는 수정한 항목을 설명한다. 신청자가 통지 내용이 원래 신청과 다르다고 알리면 최초 제출본, 정정 이력, 현재 표시값을 대조하여 어떤 단계에서 차이가 생겼는지 확인한다. 오류가 확인되면 원래 안내와 정정 안내를 연결하고, 이미 확인한 내용까지 새로 제출해야 하는 것처럼 요청하지 않는다. 문의가 여러 시험이나 여러 날짜를 포함했다면 확인을 마친 대상과 나머지 대상을 구분하여 남긴다. 담당자가 작성한 안내는 그 시점에 확인한 기록을 설명하는 것이며, 시험 합격 여부나 비용 지원 여부처럼 이 장에서 정하지 않은 내용을 함께 확정하는 자료로 사용하지 않는다.

#### ED-05 시험 일정 변경과 신청 정정

<!-- kind: added_fictional -->
시험 일정이 변경되었다는 연락을 받으면 담당자는 변경 전 일정, 새로 전달된 일정, 신청자가 실제로 바꾸려는 사용 희망일을 서로 연결한다. 시험 일정이 바뀌었다는 사실만으로 휴가 신청 날짜도 자동으로 같은 방식으로 바꾸지 않고 신청자의 현재 의사를 확인한다. 일정 안내의 오입력인지 시험 주관 측 일정의 변경인지 신청자의 응시 계획 변경인지 확인 가능한 범위에서 사유를 구분하되, 그 구분을 새로운 자격 심사 항목으로 만들지 않는다. 같은 시험의 여러 회차가 함께 표시되어 있으면 어느 회차와 연결된 요청인지 확인하고 다른 회차의 날짜를 잘못 참조하지 않도록 한다. 원래 요청이 아직 정보 확인 단계이면 기존 요청에 정정 내용을 연결하고, 이미 안내가 전달된 상태이면 안내 내용과 변경 요청을 함께 확인하여 현재 처리 대상을 분명히 한다. 통상적으로는 시스템의 기존 신청을 찾아 변경 관계를 남기지만 해당 기록이 조회되지 않는 경우에는 신청자를 다시 접수시키기 전에 확인 가능한 기록 번호나 전달 내용을 이용해 원래 요청을 찾는다.

<!-- kind: explanatory -->
시험 안내 화면에는 정정된 일정이 나타나고 휴가 신청 화면에는 이전 날짜가 남아 있는 사례가 있을 수 있다. 이때 두 화면의 날짜 차이는 곧바로 두 건의 휴가 신청이 있다는 뜻이 아니다. 한 화면의 안내가 먼저 바뀌고 신청자의 실제 날짜 변경 의사는 아직 확인되지 않은 상태일 수도 있다. 시험 정보의 변경과 휴가 신청의 변경을 구별하면 원래 신청을 유지하면서도 새 문의의 이유를 설명할 수 있다. 이 사례는 ED-03@v4의 정보 구분을 설명하는 것으로, 시험 일정 변경 시 추가 휴가를 부여하거나 기존 사용량을 자동 복구한다는 별도 규칙을 뜻하지 않는다.

#### ED-06 응시 계획 취소와 요청 상태의 정리

<!-- kind: added_fictional -->
응시 계획을 취소했다는 연락을 받으면 담당자는 취소하려는 교육휴가 요청을 먼저 식별한다. 시험 접수만 취소한 것인지 휴가 신청도 취소하려는 것인지 구분하고, 신청자가 아직 결정하지 못한 문의를 확정된 취소로 기록하지 않는다. 확인된 취소 의사는 원래 신청과 연결하여 남기며, 다른 시험에 관한 요청이나 이미 별도로 관리되는 휴가 기록까지 일괄 삭제하지 않는다. 신청 날짜를 잘못 선택하여 다시 입력하려는 경우에는 날짜 정정으로 처리할 수 있는지 ED-05@v4의 변경 관계를 확인한다. 취소 후 새로운 신청이 접수되면 두 요청의 관계를 식별하되, 새로운 요청의 시험과 날짜는 실제 입력된 내용으로 확인한다. 취소 통지에는 정리한 대상과 현재 기록 상태를 적고, 사용량의 표시가 아직 이전 값이면 그 차이를 확인 중인 항목으로 구분한다. 취소 의사를 접수했다는 사실만으로 잔여 일수가 복구되었다고 안내하지 않으며, 반영된 기록을 확인한 후 그 결과를 설명한다. 신청자가 취소 요청을 철회하면 이전 요청을 조용히 되살리지 않고 철회 의사와 현재 처리 상태를 대조한다. 이미 완료된 정리와 아직 진행 중인 정리를 구분하여 후속 담당자에게 넘기고, 정정 이력을 남겨 같은 취소가 반복 반영되지 않게 한다.

#### ED-07 신청 화면 장애와 복구 후 연결

<!-- kind: added_fictional -->
신청 화면을 사용할 수 없거나 제출 후 접수 여부가 표시되지 않는 경우에는 ED-04@v4의 통상 접수 기록을 즉시 확인하기 어려울 수 있다. 이때 담당자는 신청자가 전달한 희망일, 시험을 식별하는 설명, 전달 시점을 임시 기록하고 시스템 확인이 필요한 항목을 구분한다. 장애가 있었다는 설명을 확인되지 않은 승인 사실로 바꾸지 않으며, 임시 기록의 목적이 신청 내용의 유실을 막기 위한 것임을 안내한다. 화면이 복구되면 기존 접수 기록이 생성되었는지 먼저 조회하고, 같은 내용이 이미 있으면 임시 기록을 그 요청에 연결한다. 별도의 접수 기록이 없는 경우에는 전달받은 내용을 확인하여 시스템 반영 기록과 연결하고, 실제 전달 시점과 복구 후 입력 시점을 각각 남긴다. 장애 기간에 신청자가 내용을 수정한 경우에는 가장 최근의 의사를 확인하여 이전 임시 기록이 최종 요청으로 잘못 반영되지 않게 한다. 복구 안내에서는 어떤 요청을 찾아 연결했는지와 아직 확인되지 않은 사항을 구분한다. 장애 해소 여부와 휴가 요청의 처리 완료 여부는 별도로 확인하며, 화면이 다시 열린 사실만으로 요청 처리가 끝났다고 안내하지 않는다. 임시 기록과 시스템 기록의 식별 정보가 달라 연결할 수 없으면 확인 중인 상태를 유지하고 신청자에게 차이가 있는 항목만 문의한다.

#### ED-08 자발적으로 전달된 결과 정보의 관리

<!-- kind: added_fictional -->
신청자가 시험 응시 후 결과나 후기를 자발적으로 전달하면 담당자는 해당 내용이 어떤 교육휴가 기록과 관련되는지 확인한다. 결과 자료를 받았다는 사실과 휴가 사용 기록의 확인을 구분하고, 합격 여부를 기존 신청 자격의 새로운 조건으로 추가하지 않는다. 결과 자료에 새로운 시험 일정이나 다음 회차에 관한 설명이 포함되어 있어도 이를 다음 교육휴가의 신청으로 자동 등록하지 않는다. 신청자가 실제 사용 날짜의 오입력을 함께 알리면 그 항목을 별도 정정 요청으로 식별하고 원래 기록과 대조한다. 자료의 일부가 읽히지 않더라도 휴가 기록 확인에 필요하지 않은 내용까지 다시 제출하도록 요구하지 않으며, 확인 가능한 범위와 미확인 범위를 내부 기록에 구분한다. 담당자가 결과 안내를 작성할 때에는 자료 수신 여부와 기록 정정 여부를 각각 표시한다. 다른 업무로 자료를 전달할 필요가 있는 경우에도 어떤 사실을 확인하려는 것인지 특정하고, 교육휴가의 이용 기록이 시험 성적 평가 자료로 잘못 분류되지 않도록 한다. 신청자가 결과 자료의 연결 대상을 정정하면 기존 연결 관계와 정정 사유를 기록하되 원래 휴가의 종류를 바꾸지 않는다.

#### ED-09 복합 문의의 답변과 담당 업무 인계

<!-- kind: added_fictional -->
교육휴가 신청과 시험 비용, 근무 일정, 다른 휴가 사용을 함께 묻는 문의에서는 먼저 이 장에서 확인할 수 있는 항목을 구분한다. 교육휴가에 관한 기록은 ED-01@v4과 ED-02@v4의 기준에 연결하고, 규정집에 답이 없는 비용 지원이나 별도의 시험 제도는 확인되지 않은 사항으로 남긴다. 담당자가 알고 있는 다른 사례만으로 이번 문의의 지원 여부를 확정하지 않는다. 여러 항목 중 일부 확인이 끝나면 완료된 항목을 안내하면서 남은 항목의 상태를 함께 적고, 전체 문의가 종결된 것으로 오해할 표현을 피한다. 담당 업무가 바뀔 때에는 최초 질문, 확인에 사용한 기록, 이미 전달한 답변, 남은 질문을 연결한다. 새 담당자는 같은 질문을 반복하기 전에 인계 내용을 확인하고 서로 다른 날짜의 안내가 있으면 적용 대상을 대조한다. 문의자가 안내의 누락을 지적하면 원래 질문과 답변의 항목을 맞춰 빠진 부분을 확인한다. 답변을 보완할 때에는 기존 설명 중 바뀌는 부분을 표시하고, 단순한 보충 설명을 새로운 신청이나 승인으로 등록하지 않는다.

## 제6장 출장의 승인과 일정 관리 [TR]

### 제1절 출장 요청의 기본 사항 [TR-S1]

#### TR-01 승인 기한과 승인 주체

<!-- kind: preserved -->
출장은 출발 5영업일 전에 팀장의 승인을 받는다.

<!-- kind: added_fictional -->
신청 기록에는 출발 예정일과 해당 요청을 식별할 수 있는 정보를 연결한다. 제출 시점과 승인 시점을 서로 다른 기록으로 관리하며, 접수 확인 안내가 승인 안내를 대신하지 않도록 표시한다. 일정 설명과 선택 날짜가 다르면 신청자가 요청한 날짜를 확인한다.

#### TR-02 다른 제도의 승인과 구분

<!-- kind: preserved -->
출장 승인으로 휴가나 재택근무가 자동 승인되지는 않는다.

<!-- kind: added_fictional -->
출장 일정에 다른 근무 형태나 휴가에 관한 문의가 포함되면 해당 종류를 구분한다. 재택근무는 RM-02@v4의 기준을 확인하고, 출장 승인 기록의 제목이나 날짜만으로 별도의 재택근무 승인 상태를 입력하지 않는다.

#### TR-03 목적과 일정 정보의 작성

<!-- kind: added_fictional -->
출장 신청의 설명에는 업무 목적, 방문할 장소, 출발과 복귀의 예정 일정이 서로 대응하도록 적는다. 신청자가 이미 전달한 업무 설명으로 목적을 식별할 수 있으면 해당 기록을 연결하고 같은 내용을 형식만 바꾸어 다시 제출하게 하지 않는다. 방문지가 여러 곳이면 이동 순서와 각 장소에 관한 일정을 구분하여 다른 장소의 날짜를 잘못 적용하지 않도록 한다. 확정된 일정과 아직 협의 중인 일정이 함께 들어 있으면 각각의 상태를 표시하며, 담당자가 임의의 날짜를 넣어 확정된 것처럼 보이게 하지 않는다. 예약 화면이나 일정표가 자발적으로 첨부된 경우에는 신청 설명과 일치하는 부분을 확인하고, 첨부 자료가 있다는 사실만으로 출장 승인까지 완료된 것으로 처리하지 않는다. 신청 내용의 확인에 직접 필요하지 않은 개인 일정은 업무 목적과 섞어 기록하지 않도록 안내한다. 같은 방문 목적을 가진 과거 출장 기록을 참고하더라도 이번 방문지와 날짜를 새로 대조하고 과거 승인을 현재 신청의 승인으로 복사하지 않는다. 작성 중인 내용에 대한 문의와 실제 신청 제출은 구분하여 남기며, 문의가 접수되었다는 사실을 신청 완료로 안내하지 않는다. TR-01@v4의 승인 기한을 확인할 때에는 실제로 제출된 요청의 출발 예정일과 제출 기록을 연결한다.

### 제2절 검토와 승인 내용의 전달 [TR-S2]

#### TR-04 접수부터 승인 통지까지의 연결 절차

<!-- kind: added_fictional -->
출장 신청을 접수한 담당자는 제출된 목적과 일정이 같은 요청을 설명하는지 확인하고 원래 제출 기록을 보존한다. 출발일이나 방문지가 여러 곳에 다르게 적혀 있으면 어떤 항목을 확인해야 하는지 특정하여 신청자에게 문의한다. 담당자가 내용의 차이를 발견했다는 사실만으로 요청을 취소하거나 새 신청으로 바꾸지 않으며, 신청자가 정정한 내용과 최초 제출본의 관계를 남긴다. 이미 전달받은 일정표에서 확인할 수 있는 정보는 그 자료를 연결하고 반복 입력을 요구하지 않는다. 팀장 검토에 전달할 때에는 현재 신청 내용과 아직 확인 중인 항목을 구분하여 잘못된 정보가 확정값으로 전달되지 않도록 한다. 담당자가 처리 편의를 위해 작성한 요약은 원래 신청을 대신하는 새로운 정책 자료로 사용하지 않고, 요약과 원문이 다르면 원래 기록과 신청자의 설명을 대조한다. 접수된 시점, 내용이 정정된 시점, 검토를 위해 전달된 시점은 서로 구분하여 기록하며 TR-01@v4의 승인 기한과 승인 주체를 유지한다.

팀장의 검토 결과를 받으면 어떤 신청과 어떤 일정에 대한 결과인지 확인한다. 승인 또는 추가 확인 요청이 여러 날짜의 신청과 함께 전달된 경우에는 각 결과의 적용 대상을 식별하고 다른 출장에 같은 결과를 복사하지 않는다. 승인 내용에서 확인되지 않은 방문지나 날짜는 자동으로 승인 범위에 포함하지 않으며, 승인 기록과 현재 신청 내용이 다르면 그 차이를 확인 중인 사항으로 남긴다. 추가 확인이 필요한 경우에는 이미 확인한 내용과 아직 필요한 설명을 구분하여 안내하고, 원래 요청이 유실되지 않도록 보완 내용과 연결한다. 신청자가 검토 중에 일정을 변경하면 변경 전후를 함께 전달하여 어느 버전을 대상으로 검토하는지 분명히 한다. 내용 확인 담당자가 바뀌어도 팀장 승인 주체를 임의로 바꾸지 않으며, 업무 인계는 승인 권한의 이전으로 표시하지 않는다. 일정표에 연차나 재택근무 문의가 포함되어 있으면 TR-02@v4에 따라 별도 항목으로 구분하고, 출장 승인 결과를 그 항목들의 결과로 전파하지 않는다.

처리 결과를 신청자에게 안내할 때에는 요청을 식별할 수 있는 정보, 확인된 출장 일정, 승인 기록과의 관계, 남아 있는 확인 사항을 함께 적는다. 접수 확인이나 자료 보완 안내만 이루어진 경우에는 승인 완료라는 표현을 사용하지 않는다. 통지 내용의 날짜가 신청 내용과 다르다는 연락을 받으면 최초 제출본과 정정 이력, 팀장 검토 결과를 순서대로 대조하여 차이가 생긴 지점을 확인한다. 단순한 안내 오입력은 수정한 내용을 명시해 다시 안내하고, 실제 신청 일정이 바뀐 경우에는 변경 요청과 기존 승인 내용의 관계를 확인한다. 통지 수신 여부가 확인되지 않을 때에는 이미 보낸 안내 기록을 찾아 재전달 여부를 기록하되, 같은 승인 결과를 여러 번 별도 승인으로 계산하지 않는다. 신청자가 답변 일부에만 이견을 제시하면 그 항목을 특정하여 확인하고 다른 항목의 처리 상태까지 임의로 되돌리지 않는다. 최종 안내에는 확인을 마친 범위를 적어 비용이나 다른 제도까지 모두 승인되었다고 오해하지 않도록 한다.

#### TR-05 방문 순서와 세부 일정의 변경

<!-- kind: added_fictional -->
신청 후 방문 순서나 이동 일정이 달라지면 담당자는 신청자가 변경하려는 항목을 기존 일정과 대응시킨다. 방문지 표기의 오입력을 바로잡는 것인지 실제 방문 장소를 바꾸는 것인지 구분하고, 변경 전후의 날짜와 장소를 같은 기록에서 확인할 수 있게 한다. 일정표 파일이 새로 전달되었다는 이유만으로 그 안의 모든 항목을 변경 요청으로 간주하지 않으며, 신청자가 바꾸려는 부분을 확인한다. 여러 방문지 중 일부만 변경하려는 경우에는 나머지 일정을 유지하는지 확인하여 전체 출장 취소나 새 신청으로 잘못 처리하지 않는다. 변경된 설명이 아직 협의 중이면 잠정 문의로 표시하고 확정된 신청 내용에 바로 덮어쓰지 않는다. 기존 신청이 TR-04@v4의 검토 단계에 있으면 정정된 내용을 해당 요청과 연결하여 전달하고, 이미 승인 결과가 있는 경우에는 변경된 부분과 승인 기록의 관계를 별도로 확인한다. 담당자는 일정 변경을 안내받았다는 사실만으로 새 날짜가 승인되었다고 표시하지 않는다.

여러 사람이 서로 다른 일정표를 전달한 경우에는 파일을 받은 순서만으로 최종본을 결정하지 않고 신청자의 현재 요청과 각 자료의 작성 시점을 대조한다. 동일한 파일 이름을 사용하더라도 내용이 다른 경우에는 변경된 항목을 구분하여 기록한다. 신청자가 이전 일정으로 돌아가겠다고 알리면 과거 파일을 조용히 복원하지 않고 현재 요청의 변경 이력을 남긴다. 일정 정리가 끝난 뒤에는 실제로 반영한 항목과 확인 중인 항목을 나누어 통지하고, 변경과 무관한 비용 내역이나 휴가 상태를 함께 바꾸지 않는다.

#### TR-06 승인 범위와 문의 답변의 대조

<!-- kind: added_fictional -->
승인 기록을 조회하거나 사본을 전달할 때에는 해당 기록이 어느 신청에 관한 것인지 확인한다. 출장 제목이 같아도 날짜와 방문지가 다른 요청일 수 있으므로 제목만으로 승인 범위를 판단하지 않는다. 신청자가 전달받은 승인 안내와 시스템 표시가 다르다고 알리면 원래 결과 기록, 안내 문구, 현재 표시를 대조하고 어떤 항목에서 차이가 있는지 구분한다. 안내 문구의 오입력이라면 수정한 범위를 설명하고 원래 승인 내용이 바뀐 것으로 기록하지 않는다. 반대로 신청자가 실제로 일정을 변경한 경우에는 TR-05@v4의 변경 관계를 확인하여 기존 승인 기록만으로 변경된 일정까지 확정하지 않는다. 승인 기록에 명시되지 않은 항목을 질문받으면 확인되지 않은 범위라고 안내하고 담당자의 추정으로 채워 넣지 않는다. 검토 결과의 일부가 누락되어 조회되지 않는 경우에는 미확인 상태로 남겨 자료를 찾으며, 표시 오류를 승인 거절이나 승인 완료로 바꾸지 않는다.

승인 내용을 다른 업무에 전달할 때에는 전달 목적과 확인이 필요한 항목을 적는다. 출장 일정이 연차 기록과 같은 날짜를 포함하더라도 두 기록의 관계는 TR-02@v4의 구분에 따라 확인하며, 일정의 중복만으로 한쪽을 삭제하지 않는다. 신청자가 한 번에 여러 요청의 상태를 문의하면 각 요청별로 확인한 결과를 정리한다. 일부 요청의 승인 사실을 나머지 요청의 결과로 일반화하지 않고, 확인되지 않은 요청은 따로 표시하여 후속 확인 대상이 남아 있음을 알린다.

### 제3절 예외 접수와 출장 이후의 기록 [TR-S3]

#### TR-07 신청 시스템 장애 시의 임시 기록

<!-- kind: added_fictional -->
신청 시스템이 열리지 않거나 제출 직후 오류가 발생하여 접수 여부를 알 수 없는 경우에는 TR-04@v4의 통상 기록을 바로 확인하기 어려울 수 있다. 이때 담당자는 전달받은 출장 목적, 출발 예정일, 전달 시점과 접수 확인이 필요한 사유를 임시 기록한다. 임시 기록은 신청 내용을 보존하기 위한 것이며 TR-01@v4의 승인 기한이나 팀장 승인 조건을 없애는 예외로 안내하지 않는다. 신청자가 오류 화면이나 메시지를 자발적으로 전달하면 해당 설명을 연결하되, 화면 자료가 없다는 이유로 새로운 증빙 의무를 만들지 않는다. 복구 후에는 시스템에 이미 생성된 요청이 있는지 먼저 조회하고, 같은 요청이 확인되면 임시 기록을 연결하여 중복 신청을 만들지 않는다. 시스템에 기록이 없다면 전달받은 내용과 현재 신청자의 의사를 확인하여 반영하며 실제 전달 시점과 시스템 입력 시점을 구분한다. 장애 기간에 일정이 수정되었다면 이전 임시 기록이 현재 요청으로 잘못 반영되지 않도록 변경 이력을 함께 확인한다.

복구 과정에서 승인 안내가 먼저 도착하고 신청 화면은 아직 조회되지 않는 경우에는 승인 안내의 대상과 임시 기록의 관계를 확인한다. 확인되지 않은 관계를 임의로 연결하지 않으며, 신청 기록의 복구와 승인 상태의 확인을 각각 진행 상태로 남긴다. 복구 안내에는 연결한 신청, 중복 여부를 확인한 결과, 아직 대조하지 못한 항목을 적어 시스템 복구 자체가 출장 처리 완료로 오인되지 않게 한다.

#### TR-08 전체 취소와 일부 일정 취소의 구분

<!-- kind: added_fictional -->
출장을 취소하려는 연락을 받으면 담당자는 전체 요청을 취소하려는 것인지 여러 방문 일정 중 일부만 제외하려는 것인지 확인한다. 문의자가 취소 가능 여부만 묻는 단계에서는 실제 취소 의사가 확정된 것으로 처리하지 않는다. 확인된 의사는 기존 신청과 연결하고, 일정 일부가 남는 경우에는 남아 있는 날짜와 장소를 식별하여 전체 요청이 사라지지 않게 한다. 이미 승인된 요청이라면 원래 승인 기록과 취소 요청의 관계를 남기고, 취소 통지를 전달할 때에는 정리한 대상과 현재 상태를 구분한다. 신청자가 취소 요청을 철회하면 취소 처리 전후의 기록을 대조하여 무엇을 유지하거나 다시 확인해야 하는지 파악한다. 예약 취소나 비용 환급에 관한 문의가 함께 들어오더라도 출장 기록의 취소와 같은 결과로 자동 처리하지 않으며, 실제로 확인된 자료가 무엇인지 별도로 기록한다. 취소 후 같은 이름의 새 출장이 신청되면 이전 취소 건의 상태를 복사하지 않고 새 요청을 식별한다. 일부 일정 취소가 날짜 변경으로도 해석될 수 있으면 TR-05@v4의 변경 절차와 대조하여 신청자가 원하는 처리를 확인한다. 담당자는 취소 이유를 요약하면서 원래 설명을 다른 의미로 바꾸지 않으며, 처리 결과의 안내가 원래 요청과 맞는지 확인한다.

#### TR-09 비용 관련 자료를 접수하고 구분하는 절차

<!-- kind: added_fictional -->
출장과 관련하여 비용 자료가 전달되면 담당자는 어떤 출장 요청에 연결되는 자료인지 먼저 확인한다. 자료에 표시된 이용 날짜, 항목, 원래 단위를 구분하여 기록하고, 일정표의 날짜와 다르다는 사실만으로 잘못된 비용이라고 단정하지 않는다. 예약과 실제 이용의 시점이 다를 수 있으므로 어떤 사실을 확인하기 위한 자료인지 설명을 연결한다. 여러 출장의 자료가 하나의 파일에 섞여 있으면 각 항목의 대상을 구분하고, 확인되지 않은 항목을 임의의 출장에 배분하지 않는다. 같은 자료가 여러 경로로 전달되면 중복 수신 여부를 표시하여 같은 항목을 별개의 내역으로 반복 등록하지 않도록 한다. 비용 자료의 수신 사실은 비용 지급이나 정산 승인을 뜻하지 않으며, TR-04@v4의 출장 승인 통지와도 구분한다. 이 규정집에 없는 지급 한도, 환율, 지원 대상, 비용 승인권자를 담당자가 새로 정하여 안내하지 않는다.

자료를 확인하는 중 금액이나 날짜의 판독이 어려운 항목이 있으면 어떤 부분을 확인할 수 없는지 구체적으로 안내한다. 이미 읽을 수 있는 항목까지 모두 다시 제출하도록 요청하지 않고, 신청자가 설명한 내용과 자료에서 직접 확인한 내용을 구분해 남긴다. 수정된 자료를 받으면 이전 자료와의 관계를 연결하여 어느 값이 현재 확인 대상인지 식별한다. 단순한 파일 재전송을 새로운 비용 발생으로 계산하지 않으며, 여러 통화나 포인트 단위가 섞여 있으면 임의로 합산하거나 환산하지 않는다. 자료 확인 결과를 전달할 때에는 수신 완료, 내용 대조 중, 정정 반영처럼 실제 처리한 상태를 설명하고, 비용의 지급 가능 여부를 확인하지 않았다면 그 사실을 명시한다.

#### TR-10 대상이 불분명한 비용 자료의 보완

<!-- kind: added_fictional -->
출장을 식별할 수 없는 비용 자료가 먼저 도착한 경우에는 TR-09@v4의 통상 연결을 바로 완료하지 않고 확인 대기 항목으로 남긴다. 담당자는 자료에 이미 표시된 날짜와 항목을 확인한 후 필요한 연결 정보만 문의한다. 유사한 날짜에 등록된 다른 출장과 자동으로 연결하거나 자료 발신자의 이름만으로 대상 요청을 결정하지 않는다. 신청자가 기존 요청 번호를 잘못 알려 준 경우에는 번호의 정정과 자료의 내용을 구분하여 기록하고, 잘못 연결되었던 내역이 있다면 정정 전후의 대상을 함께 남긴다. 자료에 여러 건이 포함되어 일부만 연결할 수 있으면 확인된 부분과 남은 부분을 나누어 안내한다. 나중에 같은 자료가 다른 설명과 함께 전달되면 새 비용으로 추가하기 전에 기존 수신 기록을 찾아 설명이 보완된 것인지 확인한다. 보완 과정에서 자료가 누락되거나 파일이 열리지 않으면 그 상태를 기록하되, 실제 비용이 발생하지 않았다는 결론으로 바꾸지 않는다. 이 절차는 자료를 올바른 요청에 연결하기 위한 것으로, 자료가 불완전하다는 사실만으로 이 규정집에 없는 지급 제외 기준을 만들지 않는다. 연결이 완료되면 어떤 신청과 어떤 항목을 대응시켰는지 통지하고 추가 확인 사항을 구분한다.

#### TR-11 실제 일정과 사후 문의의 기록

<!-- kind: added_fictional -->
출장 이후 실제 방문 일정이 신청 당시 기록과 달랐다는 설명을 받으면 담당자는 예정 일정과 실제로 확인된 일정을 각각 남긴다. 사후 설명을 받았다는 이유만으로 과거 승인 기록의 날짜를 조용히 바꾸지 않고, 어떤 차이가 있었는지와 현재 확인하려는 목적을 연결한다. 방문지 일부를 가지 못했거나 이동 순서가 바뀌었다는 설명이 있으면 해당 부분을 특정하고 나머지 일정까지 변경된 것으로 처리하지 않는다. 기록 정정이 필요한 문의인지 비용 자료의 연결을 확인하려는 문의인지 먼저 구분하여 관련 기록을 찾는다. 실제 일정에 관한 설명과 비용 자료의 날짜가 다르면 TR-09@v4에 따라 각 자료가 나타내는 시점을 확인하고 단순한 날짜 차이만으로 결론을 내리지 않는다. 담당 업무를 인계할 때에는 최초 신청, 승인 기록, 변경·취소 이력, 사후 설명 중 현재 질문에 필요한 항목을 연결한다. 이미 확인한 사실과 아직 확인하지 못한 설명을 구분하여 새 담당자가 원래 문의를 다시 구성하지 않아도 되도록 한다. 문의 종료 안내에는 어느 일정과 기록을 대조했는지 적고, 확인하지 않은 비용 지급이나 다른 휴가 상태까지 모두 정리되었다고 표현하지 않는다.

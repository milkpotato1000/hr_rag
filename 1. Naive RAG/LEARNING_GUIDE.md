# Naive RAG를 배우는 순서

구현·설치·테스트·수정은 Codex가 맡고, 사용자는 **예상 → 관찰 → 실패 위치 분류 → 한 변수 실험 → 해석**에 집중한다.
기존 화면은 수작성 15개 청크를 사용한다. P006에서 새로 작성한 원문 6개와 자동 생성 청크 20개는 별도 corpus로 추가했다. 원문부터 따라가는 학습은 아래 10절을 참고한다.

## 1. 실행하고 첫 질문 세 개를 관찰하기

현재 macOS arm64 환경에는 Python·Ollama·BGE-M3·Qwen3와 영속 색인을 준비했다.
제품 폴더 `1. Naive RAG/`에서 실행한다. 설치를 직접 수행하는 과제가 아니며, 아래는 재시작 명령이다.

```sh
.venv/bin/python scripts/runtime.py start
.venv/bin/python scripts/serve.py --port 8000
```

브라우저에서 http://127.0.0.1:8000 을 연다. UI 종료는 실행 터미널에서 Ctrl+C, 모델 종료는 별도 터미널에서
`.venv/bin/python scripts/runtime.py stop`이다. 이미 사용 중인 포트를 강제로 종료하지 않는다.
모델/색인을 지울 필요는 없다. 재시작하면 같은 자산을 다시 쓴다.

1. **생일 휴가 자격**: “생일 휴가는 누구나 입사 직후부터 사용할 수 있나요?” 먼저 자격 원문을 예상한다.
   정답 근거는 입사3개월 경과와 수습 제외다. 현재 실제 실행에서는 근거가 검색·전달됐는데 모델이 과도 보류했다.
   이것은 검색 실패가 아니라 생성 판단 실패다. 문서가 있는데 보류했다고 무조건 안전한 정답으로 세지 않는다.
2. **여러 근거 연결**: “생일 휴가의 자격과 신청 기한, 사용 기간을 함께 알려 주세요.”
   birthday-eligibility/request/window 세 근거를 찾아야 한다. 현재 답변에는 대부분 조건이 있지만 연1일이 빠졌다.
   인용문에 있는 조건과 answer에서 사용자에게 설명한 조건을 따로 비교한다.
3. **근거 없는 질문**: “퇴직금 계산식은 어떻게 되나요?”
   문서에 계산식이 없다. Dense가 가까운 문서를 반환하더라도 답을 만들면 안 된다. 현재 실제 실행은 보류했다.
   문서의 부재는 제도 자체가 없다는 뜻이 아니다.

정상 답변 비교용으로 “재택근무일과 휴가일에도 사무실 식대가 나오나요?”를 실행한다.
실제 q10은 사무실 출근일1만 원, 재택/휴가일 미지원을 welfare-meal 원문으로 인용해 답했다.
모델 출력은 다시 실행할 때 달라질 수 있다. 고정 temperature/seed를 바이트 재현성 보장으로 해석하지 않는다.

화면에서 순서대로 읽는다: 검색된 근거 펼치기 → 실제 전달 문맥 확인 → 답변 조건과 인용 대조 → trace의 reason/validation 확인.
“결과 JSON 저장”으로 이번 질문·순위·문맥·모델 digest·프롬프트·시간을 보관할 수 있다. 저장 내용은 가상 자료만 사용한다.

## 2. 흐름 지도

```text
기존 화면: 수작성 청크(title/text/source/version)
                ↓ BGE-M3 문서 임베딩
          Qdrant local 영속 cosine 색인
                ↑ BGE-M3 질문 임베딩
질문 → Dense 또는 BM25 검색 한 번 → top-k 후보
     → 전체 청크 문맥 예산 → 시스템 프롬프트 + 질문 + 선택 문맥
     → Qwen3 생성 한 번 → JSON/인용 검사 → 답변 또는 보류
```

- 청크: 검색·전달하는 자료 조각. UI 기본값은 수작성 15개이며, P006에는 별도 원문을 400자/겹침 80자로 분할한 20개 청크도 있다.
- 임베딩: 문서와 질문을 같은 벡터 공간에 놓는다. 유사도가 높다는 것은 그 문서가 정답을 보장한다는 뜻이 아니다.
- Qdrant: 저장한 벡터와 원문 payload를 다시 열어 검색한다. 현재는 프로세스 내 로컬 모드다.
- BM25: 단어 겹침과 빈도를 이용한다. `휴가`와 `휴가는`은 현재 토큰화에서 다르다.
- top-k: 검색에서 가져올 후보 수. **검색 후보와 모델에 전달된 문맥은 다를 수 있다.**
- 문맥 예산: 메타데이터 포함 청크 JSON 객체의 문자 수 합. 전체 청크가 들어가지 않으면 제외한다. 토큰 수와 같지 않다.
- 생성: 문맥을 읽고 답을 구성한다. 문맥에 없는 것을 보태거나 있는 조건을 놓칠 수 있다.
- 검증·조립: 모델은 실제 전달 문맥의 근거 ID만 선택한다. 코드가 ID와 중복/추가 필드를 검사한 뒤 해당 청크 원문 전체를 quote로 붙인다. 인용문은 특정 문장만 발췌한 것이 아니다.
  유효한 인용을 붙인 틀린 답변도 가능하므로 의미 검토를 별도로 한다.

코드가 궁금해질 때만 `scripts/rag.py`의 ask → retrieve → select_context → validate_answer 순서로 읽는다.
UI/API도 이 ask 함수를 그대로 호출한다. 자동 재검색·Agent·reranker·Hybrid는 없다.

## 3. 실패가 어느 층에 있는지 먼저 분류하기

| 관찰 | 확인할 위치 | 다음 실험 |
| --- | --- | --- |
| 원문에 규정 자체가 없음 | data/synthetic/chunks.jsonl | 적절 보류인지, 허구를 만들었는지 |
| 원문은 있는데 검색 후보에 없음 | 후보 순위와 qrels | top-k/표현/BM25 vs Dense |
| 후보에는 있는데 전달 문맥에서 빠짐 | contexts/excluded/context_chars | 문맥 예산 또는 전체 청크 크기 |
| 전달했는데 조건을 빠뜨림 | answer와 실제 contexts | 프롬프트/모델의 의미 처리 |
| 근거 있는데 보류 | reason과 raw_content | 과도 보류; q01/08/09 사례 |
| 없는 ID·미전달 ID·중복 ID·추가 quote 출력 | validation | invalid_model_response로 차단되는지 |
| 유효한 ID지만 답변을 뒷받침하지 못함 | answer와 인용 원문 전체 | 별도 의미 검토로 잘못된 근거 선택 판별 |
| HTTP/timeout/stale index | status=error, trace.error | 실행 장애 수정 후 재실행; 품질 보류와 분리 |

P004 당시 system-v2, top-k5 실제14질문을 사전 rubric으로 Codex가 대조했다. 사람 검토 결과가 아니다.
답 가능11: 정확5/부분2/과도보류4/오답0/장애0. 근거 없음3: 적정보류3/허구답변0/장애0.
첫 system-v1에는 최종 오답1이 있었고, v2에서는 해당 q11의 인용 오류가 차단돼 보류가 됐다.
정확한 답변 수는 늘지 않았으며 q07은 조건 누락이 늘었다. “프롬프트를 길게 쓰면 좋아진다”는 결론을 내리지 않는다.
루트 `docs/verification/p004/first-review.md`, `final-review.md`, `03-live-first/`, `05-live-v2/`를 비교한다.
단독 복사본에는 루트의 검증 기록이 포함되지 않으므로 원 저장소에서 확인하거나 필요한 기록도 별도로 복사한다.

## 4. 평가 지표를 구분하기

| 평가 | 무엇을 묻나 | 주의 |
| --- | --- | --- |
| Recall@K | 필요한 관련 청크 중 K개 안에 몇 개가 들어왔나 | 한 근거만 맞아도 복수 조건 전체를 답할 수 있는 것은 아님 |
| MRR | 첫 관련 청크가 얼마나 앞에 있나 | 첫 근거 뒤에 필요한 다른 근거가 누락돼도 높을 수 있음 |
| nDCG | 관련성 등급이 높은 근거가 앞에 배치됐나 | 등급 정의와 정답 자료 품질에 의존 |
| 문맥 근거 충족 | 필요한 근거가 실제 LLM 입력에 모두 있었나 | 검색 Recall과 별도; 예산으로 제외 가능 |
| 사실 정확/조건 누락 | 답변이 필수 사실·예외·일수·주체를 지켰나 | 원문과 사전 rubric으로 검토 |
| 인용 구조/의미 지지 | 원문 quote가 맞나 / 그 quote가 주장을 지지하나 | 두 판단을 합치지 않음 |
| 과도보류/허구답변 | 답할 수 있는데 보류했나 / 못 답하는데 만들었나 | answerable11와 unanswerable3의 분모 분리 |

현재 같은 corpus의 검색 Recall@5는 Dense1.0, BM25 약0.8939다. Dense는 근거 없는3질문에서도 모두 검색 결과를 반환했다.
그래서 검색 점수만으로 답변 가능을 판정하지 않는다. Dense/BM25 원점수 크기도 직접 비교하지 않는다.
qrels·answerability·기대답은 평가 전용이다. 이를 검색/프롬프트에 넣으면 답을 미리 알려준 실험이 되어 평가가 무효다.
자동 키워드 일치와 생성 모델 자기평가는 독립 의미 정답을 대신하지 않는다. 현재 14개는 작은 합성 세트이며 일반 HR 성능이 아니다.

## 5. 첫 최적화: top-k만 바꾸기

가설 예: “복수 조건 질문에서는 K가 커지면 누락 근거가 줄지만, 문맥/지연은 늘 수 있다.”
화면에서 q03을 고정하고 Dense·문맥8000·모델·프롬프트를 그대로 둔 채 K=1/3/5/10을 각각 실행한다.
각 실행의 JSON을 저장하고 아래 표를 채워 보도록 Codex에 요청한다. 직접 코드를 수정할 필요는 없다.

| K | 세 필수 근거 검색/전달 수 | 답변의 빠진 조건 | 인용 구조 | 보류 사유 | 문맥 문자 | embedding/search/generation/total |
| --- | --- | --- | --- | --- | --- | --- |
| 1 / 3 / 5 / 10 | 결과에서 기록 | 원문 대조 | 통과/실패 | reason | trace | cold/warm 구분 |

실제로 같은 q03으로 위 실험을 실행했다(Codex 원문 대조, 사람 검토 아님).

| K | 필수3근거 전달 | 문맥 문자 | 실제 관찰 | 전체 시간(단일 관측) |
| --- | --- | --- | --- | --- |
| 1 | 1개 | 247 | 모델이 자격/기간을 만들고 인용을 변형해 검증 보류 | 17.42초 |
| 3 | 3개 | 775 | 답변 생성, 연1일·시스템·팀장 승인 누락 | 27.70초 |
| 5 | 3개 | 1274 | 답변 생성, 연1일 누락 | 28.80초 |
| 10 | 3개 | 2540 | 답변 생성, 연1일 누락 유지 | 34.97초 |

K3부터 검색 근거가 충분해도 답변이 완전하지 않았다. K10은 이 실행에서 문맥/시간을 늘렸지만 남은 누락을 고치지 않았다.
K1 보류도 모델이 잘 판단한 것이 아니라 허구 답변의 인용 오류를 검증기가 막은 결과다.
실제 request/result는 원 저장소 docs/verification/p005/04-k-experiment/, 의미 검토는 k-experiment-review.md에 있다.
이 표는 한 질문의 순차 관측이며 독립 holdout이나 p95/보편 성능이 아니다.

검색 전용 비교는 같은 rankings를 평가하는 것으로 충분하며 생성 결과까지 추정하지 않는다.

```sh
.venv/bin/python scripts/run_dense_baseline.py --chunks data/synthetic/chunks.jsonl --queries data/synthetic/queries.jsonl --index-dir .runtime/index-v1 --top-k 10 --k 1 3 5 10 --output-dir /tmp/rag-dense-k-new
.venv/bin/python scripts/run_bm25_baseline.py --chunks data/synthetic/chunks.jsonl --queries data/synthetic/queries.jsonl --top-k 10 --k 1 3 5 10 --output-dir /tmp/rag-bm25-k-new
```

출력 경로는 새 경로여야 한다. 기존 결과를 지우거나 덮어쓰지 않는다. 질문/모델/문서/prompt hash가 같은지 확인한다.
P003 실제 q03은 BM25의 자격 근거가6위, Dense에서는2위였다. K=5에서 필요한 근거가 달라지는 이유를 원문과 토큰으로 설명해 본다.
14질문에 맞춘 변경을 일반화하지 말고 이후 별도 holdout/표현 변형 세트를 준비한다.

## 6. 두 번째 실험과 그 다음

두 번째는 **같은 질문·K·예산으로 Dense/BM25만 비교**한다. q03과 q10, 그리고 q13을 사용한다.
q13에서 BM25 빈 결과→no_context와 Dense 후보 있음→model_abstained를 구분한다.
표현·조사를 바꾸는 실험은 검색 방식 비교가 끝난 뒤 별도 실행한다. 두 변수를 동시에 바꾸면 원인을 분리하기 어렵다.

그 다음에는 문맥 예산만 줄여 전체 청크가 언제 빠지는지 본다. 극단적으로1자로 두면 no_context가 되고 모델 호출은0이다.
프롬프트 실험은 v1/v2처럼 버전과 hash를 남기고 첫 실패와 재검증을 모두 보관한다. 실패를 보고 조정한 세트는 holdout이 아니다.
모델 크기·temperature 변경은 별도 계획으로 진행한다. 현재 qwen3:4b와 고정 옵션은 계약/lock이므로 UI에서 임의 전환하지 않는다.
청킹이나 corpus 변경은 새 데이터 버전, 새 색인, qrels/rubric 재검토가 필요하다. 원본은 비교 기준으로 보존한다.
추후 Hybrid·reranker·Agentic은 별도 큰 방식/계약으로 비교한다. 아직 구현됐다고 보지 않는다.

## 7. 테스트와 품질 검토 지도

| 층 | 실제 프로젝트 예 | 검출할 문제 |
| --- | --- | --- |
| 단위 | 평가 산식, 전체 청크 예산, JSON/quote 검증 | 계산/타입/조건 분기 오류 |
| 통합 | 영속 Qdrant 재open, Ollama 어댑터, 실제 localhost HTTP + fake provider | 경계/프로토콜/오류 매핑 |
| 회귀 | 기존68개 포함 고정 테스트, 원본 hash 보존 | 변경으로 이전 기능이 깨지는지 |
| 실제 E2E | 브라우저 입력→API→BGE→Qdrant→Qwen→화면 | 실제 연결·렌더링·사용 흐름 |
| 의미 검토 | 사전 rubric과 질문별 answer/citations 원문 대조 | 조건 누락·모순·과도보류·허구답변 |

fake provider 테스트 통과를 live 모델 품질로 표기하지 않는다. 실제 E2E도 모든 질문 정답을 증명하지 않는다.

```sh
.venv/bin/python -m unittest discover -s tests -v
```

이 명령은 제품 폴더에서 실행한다. 루트의 P001 과거 회귀는 저장소 루트에서 `python3 -m unittest discover -s tests -v`다.
검증 증거는 원 저장소 `docs/verification/p001/`~`p005/`에 보존한다.

## 8. 시간을 해석하는 법

첫 요청은 모델 로드(cold)가 들어갈 수 있다. Ollama는 현재 동시에 모델 하나를 유지하므로 Dense 질문에서는 임베딩 모델과 생성 모델 교체도 발생한다.
같은 질문을 반복해도 임베딩/생성 교체가 있어 전 구간이 warm이라고 단정하면 안 된다.
trace의 retrieval.embedding_ms / search_ms / index_open_ms와 generation.observations.load_duration,
timings_ms의 retrieval/context/generation/total을 나눠 본다. UI 전체시간에는 HTTP 왕복과 다른 요청의 직렬화 대기도 있다. trace의 처리시간은 대기 후 코어 실행 구간이며 두 시간을 혼동하지 않는다.
같은 하드웨어·모델 digest·prompt·문맥/출력 길이·동시성·cold/warm 조건을 기록한다. 단일 관측이나14개 표본의 p95를 보편 성능으로 과장하지 않는다.

## 재현 자산과 한계

runtime-lock.json: Python/의존성/임베딩/런타임. generation-lock.json: 생성 digest/양자화/template/설정.
requirements.lock: 설치 버전. stage-manifest.json: 원본 출처/hash. prompts/: 버전별 프롬프트.
현재 기능은 P001~P005 Naive RAG 기준선이다. 실제 직원 문서·개인정보·외부 계정·유료 API는 사용하지 않는다.
학습은 준비된 실제 UI와 관측 실패에서 시작한다. 개선의 판단은 사용자가 하고 구현/테스트 실행은 계속 Codex에 맡길 수 있다.

## 10. 원문부터 청크가 생기는 과정 관찰하기

이제 문서를 직접 열 수 있다. [생일 휴가 PDF](data/source-v2/output/pdf/birthday.pdf), [연차 PDF](data/source-v2/output/pdf/annual.pdf)는 각각 2페이지다. 여섯 주제의 Markdown 편집 원문은 `data/source-v2/authoring/`에 있다. 이번에 새로 쓴 가상 원문이며 예전 청크 이전부터 있었던 문서가 아니다.

업무 가정은 “HR 담당자가 Drive 지정 폴더에 규정을 올린다”이다. 이번 실습은 **Drive fixture 모사**다. 실제 업로드/다운로드나 폴더 동기화는 하지 않았다.

```text
새 가상 원문 6개 → Drive fixture 목록 → snapshot/cache (바이트 동일 사본)
 → PDF 페이지 추출 / Markdown 읽기 → NFC·LF 정규화 → canonical text + page map
 → fixed 문자 청킹 400/overlap 80 → 20청크 + source map
 → 별도 BGE-M3 색인 → 기존 검색·Qwen 답변 코어
```

400은 최대 문자 수, 80은 인접 창이 겹치는 문자 수다. 첫 창 `[0,400)`, 다음 `[320,720)`처럼 이동한다. 문자 수는 모델 토큰 수와 다르다. 이 숫자는 비교를 시작하기 위한 값이며 최적값으로 고른 것이 아니다. 현재까지 fixed 문자 청킹만 구현했다.

다음 순서로 의미를 확인한다. 실행·수정·검증은 Codex가 수행한다.

1. **원문을 읽고 예상:** 연차 PDF에서 “5일분”과 “다음 해 3월 31일”을 찾는다. 둘이 같은 청크에 들어가야 답변하기 쉬울지 예상한다.
2. **추출 결과 관찰:** `extracted/canonical/hr-v2-annual.txt`를 열어 PDF의 줄바꿈과 바닥글이 어떻게 남았는지 본다. 글자가 빠졌는지, 숫자와 부정 표현이 유지됐는지 확인한다.
3. **청크 경계 관찰:** `fixed-400-80/source-map.json`의 start/end와 pages를 본다. 원문 전체 5,669자는 겹침을 포함해 6,789자의 청크 본문이 됐다. 20청크 중 3개는 PDF 페이지 경계를 걸친다. 문서끼리는 합치지 않는다.
4. **원문으로 역추적:** chunk_id → canonical 위치 → 페이지 → cache 해시 → fixture file_id/snapshot_id를 따라간다. 파일 표시 이름과 파일 ID, 내용 해시는 서로 다른 개념이다.
5. **평가 근거 확인:** `evaluation/source-evaluation.json`은 질문별 필요한 사실과 원문의 정확한 span을 기록한다. 청킹 방법이 바뀌어도 이 원문 근거를 기준으로 비교할 수 있다. 정답 파일은 검색/생성 모델에 전달하지 않는다.

첫 실제 실패도 학습 자료다. 연차 이월 질문에서 관련 원문은 검색 1위로 전달됐고 답변 초안도 “5일분/3월 31일”을 설명했다. 하지만 모델이 인용문에서 PDF 줄바꿈을 없앴기 때문에 기존의 정확한 부분 문자열 검증에 실패해 최종 보류됐다. **검색 성공, 답변 내용, 인용 형식 성공을 따로 봐야 한다.** 문맥이 없어서 보류한 경우와 다르다. 이번 단계에서는 인용 검증 규칙을 완화하거나 프롬프트/정규화를 최적화하지 않았다.

연차 발생 질문의 실제 실행에서는 “한 달 개근 시 1일”을 정확히 인용해 답했고, 퇴직금 계산식 질문에는 적절히 보류했다. 이는 기능 smoke 결과이며 전체 답변 품질 향상을 뜻하지 않는다. 기존 UI 결과와 새 corpus 결과는 문서·청크 조건이 다르므로 같은 실험으로 섞지 않는다. 현재 UI는 기존 15개 청크를 유지하고 새 원문 corpus는 README의 명시 CLI로 실행한다.

다음 실험에서 세울 가설 예시:

- 청크가 너무 작으면 수량과 예외 조건이 갈라져 답변이 불완전해질 수 있다.
- 겹침을 늘리면 경계에 걸친 근거를 더 잘 담지만 중복 문맥과 저장량이 늘 수 있다.
- PDF 줄바꿈 정규화는 인용 실패를 줄일 수 있지만 문단/표 구조와 offset의 의미를 바꿀 수 있다.

P007에서 여러 청킹 방식과 검색 지표, P008에서 최종 답변 및 UI 비교를 진행할 계획이다. 두 과제의 상세 계약이 준비되기 전에는 구현하지 않는다. 사용자는 변화의 원인과 지표 해석에 집중하고, 코드를 직접 짜거나 테스트를 수작업으로 수행할 필요는 없다.

## P009: 원문 복사는 코드에 맡기고, 의미를 평가하기

현재 system-v3에서는 모델이 답변과 근거 ID만 생성한다. 코드는 요청 시점에 실제 전달한 청크에서 원문 전체를 가져온다. PDF 줄바꿈을 모델이 다시 쓰다가 손상시키는 경로를 없앴다. 옛 system-v1/v2와 P004~P006의 실패 기록은 당시 계약의 결과로 보존한다.

식대 질문을 BM25/top-k5로 실행하고 trace의 `raw_content`에는 chunk_id만, 최종 citations에는 원문 전체가 있는지 비교한다. `generation.request.format`의 enum은 실제 contexts ID와 같아야 한다. `citation_assembly`의 원문 hash와 `citation_mode=full_chunk_from_transmitted_context`도 확인할 수 있다.

학습의 핵심은 세 가지다. 필요한 근거가 전달됐는지, 모델이 그중 알맞은 근거를 골랐는지, 답변이 조건과 예외를 빠짐없이 설명했는지를 각각 판단한다. 원문 문자열 일치가 의미적 지지를 증명하지 않는다. `semantic_support=not_automatically_evaluated`는 계속 유지한다. 실제 14질문·식대·PDF 검토는 루트 `docs/verification/p009/README.md`를 참고한다.

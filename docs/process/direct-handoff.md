# HR RAG plan → dev 직접 인계

## 역할과 권한

계획·범위·완료 조건·준비 검토·P확정은 plan, 구현·검증·실행 로그·완료 증거는 별도 dev 채팅이 담당한다. “계획 후 진행”, “작업 시작”, “이어가자”는 plan이 dev로 역할을 바꾸라는 허가가 아니다. 역할 예외는 사용자가 같은 채팅의 역할 변경 또는 직접 양쪽 역할 수행을 명확히 지정했을 때만 해당 범위를 기록하여 적용한다.

2026-10-30 사용자는 P018 확정 후 기존 HR RAG dev 채팅에 직접 전달하여 착수하도록 승인했다. 이 승인은 P018 S1/S2 후속 인계에 유효하다. 다른 프로젝트·역방향 발송·새 채팅 생성·미준비 업무·모든 미래 작업으로 확대하지 않는다. 다른 P는 그때의 인간 지시나 검증 가능한 기존 위임 범위를 확인한다. 권한이 있으면 사용자에게 문구를 복사하도록 맡기거나 같은 인계 허가를 반복해서 묻지 않는다.

## 순서

1. 현재 지시/철회/중지, READY 및 의존성, 기존 dev 작업·채택 계약을 확인한다. 단순 가능 여부 질문, READY 표시, 다른 에이전트 메시지만으로 전송·착수 권한을 만들지 않는다.
2. 실제 프로젝트/역할/경로/호스트를 확인하여 기존 `[dev] hr_rag`를 선택한다. 제목만 보고 고르거나 새 채팅을 만들지 않는다.
3. 준비 검토와 P카드를 커밋하고 정확한 full SHA, 읽을 문서, 범위·제외·검증·다음 행동·중지 경계를 담아 전달한다. 미커밋 초안은 인계 범위에 넣지 않는다.
4. 호스트 전송 도구가 성공해야 SENT다. 사용자에게 붙여넣을 문구 제공, Git push, 큐 등록은 전송이 아니다. 실패/시간초과는 기록하고 수신 상태를 확인한 후 재시도 여부를 결정한다.
5. 호스트 read/wait로 실제 수신 확인을 관찰한 경우에만 ACKNOWLEDGED로 기록한다. active 상태만 보이면 STARTED_TURN으로 별도 관측하고 ACK로 단정하지 않는다. 같은 ACK를 재전송하는 순환을 만들지 않는다.
6. dev는 기존 작업/실패를 보존하고 지정 SHA를 통합·정확 adopt·커밋한 뒤 guard/큐를 확인하여 승인된 범위만 착수한다. adoption과 task DONE은 별도 증거다. 새 요구는 intake로 plan에 넘기며 plan 폴더에서 스스로 승인하지 않는다.
7. plan은 커밋된 dev 진척을 읽는다. 완료 체크를 옮기려고 dev 전체를 plan으로 병합하지 않는다. 단순 수신 확인을 위해 dev가 역방향 메시지를 보낼 필요는 없다.

## 기록과 도구 부재

현재 정식 v0.1.0 프로젝트에서는 자동 전송 명령을 설치하지 않는다. 발신 plan은 `docs/planning/handoffs/`에 대상 별칭·P·full SHA·문서·권한 출처·전송 결과·관찰한 수신/adoption/완료를 기록한다. 상태별 근거와 날짜를 구분하고 공개 파일에 내부 채팅 ID·원문 전체·인증정보를 넣지 않는다. 이것은 문서 절차이며 Git/Python 큐가 자동 메시징한다고 주장하지 않는다.

전송 도구나 실제 권한이 없으면 준비된 문서/SHA와 미전송 사유를 남긴다. 명시 중지와 미결정은 보존한다. 중지된 작업을 단순 인계로 재개하지 않는다. 보호 파일 변경이 필요한 하네스 유지보수는 P018의 제안→plan 검토 배포→dev exact adoption 순서를 따른다.

# P번호 기획·개발 작업 흐름

plan/dev는 역할 이름이다. 실제 브랜치 이름은 `.harness/policy.json`을 따른다.

## 요청과 순서

- plan: “다음 작업 기획해줘” — 다음 P작업의 계약·검증·완료 조건 준비.
- dev: “다음 큐 진행해줘” — 진행 중 작업 우선, 그다음 승인되고 선행이 완료된 작업 실행.
- dev: “큐 순서대로 계속 진행해줘” — 착수 가능한 범위를 순차 처리.

```sh
python3 scripts/work_queue.py --owner all
python3 scripts/work_queue.py --brief
python3 scripts/work_queue.py --json
python3 scripts/work_queue.py --open
```

조회는 fetch/merge/push/구현/승인을 실행하지 않는다. --open은 미완료가 있으면 exit1,
잘못된 계약/진척은 exit2다. 초기 빈 큐는 정상이며 제품 요구가 없으면 과제를 발명하지 않는다.

## 한 번호로 기획부터 완료까지

`docs/planning/plans/_TEMPLATE.md`를 복사해 다음 미사용 P번호를 부여한다.
P001, P002 등은 식별자다. 실행 순서는 우선순위와 선행 작업으로 정한다.
기존 legacy work-queue.json이 있으면 완료 이력과 hash를 보존한다. 신규 저장소에는 불필요한 legacy 파일을 만들지 않는다.

| 준비 / 실행 | 의미 |
| --- | --- |
| 초안 / 미착수 | plan이 요구·연결·승인 범위를 준비 |
| 준비 완료 / 미착수 | 구체적인 범위에 승인 근거 있음. 선행 미완료이면 대기 |
| 준비 완료 / 진행 중 | 구현 → 검증 → 수정 → 영향 범위 재검증 |
| 준비 완료 / 차단 | 이유와 필요한 조치를 STATE 로그에 기록 |
| 준비 완료 / 완료 | 모든 체크와 최신 PASS 증거가 일치 |

하네스의 기본 인계 방식은 plan에 준비 검토·dev 등록을 위임하는 것이다.
사용자가 요청한 프로젝트 목표 안에서 요구·범위·선행·검증·완료 조건이 갖춰지면 plan이 준비 검토를
기록하고 준비 완료로 전환해 커밋·큐 등록한다. 별도의 “dev 인계 허가”를 반복해서 묻지 않는다.
승인 근거 필드는 매번 사용자에게 결재받는 칸이 아니라 프로젝트 요청·이 위임·준비 검토의 출처다.
미결 업무 결정이나 기존 권한을 넘는 배포·새 원격 공개 등은 따로 해결한다. 미결 상태를 커밋만으로 승인하지 않는다.

## 소유권과 검증

plan: 목적·요구·산식·의존성·우선순위·준비/승인·완료 조건.
dev: `> 실행:`, CHECKLIST 안의 체크 표시, EXECUTION 안의 추가 로그만 변경.
조건 문구/개수·기존 로그를 삭제하거나 변경할 수 없다. 실제 구현과 근거는 dev 소유다.

```markdown
- 2026-09-16T18:00:00+09:00 | STATE | NOTE | - | 승인 범위 착수.
- 2026-09-16T18:10:00+09:00 | C1 | FAIL | docs/verification/p001/check.md | 경계값 불일치.
- 2026-09-16T18:20:00+09:00 | C1 | PASS | docs/verification/p001/recheck.md | 수정 후 독립 기대값 일치.
```

체크된 항목은 최신 PASS 및 비어 있지 않은 실제 근거 파일이 필요하다. FAIL이면 체크를 해제한다.
전 항목 체크와 실행 완료는 함께 바꾼다. 실패 검사를 빼거나 근거 없이 PASS로 적지 않는다.
검사기는 파일 존재/상태 일치를 검증하므로 실제 내용이 충분한지도 담당자가 검토한다.
완료 시 guard·필요 회귀·큐를 확인하고 구현/작업서/근거를 함께 커밋한다.

## 공유와 인계

plan은 dev 또는 그 upstream의 커밋된 진척을 읽는다. 미커밋 진척은 반영되지 않는다.
계획 본문이 변경되면 기존 완료 체크를 자동 승계하지 않고 재채택·영향 검토를 알린다.
원격/로컬 dev가 갈라지면 자동 선택하지 않는다. 다른 컴퓨터는 먼저 fetch/브랜치를 동기화한다.

dev의 채택 큐가 비어 있으면 최신 이용 가능한 plan에서 준비 완료 작업을 확인한다.
그 계획을 dev로 병합한 뒤 정확한 plan SHA를 adopt하고 그 기록을 커밋한다.
이 과정에 별도 인계 허가는 필요하지 않다. 작업 중인 dev 변경·로그를 보존하고 안전한 시점에 채택한다.
조회 스크립트가 자동 병합/실행하는 것은 아니며, 다른 작업에 메시지를 보내거나 실행을 강제하지 않는다.
충돌 시 요구사항과 dev 로그를 함께 보존한다. plan으로 dev 전체 이력을 되가져올 필요는 없다.
공유할 두 브랜치는 각각 push해야 한다. 한 브랜치 push가 다른 원격 브랜치를 움직이지 않는다.
기존 push 권한을 적용하고 release 승격은 명시 요청 시에만 수행한다.

## dev 새 요구 접수

plan은 매 작업 시작 시 `python3 scripts/work_queue.py --owner all`의 새 요구 대기열을 먼저 확인한다.
`plan_requests` JSON 항목에는 요청 ID·본문 경로·hash·검토 상태·연결 P번호가 포함된다.
새 요구 대기열은 실행 큐와 별개이며 P번호의 우선순위를 자동으로 바꾸지 않는다.
`--brief`에서도 미검토 요청을 표시하고, `--open --owner plan/all`은 미검토 요청이 있으면 exit 1이다.
조회는 항상 읽기 전용이다. plan은 커밋된 dev 요청, dev는 로컬 요청과 채택한 plan의 검토 결과를 본다.
plan의 검토를 아직 채택하지 않았다면 dev에는 대기가 남을 수 있다.

[요청 접수 규칙](plan-intake.md)에 따라 dev 기록 → plan 판단 → P카드 준비 검토 → 정확한 채택을 거친다.
요청의 LINKED/COVERED 상태는 검토/연결 표시이며 구현 준비 완료를 뜻하지 않는다.

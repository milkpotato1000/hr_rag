# Project B — HR RAG → Agentic RAG 프로젝트 기획

HR 규정 문서에서 근거를 찾아 질문에 답하고, 근거가 부족하면 담당자에게 연결하는 에이전트를 만든다. 같은 문서와 평가 질문으로 검색 방식, 에이전트 흐름, 모델 서빙 설정을 비교하며 각 계층의 역할을 학습한다.

기획 출처는 사용자가 2026-10-22 지정한 [HR RAG 에이전트 설계 대화](https://chatgpt.com/share/6ad97a1c-ef84-83ee-bb65-982dda568ead)다. 당시 “프로젝트 B” 원기획은 공유 범위에 없었으나 2026-10-29 사용자가 RAG Generation Evaluation 설계를 제공했다. 후속 A/B/C 정의에 따라 현재 HR RAG 전체가 Project B이며, Generation Evaluation은 [B 내부의 별도 평가 모듈](../architecture/project-b-generation-evaluation.md)이다. Project A는 NL2SQL + Tool Calling, Project C는 Multi-Agent Orchestration이며 [프로젝트 구분](project-map.md)을 따른다. 아래 단계와 P001 세부 계약은 이 대화를 실행 가능한 작업으로 구체화한 것이다.

## 사용자 흐름

직원이 “생일 휴가 있나요?”라고 질문하면 관련 규정을 검색하고, 적용 조건과 시행일을 확인해 출처와 함께 답한다. 검색으로 답을 확인하지 못하면 제한된 재검색 후 답변 보류 또는 담당자 연결로 끝낸다. 문서가 없다는 이유로 제도가 없다고 단정하지 않는다.

학습자는 질문, 검색 결과, 도구 실행, 인용 근거, 최종 행동과 지연시간을 확인한다. 내부 추론 전문 대신 관찰 가능한 도구 요청과 결과, 짧은 판단 요약을 기록한다.

P011은 ADOPT_LANGCHAIN으로 완료됐고 P012 기본 학습/API/CLI는 LangChain, Direct와 A/B 비교는 별도 실험 메뉴다. 2026-10-29 최신 요청으로 **P015 원문 PDF 재작성(완료) → P016 장문 규정집 확장 → P007 청킹·검색 실험 → P013 기본 평가기 → P014 NLI 비교 → P008 답변 비교 UI → P010 Hybrid** 순서를 적용한다. 하네스는 별도 프로젝트에서 수행하며 HR RAG 번호 단계가 아니다. 현재 제품에는 기존15청크와 P006 source-v2가 남아 있고, P015의 PDF/source-v3는 완료됐다. 장문 실험용 source-v4는 P016에서 작성하며 기존 완료본을 보존한다. 실제 Drive 연결은 후속 계약이다. 완료 근거는 dev의 P카드·검증 기록, 최신 장문 확장 준비 근거는 [P016 준비 검토](reviews/P016-readiness.md)를 따른다.

## 큰 구현 단계와 세부 작업 위치

번호 폴더는 RAG 방식이 달라지는 큰 단위로 관리한다. 평가 기반·BM25·Dense·기본 답변 생성은 모두 `1. Naive RAG/` 안의 세부 작업이다. 여러 P카드가 같은 큰 단계에서 진행되며 위 개발 단계 표의 각 행을 별도 번호 폴더로 만들지 않는다.

후속 큰 단계에서 앞선 단계의 필요한 내용만 복사·선별한다. P015에서 만든 `2. Document Chunking/`을 P016/P007에서도 사용하고 `3. Hybrid RAG/`는 예정 위치이며 Agentic의 최종 번호·범위는 후속 착수 계약에서 정한다. [큰 단계별 폴더 규칙](../architecture/stage-layout.md)을 따른다. P006 원문 추출 기준선은 Naive 폴더에 보존하고 P015 보존 원문과 P016 장문 원문/추출본을 확보한 뒤 P007 청킹 비교를 먼저 진행한다.

P011은 같은 Naive 방식의 구현 비교라서 새 큰 번호 폴더를 만들지 않는다. 원래 `1. Naive RAG/`를 보존하고 후보 `1. Naive RAG/variants/langchain/`를 독립 실행 가능한 사본으로 둔다. [P011 비교 계약](../architecture/langchain-naive-comparison.md)을 따른다.

## 기술 구성 방향

| 계층 | 대화에서 제시된 방향 | 구체화할 사항 |
| --- | --- | --- |
| 애플리케이션 | Python 직접 구현과 LangChain Core 비교, 후속 API·Slack | P011 검증 후 LangChain 채택, P012에서 기본 학습 진입 정리 |
| 에이전트 | Python 직접 구현 후 필요 시 LangGraph | 재검색·도구 실행·종료를 애플리케이션이 관리 |

| 재정렬 | BGE reranker | 모델 ID, 언어 적합성, 실행 환경 |
| 생성 모델 | Qwen3 | 크기, 가중치, 양자화, 라이선스, 컨텍스트 길이 |

모델의 도구 호출 요청을 실제 실행하는 주체는 Python 에이전트다. 서빙 계층은 모델을 실행하고 응답을 반환하는 경계로 둔다. 상세 책임은 [아키텍처 방향](../architecture/system-design.md)을 따른다.

## 평가 방향

검색기 비교는 같은 corpus·청크·질문·정답을 사용해 Recall@5/10/20, Precision@K, MRR@K, nDCG@K와 지연시간을 비교한다. 관련성 정답이 없는 질문은 별도 집합으로 보류·에스컬레이션을 평가한다. MMR은 다양성 선택 실험으로 분리한다.

생성은 답변 정확성, 근거 충실성, 인용의 정확성, 보류 적절성을 평가한다. Agent는 도구 선택·인자 유효성·재검색 종료·실패 복구를 추가한다. 서빙은 TTFT, 출력 토큰 속도, 전체 지연, 처리량, GPU 메모리를 기록하며 하드웨어·가중치·양자화·프롬프트·길이·동시성을 함께 남긴다. 조건이 다르면 차이를 명시하고 엔진만의 효과로 단정하지 않는다.

품질 목표 수치는 기준선 측정 후 결정한다. P001의 통과 조건은 평가 계산과 데이터 일관성의 정확성이며, 검색·답변 성능이 이미 확보되었다는 뜻이 아니다.

## 데이터와 연동 경계

초기 문서는 가상의 규정과 질문만 사용한다. 공유 대화의 생일 휴가 예시는 실제 회사 정책으로 취급하지 않는다. 공개 GitHub에는 실제 직원 정보, 내부 HR 규정, 인증 정보를 올리지 않는다.

실제 Drive·Slack 접근, 외부 메시지 전송, 모델 다운로드, GPU 자원 생성과 배포는 이 기획 반영 작업에 포함하지 않는다. 해당 단계의 실제 대상과 실행 범위를 먼저 정한다.


## E2E 구현과 학습의 역할

사용자는 Codex가 구현·테스트·수정·실행까지 맡고 본인은 파이프라인 의미·평가·최적화 실험을 중심으로 학습하기를 요청했다. P003부터 필요한 로컬 공개 런타임·모델 다운로드와 격리 의존성 설치·loopback 실행을 해당 P계약에 명시해 진행한다. 초기 기획 반영 당시의 모델 다운로드 제외는 새 E2E 요청의 명시된 로컬 실행 범위를 막지 않는다. 유료 API·원격 GPU·실데이터·외부 메시지·배포는 별도 범위를 정한다.

청킹 전략 비교에서는 원문·질문·원문 fact/span 정답을 고정하고 청크와 색인을 전략별로 재생성한다. 청크별 지표의 분모 변화·overlap 중복과 전달 문맥의 근거 누락을 구분한다. P015/P016 원문 준비와 P007/P008 실험 범위·검증은 각 카드에 따른다.

2026-10-23 문서 원천 결정: HR은 Google Drive 지정 폴더에 문서를 업로드/개정한다. P006의 로컬 파일은 해당 원천을 모사한 fixture snapshot/캐시다. 실제 폴더가 지정되기 전에는 외부 수집/업로드하지 않으며 실제 동기화와 권한/삭제 반영은 후속 계약으로 분리한다.

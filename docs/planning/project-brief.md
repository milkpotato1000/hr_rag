# HR RAG 에이전트 프로젝트 기획

HR 규정 문서에서 근거를 찾아 질문에 답하고, 근거가 부족하면 담당자에게 연결하는 에이전트를 만든다. 같은 문서와 평가 질문으로 검색 방식, 에이전트 흐름, 모델 서빙 설정을 비교하며 각 계층의 역할을 학습한다.

기획 출처는 사용자가 2026-10-22 지정한 [HR RAG 에이전트 설계 대화](https://chatgpt.com/share/6ad97a1c-ef84-83ee-bb65-982dda568ead)다. 대화에서 언급한 이전의 “프로젝트 B” 원기획은 공유 범위에 없으므로 그 내용은 추가로 가정하지 않는다. 아래 단계와 P001 세부 계약은 이 대화를 실행 가능한 작업으로 구체화한 것이다.

## 사용자 흐름

직원이 “생일 휴가 있나요?”라고 질문하면 관련 규정을 검색하고, 적용 조건과 시행일을 확인해 출처와 함께 답한다. 검색으로 답을 확인하지 못하면 제한된 재검색 후 답변 보류 또는 담당자 연결로 끝낸다. 문서가 없다는 이유로 제도가 없다고 단정하지 않는다.

학습자는 질문, 검색 결과, 도구 실행, 인용 근거, 최종 행동과 지연시간을 확인한다. 내부 추론 전문 대신 관찰 가능한 도구 요청과 결과, 짧은 판단 요약을 기록한다.

| --- | --- | --- |

| BM25 기준선 | P002의 고정 토큰화·BM25 검색과 P001 평가 연결 | P001 완료 |

| 검색 개선 | Dense + BM25 + RRF, 이후 BGE 계열 reranker 비교 | 기본 검색 결과 재현 및 reranker 선택 |

| Slack 연결 | 질문 응답, 담당자 연결, 사람의 답변 전달 | 워크스페이스·채널·담당자·권한·중복 처리 계약 확정 |
| 서빙 비교 | Ollama와 vLLM의 동일 조건 성능·도구 호출 비교 | 모델과 GPU 환경 확보, 비교 가능 조건 기록 |

P001~P005의 검색·생성·학습 화면 기준선은 완료됐다. 2026-10-23 요청에 따라 [P006 원문 추출/청킹 기준선](plans/P006.md)을 준비 완료로 등록하고 [P007 청킹/검색 실험](plans/P007.md), [P008 답변/UI 비교](plans/P008.md)를 후속 초안으로 작성했다. 기존 기준선을 보존하며 [학습 순서](naive-rag-roadmap.md)에 따라 진행한다. Hybrid·reranker·Agentic은 이후 별도 과제다.

## 큰 구현 단계와 세부 작업 위치

번호 폴더는 RAG 방식이 달라지는 큰 단위로 관리한다. 평가 기반·BM25·Dense·기본 답변 생성은 모두 `1. Naive RAG/` 안의 세부 작업이다. 여러 P카드가 같은 큰 단계에서 진행되며 위 개발 단계 표의 각 행을 별도 번호 폴더로 만들지 않는다.

후속 큰 단계에서 앞선 단계의 필요한 내용만 복사·선별한다. 사용자가 든 `4. Agentic RAG/`처럼 큰 분류로 나누며 중간 단계 제목·범위와 최종 번호는 후속 기획에서 정한다. [큰 단계별 폴더 규칙](../architecture/stage-layout.md)을 따른다. 현재 고정 청크 기반 E2E 기준선이 완료됐으며, 원문 추출과 청킹 실험을 같은 큰 단계 안에서 확장한다.

## 기술 구성 방향

| 계층 | 대화에서 제시된 방향 | 구체화할 사항 |
| --- | --- | --- |
| 애플리케이션 | Python, FastAPI, Slack | 첫 실행은 로컬 평가 CLI, 이후 API·메신저 연결 |
| 에이전트 | Python 직접 구현 후 필요 시 LangGraph | 재검색·도구 실행·종료를 애플리케이션이 관리 |
| 검색 | Qdrant, Dense, BM25, Hybrid RRF | 임베딩·청킹·토크나이저·필터 계약 |
| 재정렬 | BGE reranker | 모델 ID, 언어 적합성, 실행 환경 |
| 생성 모델 | Qwen3 | 크기, 가중치, 양자화, 라이선스, 컨텍스트 길이 |
| 서빙 | 로컬 Ollama, 후속 vLLM 비교 | API별 thinking·tool calling·streaming 지원을 구현 시 공식 문서로 검증 |
| 지식 원천 | 초기 합성 문서, 후속 Google Drive | 원본 권한·버전·삭제와 검색 인덱스의 일치 |

모델의 도구 호출 요청을 실제 실행하는 주체는 Python 에이전트다. 서빙 계층은 모델을 실행하고 응답을 반환하는 경계로 둔다. 상세 책임은 [아키텍처 방향](../architecture/system-design.md)을 따른다.

## 평가 방향

검색기 비교는 같은 corpus·청크·질문·정답을 사용해 Recall@5/10/20, Precision@K, MRR@K, nDCG@K와 지연시간을 비교한다. 관련성 정답이 없는 질문은 별도 집합으로 보류·에스컬레이션을 평가한다. MMR은 다양성 선택 실험으로 분리한다.

생성은 답변 정확성, 근거 충실성, 인용의 정확성, 보류 적절성을 평가한다. Agent는 도구 선택·인자 유효성·재검색 종료·실패 복구를 추가한다. 서빙은 TTFT, 출력 토큰 속도, 전체 지연, 처리량, GPU 메모리를 기록하며 하드웨어·가중치·양자화·프롬프트·길이·동시성을 함께 남긴다. 조건이 다르면 차이를 명시하고 엔진만의 효과로 단정하지 않는다.

품질 목표 수치는 기준선 측정 후 결정한다. P001의 통과 조건은 평가 계산과 데이터 일관성의 정확성이며, 검색·답변 성능이 이미 확보되었다는 뜻이 아니다.

## 데이터와 연동 경계

초기 문서는 가상의 규정과 질문만 사용한다. 공유 대화의 생일 휴가 예시는 실제 회사 정책으로 취급하지 않는다. 공개 GitHub에는 실제 직원 정보, 내부 HR 규정, 인증 정보를 올리지 않는다.

실제 Drive·Slack 접근, 외부 메시지 전송, 모델 다운로드, GPU 자원 생성과 배포는 이 기획 반영 작업에 포함하지 않는다. 해당 단계의 실제 대상과 실행 범위를 먼저 정한다.


## E2E 구현과 학습의 역할

사용자는 Codex가 구현·테스트·수정·실행까지 맡고 본인은 파이프라인 의미·평가·최적화 실험을 중심으로 학습하기를 요청했다. P003부터 필요한 로컬 공개 런타임·모델 다운로드와 격리 의존성 설치·loopback 실행을 해당 P계약에 명시해 진행한다. 초기 기획 반영 당시의 모델 다운로드 제외는 새 E2E 요청의 명시된 로컬 실행 범위를 막지 않는다. 유료 API·원격 GPU·실데이터·외부 메시지·배포는 별도 범위를 정한다.

청킹 전략 비교에서는 원문·질문·원문 fact/span 정답을 고정하고 청크와 색인을 전략별로 재생성한다. 청크별 지표의 분모 변화·overlap 중복과 전달 문맥의 근거 누락을 구분한다. P006~P008 범위와 검증은 각 카드에 따른다.

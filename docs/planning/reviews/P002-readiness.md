# P002 기획 준비 검토

검토일: 2026-10-22 (Asia/Seoul)
상태: 준비 완료, P001 완료 대기

## 요청과 현재 근거

사용자는 plan 채팅에서 “큐 올려주고 dev 전달해줘. 다음 플랜 잡아주고”라고 요청했다. AGENTS.md의 plan 준비 검토·dev 등록 위임과 프로젝트 기획의 기본 검색 방향 안에서 P002를 준비한다.

검토 시작 시 plan은 99ce84f32f5cff8db0a92165fae98706dfcda89b, dev의 채택 기록도 같은 SHA였다. 큐의 P001은 준비 완료·미착수였다. dev 채팅에 기존 P001 실행을 전달했으며 P002는 그 완료 이후의 작업으로 등록한다. dev의 미커밋 진척을 plan에 복사하거나 dev 구현 이력을 plan에 병합하지 않는다.

토큰화의 조사·띄어쓰기 민감성은 알려진 실험 제한이며 P002 실행을 막는 미결 업무 결정이 아니다. Dense와 BM25의 전체 비교는 P002 완료로 주장하지 않는다.

## 기술 출처 확인

2026-10-22 다음 1차 문서를 확인했다.

- [Apache Lucene 9.12.2 BM25Similarity](https://lucene.apache.org/core/9_12_2/core/org/apache/lucene/search/similarities/BM25Similarity.html): 양수 IDF와 기본 k1=1.2, b=0.75의 참고 근거. 프로젝트의 전체 점수 산식은 P002에서 별도로 고정한다.
- [Python unicodedata](https://docs.python.org/3.9/library/unicodedata.html): NFKC 처리와 Unicode DB 버전 노출.
- [Python re](https://docs.python.org/3.9/library/re.html): Unicode 문자열의 단어 문자 처리. 구체적인 밑줄 제외 패턴은 프로젝트 결정이다.

## 인계

P002는 준비 완료로 커밋·큐 등록하며 dev가 P001의 커밋된 완료를 확인한 뒤 수행한다. 전달 시 정확한 plan SHA, 이 검토와 P002 경로를 제공한다. dev는 안전한 시점에 plan을 통합·채택하고 기존 P001 실행 로그·증거·구현을 보존한다.

## 기획 검증 결과

- git diff --check: PASS. 공백 오류 없음.
- python3 scripts/work_queue.py --owner all --json: 정상 종료. P001=READY, P002=WAITING(선행 P001), dev 다음 작업=P001.
- plan_cards.parse / validate_execution: P001·P002 스키마와 실행 상태 PASS. 새 P002는 0/7, 실행 로그 없음.
- 변경 문서 3개의 로컬 Markdown 링크: 모두 실제 파일로 연결됨.
- 정규화·토큰화 예시: 계약의 네 토큰과 일치.
- 독립 산식 상수 확인: ln(1.6)=0.47000362924573563, 반복 tf 점수=0.6462549902128865, 휴가 점수=0.9808292530117262, 길이 보정 a=0.523548346501579 / b=0.5665797174469143.
- python3 scripts/contract_guard.py check: plan 브랜치이므로 dev 비교는 SKIP. 이 결과를 dev 채택 계약 검사 PASS로 해석하지 않음.
- 로컬 core.hooksPath=.githooks 확인. 커밋 시 pre-commit, push 시 pre-push를 그대로 실행한다.

이는 기획 문서 검증 결과이며 P002 제품 구현·테스트 통과 기록이 아니다. P002 실행 검증은 dev의 채택 후 docs/verification/p002/에 남긴다.


## 2026-10-22 단계별 폴더 요청에 따른 재검토

사용자는 각 단계마다 `1. 제목`, `2. 제목`, `3. 제목` 폴더를 만들고 앞선 단계에서 필요한 것을 복사·선별한 뒤 시작하도록 요청했다.

현재 dev 커밋 `60499ff`는 P001 완료·증거를 포함하고 기존 plan `9520156`을 채택했다. P002는 미착수(0/7)다. P001의 완료 계약·로그를 그대로 두고 P002에 1단계 보관과 2단계 독립 실행, 출처 manifest 및 C8을 추가한다. 개정 후 P002는 0/8이며 재채택이 필요하다. P001 구현 전체를 plan으로 병합하지 않는다.

- 최초 루트 P001 원본은 과거 계약 재현용으로 보존한다. 1단계의 여섯 파일은 P001 구현 커밋 `4225bb1d6b9bd017a06e81125c4fce9ed1d7f227`과 byte hash가 같아야 한다.
- 1단계를 먼저 커밋한 뒤 그 실제 커밋에서 2단계에 복사해 출처를 기록한다. 이후 각 단계가 단독 복사 상태에서 실행되는지 검증한다.
- 제품 상대 경로는 각 단계 안, 하네스·검증 증거는 루트 기준으로 구분한다. 구체 계약은 [폴더 규칙](../../architecture/stage-layout.md)과 개정 [P002](../plans/P002.md)에 기록했다.
- 새 외부 서비스·모델·자원·공개 대상을 추가하지 않는다. 구현 검증은 dev가 새 plan을 채택한 후 수행한다.

재검토 검증: git diff --check 정상, 변경 문서 5개의 로컬 링크 확인, P001·P002 카드 스키마와 실행 상태 검증 통과. P001 계약 원문은 직전 plan과 byte 일치한다. 큐는 커밋된 dev의 P001 DONE(6/6)을 유지하고 개정 P002 READY(0/8)와 새 기준 재채택 필요를 표시한다. plan의 contract_guard는 역할에 따라 SKIP이며 실제 단계 독립 실행 검증은 dev에서 수행한다.

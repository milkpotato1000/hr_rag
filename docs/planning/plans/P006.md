현재 15개 수작성 청크와 질문·기존 평가 증거는 기준선으로 보존한다. 새 원문은 과거 원본을 복원했다고 주장하지 않고, 이번에 작성한 가상 학습 원문 v2라고 명시한다. 사용자는 원문·청킹·검색·답변을 관찰하고 Codex가 구현·데이터 작성·실행·검증을 맡는다.

## Google Drive 문서 원천

사용자 시나리오는 HR 담당자가 Google Drive의 지정된 규정 폴더에 PDF 등을 올리고 개정본을 관리하는 것이다. 설명용 폴더 예시는 HR 규정/휴가·근태, 근무제도, 복지이며 실제 폴더가 생성됐다는 뜻은 아니다. 문서 이름이나 로컬 경로만으로 원본을 식별하지 않는다.

이번 구현에서는 실제 계정/폴더가 지정되지 않았으므로 source_mode=fixture인 Drive snapshot 어댑터로 가상 원문을 공급한다. 수집 계층은 문서 목록/메타데이터와 로컬 원본 경로를 공통 manifest로 제공하고, 이후 추출/청킹은 수집 방식에 의존하지 않는다. 실제 Google Drive 연결·업로드·정기 동기화는 이번 완료 범위가 아니다. 임의 사용자 Drive 자료를 찾거나 가져오지 않는다.

snapshot manifest에 source_provider=google_drive, source_mode=fixture, snapshot_id, folder_id, file_id, name, mime_type, source_modified_time, source_version(확인 불가 시 null), source_url, local_path, downloaded_content_sha256을 둔다. 기존 document_id/version/title/hash와 관계를 README에 명시한다. fixture ID는 fixture: 접두어, 시간은 합성 값으로 표시하고 source_url은 null로 둔다. 존재하지 않는 Drive URL이나 실제 다운로드 시각을 만들어내지 않는다. synthetic=true를 유지한다. 문서 버전과 원격 source_version은 별도 값이며 로컬 다운로드 바이트 hash가 처리 입력의 재현 기준이다.

source map은 snapshot/file_id→캐시 원본 hash→추출 페이지/offset→chunk_id를 연결한다. 새 파일을 업로드한 경우 새 file_id, 같은 파일의 이름 변경은 같은 file_id, 내용 변경은 다른 hash/snapshot으로 표현하는 fixture 검증을 포함한다. snapshot에 파일이 없다는 사실만으로 실제 삭제를 확정하지 않는다. 폴더 이동·삭제·권한 변경과 활성 색인 교체는 실제 동기화 후속 계약에서 정한다.

후속 실제 연결은 사용자가 지정한 폴더 범위만 읽고, 실제 file_id/원본 링크/수정 시각과 다운로드 hash를 채운다. PDF 등 업로드 파일은 다운로드, Google Docs 등 네이티브 문서는 별도의 export 형식/버전 계약이 필요하다. 파일별 접근 권한 보존·삭제/접근 취소·재색인 정책을 확정한 후 활성화한다. 현재 공개 저장소에는 가상 fixture만 포함한다.

## 범위와 입력

- Drive snapshot의 로컬 캐시에 있는 UTF-8 Markdown/TXT 및 텍스트 레이어가 있는 PDF를 지원한다. 초기 실습 자료는 기존 6개 HR 주제를 바탕으로 작성한 원문 문서 6개와 그중 최소 2개의 다중 페이지 PDF다. PDF와 Markdown이 동일 내용을 표현하면 같은 corpus에 둘 다 중복 수록하지 않고 manifest에서 대표 입력을 선택한다.
- 원문은 제목·문단·목록·예외 조건을 포함하고, 최소 한 문서에는 800자보다 긴 본문과 페이지 경계를 넘는 설명을 넣어 실제 분할을 관찰하게 한다. 과도한 반복으로 분량만 늘리지 않는다. 기존 질문에 대한 규정 의미는 출처 대조표로 확인하고, 추가 예시/설명은 가상 자료임을 명시한다.
- 입력 manifest는 document_id, version, title, 상대 원본 경로, SHA-256, 형식, synthetic=true와 작성 출처를 갖는다. 원본 파일은 입력에서 수정하지 않는다. 임의 디렉터리 재귀 수집 대신 명시 manifest만 처리한다.
- PDF 추출기는 pypdf를 사용하고 격리된 기존 Python 환경의 의존성 lock에 정확한 버전·hash를 기록한다. PDF fixture 생성/시각 확인에는 PDF 스킬과 이용 가능한 로컬 도구를 사용한다. 계정·클라우드 OCR·유료 API는 필요하지 않다.
- 이미지 전용 페이지는 추출 텍스트 없음/검토 필요를 표시한다. 이미지 존재+텍스트 없음은 OCR 필요 후보로, 이미지도 없는 페이지는 빈 페이지로 분류하되 자동 판단 한계를 기록한다. 자동 OCR과 복잡한 표·다단 레이아웃 복원은 이번 완료 범위가 아니다. 암호화·손상·미지원 입력은 명시 오류다. 누락 페이지를 정상 완료로 숨기지 않는다.
- 파일당 20 MiB·100페이지·정규화 문서당 100만 문자 제한은 초기 보호용 설정으로 명시하고 오류를 반환한다. PDF 추출은 별도 프로세스·타임아웃으로 실행해 오류나 과도한 처리 시 기존 결과를 보존한다. 이 제한들이 모든 PDF의 자원 사용을 보장하지는 않는다.

## 추출·청킹·출처 계약

1. `scripts/ingest_documents.py --manifest ... --output-dir ...`로 페이지별 추출 텍스트와 정규화 문서를 별도 저장한다. UTF-8, 줄바꿈 LF, Unicode NFC, 페이지 결합 구분자를 고정하고 정규화 버전·parser 버전을 기록한다. 내용 자체의 요약/재작성이나 예외 조건 삭제는 하지 않는다. PDF 독서 순서는 제공 fixture에 대해 직접 확인하며 일반 PDF 정확성으로 일반화하지 않는다.
2. 각 문서의 canonical text와 페이지 경계 offset을 저장한다. offset은 정규화 text의 Unicode code point 기준 [start,end)이며 PDF 바이트 위치가 아님을 명시한다. 원본 hash·페이지 번호·추출본 hash를 통해 원문까지 추적한다.
3. `scripts/chunk_documents.py --documents ... --method fixed --size-chars 400 --overlap-chars 80 --output-dir ...`를 제공한다. 이번 기준선은 문자 고정 길이이며 token chunking/semantic chunking으로 부르지 않는다. 400/80은 비교 시작값이고 최적값이나 모델 사양이 아니다.
4. 문서별 start=0에서 [start,min(start+size,length))를 생성하고, 마지막 청크에 도달하면 종료한다. 그 외에는 start+=size-overlap이다. 0<=overlap<size, size>0이며 bool·잘못된 타입·빈 입력을 거부한다. 문서 사이를 합치지 않는다. text는 canonical text의 정확한 slice이며 제목을 본문에 몰래 붙이지 않는다. 공백만 있는 범위는 명시 기록 후 생략한다.
5. `chunks.jsonl`은 기존 필수 7개 필드(chunk_id/document_id/version/title/text/source/synthetic)를 충족한다. source는 가상 자료의 synthetic:// URI이며 페이지·원문 범위를 추적할 수 있게 한다. 상세 source map은 sidecar로 저장해 기존 Qdrant payload 계약을 임의로 바꾸지 않는다.
6. 청크 ID는 문서/원문 hash·정규화 버전·방법·설정·offset 기반의 결정적 hash다. 같은 입력·설정은 같은 내용/ID/hash, 변경된 입력/설정은 다른 실행 ID다. 실행 manifest에 원문·추출·청크 hash, 알고리즘·설정·의존성 버전, 길이 분포·청크 수·겹친 문자 비율과 시간을 기록한다.
7. 출력은 새로운 디렉터리에만 원자적으로 게시한다. 실패 시 완료 manifest를 남기지 않으며 기존 corpus/index를 덮어쓰지 않는다. 원문 hash 불일치, 경로 탈출, 중복 document_id, 추출 누락, 잘못된 offset을 검출한다.

## 기존 RAG 연결과 평가 준비

- 기존 build_dense_index.py와 BM25 경로로 새 청크를 처리한다. 새 색인은 별도 .runtime 경로에 생성하고 기존 index-v1은 보존한다.
- rag.ask와 ask.py에 명시적 chunks 경로를 전달할 수 있게 최소 확장한다. 기존 기본값·명령·UI는 그대로 동작한다. 새 corpus와 맞지 않는 색인은 계속 거부한다. UI의 corpus 전환은 P008에서 구현한다.
- 원문 기반 질문/필수 근거 fact_id·document_id·원문 offset·정확 quote·의미 rubric을 별도 평가 파일에 준비한다. 기존 14개 질문은 새 원문과 대조해 사용하되 기존 chunk ID qrels를 복사하지 않는다. 정답 정보는 검색/생성 런타임 입력에 넣지 않는다.
- 한 사실이 여러 청크에 걸쳐 있을 수 있도록 하나의 fact에 하나 이상의 필수 span을 기록한다. 근거 없는 질문은 별도 표시한다. 원문 누락·조건 변경이 발견되면 원문을 고치거나 새 평가 버전에서 변경 사유를 명시한다.
- 실제 PDF 추출→fixed 청킹→실제 BGE 색인→질문 검색→실제 Qwen 답변까지 정상 질문과 근거 없는 질문으로 smoke를 수행한다. 검색/답변이 기대와 다르면 원인과 실제 결과를 남기며 품질 목표를 몰래 완화하지 않는다. 최소 근거 있는 답변 1개와 적절 보류 1개를 실제 확인한다. 정식 청킹 최적화는 P007/P008에서 한다.

## 검증과 인계

Drive fixture의 파일 추가/이름 변경/내용 변경과 안정된 file_id·snapshot/hash·source map 역추적, 원문 PDF 렌더링과 추출 텍스트 대조, 한글/숫자/부정·예외 조건 보존, 독립 작은 문자열의 예상 slice, 경계 length=size/size+1, overlap=0/size-1, 페이지 걸침, 마지막 중복 방지, source map 역추적, 결정성·설정 변경·stale index·입출력 실패를 검증한다. PDF 이미지 전용/빈 페이지/손상 입력은 실패 또는 검토 필요로 분리한다.

기존 회귀, 별도 원문 corpus 실제 E2E, 큰 단계 단독 복사와 재현 명령을 확인한다. docs/verification/p006/에 최초 실패·수정·최종 PASS, PDF 시각 확인, 원본 보존 hash와 실제 출력을 커밋한다. README/LEARNING_GUIDE에 새 경로와 “현재까지 fixed 문자 청킹만 구현”을 명시한다. 정답률이 향상됐다고 단정하지 않는다.

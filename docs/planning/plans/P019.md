## 목적과 완료 경계

P013의 실제 평가 실행을 승인하기 전에 필요한 **고정 평가 모델·호환성/예산 증거·사람이 읽을 정답/판정 검토 묶음**을 dev가 준비한다. P013의 승인 정답 조건을 없애거나 모델 답변을 사람 승인으로 승격하지 않는다. 이 카드의 완료는 검토 자료 준비이며 사람 승인이나 답변 평가기 제품 완성이 아니다.

구현 위치는 `evaluation/project_b/preparation/`와 `docs/verification/p019/`다. 작은 준비 CLI/JSON schema/읽기용 HTML 또는 Markdown 보고서로 제한한다. 기존 Naive/청킹 UI·색인·P007/P017 산출물은 바꾸지 않는다. evaluation 모듈의 실제 scoring/서빙/UI는 P013/P008에서 구현한다. plan은 계획·검토만 하며 dev가 정확 채택 후 구현한다.

## 모델 설치와 자원 한도

기존 Ollama0.40.8·qwen3:4b·bge-m3:567m 및 각 digest는 보존한다. 평가 후보는 공식 `qwen3:8b` Q4_K_M, manifest SHA `500a1f067a9f782620b40bee6f7b0c89e17ae61f686b92c24933e4ca4b2b8b41`, model layer `a3de86cd1c132c822487ededd47a324c50491393e6565cd14bafa40d0b8e686f` (5,225,374,496 bytes), Apache-2.0다. 설치 직전 공식 manifest와 일치 확인 후 이 모델 한 개만 로컬 Ollama 캐시에 내려받을 수 있다. 태그가 바뀌면 임의 다른 버전으로 진행하지 않는다. global skill/모델 서버/시스템 설정을 교체하지 않는다.

- 다운로드 총6GiB/30분 상한, 시작 시 가용 디스크12GiB 이상. 초과/실패 시 기존 모델을 지우거나 상한을 확대하지 않는다. 가중치는 repo에 복사·커밋하지 않는다.
- 모델 실행은 직렬1개, 로컬 loopback11434만 사용한다. 다른 실제 모델 작업이 있으면 기다리거나 상태를 보고한다. 서버를 재시작하거나 타 사용자 실행을 종료하지 않는다. 기존 P007/P017 ledger는 읽기/보존하고 P019 별도 ledger를 둔다.
- request: stream=false, think=false, temperature0, seed42, num_ctx8192, num_predict1024, keep_alive=0. 요청 timeout120초, 동일 payload 최대2시도, 전체 **34회**/모델wall45분. 재시작·실패·재시도도 ledger에 누적한다. prompt/schema 수정 후 새 요청도 전체 한도에 포함한다. timeout 후 서버 종료를 확인하지 못하면 다음 호출을 자동 시작하지 않는다.
- 계획: 역할 smoke6종×최대2=12회, 첫 성공 payload 동일조건 반복6회(재시도 없음), 질문8개 정답 초안×최대2=16회. 합계34. 금액 미명시 후보2개는 전체 원문/정책 목록 검토로 작성하며 모델에 빈 근거를 넣어 승인시키지 않는다.
- 정확 모델/template/tokenizer/params/license hash를 lock에 보존한다. 설치한8B의 metadata에서 byte-BPE와 단일user template를 확인한 뒤 `UTF8(user content)+UTF8(full template)+UTF8(schema)+64+1024 <=8192`라는 보수 상한을 모든 요청 전에 적용한다. 전제 검증이 불가하면 입력 안전성 미확인으로 실패 처리한다. model context 사양과 실행8192 설정을 구분한다.
- 요청 body는 단일user, instruction/schema와 source를 명확히 구분하고 문서 내 지시는 데이터로만 다룬다. 전체 지정 원문 span을 유지한다. 한도 초과면 무음 자르기·임의 근거 제거·num_ctx 확대 없이 그 사례를 보류하고 plan에 입력 예산 재검토 근거를 남긴다.

## 역할 smoke와 출력 규칙

6종은 원자 주장 추출, entailment, neutral, contradiction 검증 각각1, 의미 동등 매칭1, 근거부 정답 초안1이다. 숫자/부정/조건을 포함하는 짧은 한국어 fixture와 기대 라벨을 dev가 호출 전에 고정·커밋하거나 immutable manifest로 동결한다. 형식 성공과 의미 정확도를 별도 보고한다. 튜닝을 위한 반복 질문 변경으로 성공만 남기지 않는다.

출력은 extra fields 금지 JSON schema로 제한한다. claim은 원문/답변 quote 및 입력 unit ID를 반환하고 Python이 정확 quote 검색/유일성·범위를 검증하여 offsets를 계산한다. 무근거 주장·존재하지 않는 ID·불일치/중복 quote·숫자/부정 누락은 오류 또는 명시 수정대상이다. 해설은 짧은 근거 설명만 저장하며 숨은 사고 과정 출력은 요구하지 않는다. raw content/응답 사용량/시간/실패/변경 전후는 보존한다.

같은 성공 payload 반복의 출력/라벨 일치율과 실제 지연/메모리(측정 방식 포함)를 기록한다. 6개 smoke의 정확도가 일반 한국어 HR 성능이나 독립 평가기 검증 완료를 뜻하지 않는다. 8B가 실행 불가하거나 의미 품질이 부족하면 실패와 후속 검토안을 남기고4B로 자동 대체해 성공을 주장하지 않는다.

## 사람 검토 묶음

- 질문10개 각각: 질문 → 초안 답변 → 원자 claim별 source quote·페이지·조항·offset → 검토 상태/수정사항. 원문의 조건·예외를 보존한다. 최대8 reference claims/질문; 더 필요하면 복합 주장을 억지로 합치지 않고 추가 검토로 남긴다.
- 정답은 모델 원응답 초안과 Codex 원문 대조 수정본을 구분해 저장한다. 모든 항목은 `draft` 또는 `needs_revision`이며 reviewer는 `Codex`, human approval은 null이다. 검증된 초안이라도 approved가 아니다.
- gt09/gt10은 규정집 전체 및 policy inventory 대조 범위를 기록하고 “이 문서에 지원 금액이 명시되지 않음”으로만 작성한다. 실제 회사에서 지원하지 않는다는 단정은 금지한다. absence를 존재하지 않는 원문 span으로 꾸미지 않는다.
- 별도 평가기 검토 후보18개: 숫자/부정/조건·예외/기한/다중 근거/근거 없음 6유형×E/N/C. premise·claim·제안 라벨·짧은 이유를 제시한다. label은 사람 미승인 proposal로 유지한다. 원문과 다른 통제된 synthetic premise는 사실 규정이 아니라 fixture임을 명시한다. 필요 시 E/N/C 생성이 부자연스러운 유형은 의미 있는 사례로 구성하고 정확 분포/근거를 기록한다.
- 동일 정답·판정 패킷의 JSON/읽기 보고서에 전체 hash와 항목 ID를 표시한다. 현재 앱에서 파일을 열어 확인할 수 있고, 승인/수정 요청은 실제 사용자의 명시 응답을 기다린다. 버튼/CLI를 실행했다는 이유만으로 사람 승인을 만들어내지 않는다. 이 카드에는 승인을 대신할 기능을 넣지 않는다.

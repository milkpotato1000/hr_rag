## 목적

P001의 고정 합성 corpus와 관련성 정답을 그대로 사용해 질문에서 검색 순위를 만들고 같은 평가기로 측정한다. 수작업 순위 입력 이후의 첫 검색 기준선이다. Dense 비교에 앞서 BM25의 계산·토큰화·빈 결과·재현성 계약을 고정한다.

## 기획 준비

[프로젝트 기획](../project-brief.md)의 기본 검색 단계를 BM25 기준선과 후속 Dense 비교로 나눈다. 모델·토크나이저 패키지·Qdrant 실행 환경을 선택하지 않아도 독립적으로 검증할 수 있는 부분을 먼저 등록한다. [준비 검토](../reviews/P002-readiness.md)에 근거와 잔여 경계를 기록했다.

P001이 커밋된 증거와 함께 완료된 후 착수한다. P001의 corpus·질문·관련성 정답과 평가 정의를 변경하지 않는다. 검색 품질이 낮아도 데이터나 정답을 유리하게 수정하지 않고 그대로 보고한다. 준비 완료는 검색 품질 확보를 뜻하지 않는다.

## 범위와 계약

완료 P001 구현 커밋 `4225bb1d6b9bd017a06e81125c4fce9ed1d7f227`의 여섯 제품 파일(평가기·테스트·합성 데이터 네 파일)을 `1. Naive RAG/`에 확보하고 최초 복사 hash·출처 manifest와 단계 README를 남긴다. 이후 같은 폴더에 BM25 코드·테스트·안내를 작성한다. P001 corpus·질문의 최종 hash와 평가 의미·회귀는 보존하며 같은 큰 단계 코드의 리팩터링은 아래 계약 범위에서 허용한다.

직전 세부 폴더 지시에 따라 작성한 `1. 검색 평가 기반/`·`2. BM25 검색 기준선/` 작업은 새 큰 단계 폴더로 옮겨 보존한 뒤 잘못 만든 경로를 정리한다. 두 개의 별도 큰 단계나 중간 보관 커밋을 만들 의무는 없다. 원래 루트의 완료 P001 계약·제품 파일·기존 증거는 과거 재현용으로 보존하며 후속 기능은 새 큰 단계에만 추가한다. 기존 실행 로그에 정정·영향을 추가하고 과거 로그는 지우지 않는다.

아래 제품 scripts/data/tests 상대 경로와 CLI·전체 테스트 명령은 `1. Naive RAG/` 내부 기준이다. 하네스 검사·큐 및 docs/verification/p002/는 저장소 루트 기준이다. 루트 README는 새 실행 위치를 안내한다. dev는 이 정정이 포함된 정확한 plan SHA를 다시 채택한다.

### 실행과 데이터 경계

Python 3.9 이상과 표준 라이브러리만 사용한다. 새 검색 코드·테스트·사용 안내·검증 증거를 dev가 작성한다. P001 평가기와 입력 검증은 공개된 CLI 또는 내부 모듈로 재사용하며, 공유 모듈 추출은 기존 CLI·출력 의미와 회귀를 유지하는 범위에서 허용한다.

모델 다운로드, 의존 패키지 설치, 네트워크, 실제 HR 문서, Qdrant·Dense·RRF·reranker·생성·API·Drive·Slack은 이 카드의 실행 범위에 포함하지 않는다. 후속 Dense 단계는 모델 ID·revision·라이선스·실행 환경·다운로드 범위를 정한 별도 P카드로 준비한다.

CLI 계약(저장소 루트에서 시작):

```sh
cd '1. Naive RAG'
python3 scripts/run_bm25_baseline.py \
  --chunks data/synthetic/chunks.jsonl \
  --queries data/synthetic/queries.jsonl \
  --top-k 20 --k 5 10 20 \
  --output-dir <새 결과 디렉터리>
```

모든 인자는 명시 가능하고, top-k 기본값은 20, k 기본값은 5 10 20이다. top-k는 양의 정수, K는 P001의 양의 고유 정수 정책을 따르며 top-k는 max(K) 이상이어야 한다. 잘못된 숫자·중복 K·음수·0·부족한 top-k를 거부한다. 라이브러리 경계를 제공하면 불리언을 정수로 허용하지 않는다.

입력 스키마·중복·참조·근거 없음 검증은 P001 계약을 유지한다. 검색기는 corpus의 title·text와 질문의 question만 사용한다. query_id는 결과 연결에만 쓴다. relevance·answerability는 평가에만 사용하며 순위·점수·검색 필터에 영향을 주지 않는다.

### 토큰화와 BM25 산식

토큰화 버전은 `unicode-word-v1`이다. 문서별 입력은 title + LF 1개 + text이며, 질문 입력은 question이다. 각 문자열에 순서대로 NFKC 정규화 → casefold → Python Unicode 모드의 `re.findall(r"[^\W_]+", value)`를 적용한다. 숫자를 유지하고 밑줄·구두점은 구분자로 취급한다. stopword 제거·조사 제거·어간화·형태소 분석·동의어·n-gram·제목 가중치는 없다.

예를 들어 “생일 휴가 ＨＲ_2026!”의 결과는 ["생일", "휴가", "hr", "2026"]이다. “휴가”와 “휴가는”은 다른 토큰이다. 이 차이는 한국어 품질 제한으로 기록하고 런타임에 임의 규칙을 추가하지 않는다.

검색 단위는 chunk이며 같은 document_id의 여러 chunk도 각각 하나로 센다. N은 빈 토큰 chunk를 포함한 전체 chunk 수, df(t)는 t를 한 번 이상 가진 chunk 수, tf(t,d)는 d에서 t의 빈도, dl은 토큰 수, avgdl은 전체 dl 합 / N이다. k1=1.2, b=0.75로 고정한다.

- idf(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
- score(q,d) = Σ idf(t) × tf(t,d) × (k1 + 1) / (tf(t,d) + k1 × (1 - b + b × dl / avgdl))
- 합산 대상은 질문의 중복을 제거한 토큰 중 d에 존재하는 토큰이며 토큰 문자열 오름차순으로 합산한다. 질문 내 같은 토큰을 반복해도 점수가 변하지 않는다.
- 질문 토큰이 비거나 avgdl=0이면 모든 결과가 빈 목록이다. 미등록 토큰은 기여하지 않는다. 0점 chunk를 임의로 채우지 않는다.
- 양수 점수만 점수 내림차순, 정확한 동점은 chunk_id의 Python 문자열 오름차순으로 정렬해 top-k까지 반환한다. 정렬 전에 점수를 반올림하지 않는다.

위 산식은 이 프로젝트의 명시적 BM25 변형이다. 양수 IDF 및 기본 k1·b는 [Apache Lucene BM25 API](https://lucene.apache.org/core/9_12_2/core/org/apache/lucene/search/similarities/BM25Similarity.html)를 참고했으며 Lucene의 내부 norm·부동소수점 처리까지 동일하다고 주장하지 않는다. 정규화와 정규식은 [Python unicodedata](https://docs.python.org/3.9/library/unicodedata.html), [Python re](https://docs.python.org/3.9/library/re.html)를 따른다.

### 결과와 실패 정책

정상 실행은 output-dir에 다음 네 파일을 생성한다. JSON·JSONL은 UTF-8이며 NaN·Infinity를 쓰지 않는다.

1. rankings.jsonl: P001이 바로 받을 수 있는 query_id·chunk_ids만의 행. 모든 질문을 정확히 한 번 포함하며 query_id 문자열 오름차순으로 기록한다. 빈 결과도 행을 남긴다.
2. scores.jsonl: 같은 질문·순서로 query_id, query_tokens(중복 제거·문자열 정렬), results 목록을 기록한다. results의 각 원소는 chunk_id·score이며 rankings와 순서·개수가 일치한다.
3. metrics.json: P001 평가기를 그대로 실행한 결과. K·분모·null·짧은 순위 처리·hash·평가기 버전 계약을 유지한다. 별도 지표 구현을 만들지 않는다.
4. run.json: 검색기 버전, tokenizer ID와 처리 순서·패턴, k1·b·top-k·K, Python 버전·Unicode DB 버전·platform, corpus·질문·생성 rankings의 SHA-256, N·avgdl을 기록한다. 관측치는 observations에 분리해 색인 준비 시간과 query별 검색 시간(밀리초, 유한한 0 이상)을 기록한다.

시간 측정은 perf_counter로 한다. 색인 준비는 입력 검증 후 corpus 토큰화·통계 구축, query별 시간은 질문 토큰화부터 top-k 선택까지이며 파일 읽기·결과 쓰기·평가 시간은 제외한다. 단일 실행 지연은 관측값이며 엔진 간 성능 우열로 해석하지 않는다.

같은 입력·설정·Python/Unicode 환경에서 rankings·scores·metrics는 반복 실행 간 동일해야 한다. run.json의 observations 이외 필드도 동일해야 한다. 입력 행 순서를 바꿔도 검색 점수·결과 순서는 동일하며, 원본 파일 hash는 바뀔 수 있다. 실행 환경이 다르면 메타데이터를 확인한 뒤 비교한다.

output-dir의 부모 디렉터리는 존재해야 하며 output-dir은 존재하지 않아야 한다. 파일·디렉터리·심볼릭 링크 등 이미 있는 경로는 덮어쓰지 않고 stderr와 nonzero exit로 실패한다. 입력·인자·평가·출력 실패에는 최종 결과 디렉터리를 남기지 않고 기존 파일을 보존한다. 새 임시 디렉터리에서 생성·평가를 완료한 뒤 게시하고 실패 시 이번 실행의 임시 파일을 정리한다. 사용자 입력이나 기존 결과를 삭제하지 않는다.

## 검증 계획

`1. Naive RAG/`에서 `python3 -m unittest discover -s tests -v`로 가져온 P001 평가 회귀와 P002를 함께 검증한다. 기존 루트 P001 회귀도 별도 실행한다. 큰 단계 폴더 하나를 저장소 밖 임시 경로에 단독 복사한 후 테스트·대표 CLI를 실행하고 corpus·질문 원본 hash 보존을 검증한다. manifest의 최초 복사 출처 커밋·경로·hash는 git show의 실제 원본과 대조한다. 잘못 만든 세부 단계 경로에 고유 작업이 남거나 실행이 의존하지 않는지 확인한다. 검색 구현 함수를 호출해 기대 점수를 만들지 않고 아래 독립 fixture의 식 또는 미리 산출한 상수와 절대 오차 1e-12 이내로 비교한다.

- 같은 길이 fixture: a=(title "생일", text "휴가"), b=("생일", "생일"), c=("연차", "안내"). N=3, 각 dl=2, 생일 df=2이므로 idf=ln(1.6). 질문 "생일"의 a 점수는 ln(1.6), b 점수는 ln(1.6)×4.4/3.2, 순위는 [b,a]다. "휴가"는 a만 반환하고 점수는 ln(8/3)이다. "생일 생일"은 "생일"과 같다.
- 길이 정규화 fixture: 위 b의 text만 "생일 안내 안내"로 바꾸면 dl=[2,4,2], avgdl=8/3이다. 질문 "생일"의 a 점수는 ln(1.6)×2.2/1.975, b 점수는 ln(1.6)×4.4/3.65다. 상수 tf 순위 구현이나 길이 무시를 이 fixture로 검출한다.
- 동일 title·text를 가진 서로 다른 chunk의 동점은 ID 순서로 결정한다. corpus·질문 입력 순서를 섞고 반복 실행해 순위와 점수를 비교한다.
- NFKC·대소문자·숫자·밑줄·한국어 조사 차이, 질문 중복 토큰, 빈 토큰 질문, OOV, 개별 빈 토큰 chunk, corpus 전체 빈 토큰, top-k보다 적은 양수 결과를 검사한다. 빈 토큰 fixture도 P001의 비어 있지 않은 title·text를 만족하게 구두점을 사용한다.
- P001 스키마를 만족하는 상태에서 relevance와 answerability만 바꾸면 검색 순위·점수가 같고 평가·질문 hash만 영향을 받는지 검사한다. 검색에 정답이 유입되지 않음을 확인한다.
- 생성 rankings를 P001 CLI로 다시 평가해 metrics.json과 일치하는지 비교한다. P001의 기존 독립 기대값과 오류 테스트도 유지한다.
- 잘못된 JSON·중복 ID·타입·관련성 참조, 잘못된 옵션, 기존 결과 경로와 output 부모 부재, 평가/쓰기 실패를 검사해 stderr·nonzero exit·기존 파일 보존·최종 결과 미생성을 확인한다. 결정적인 실패 주입으로 재현하며 OS 권한만으로 실패를 가정하지 않는다.
- run.json의 입력·rankings hash를 파일 바이트에서 독립적으로 다시 계산하고, 환경·통계·시간 필드를 확인한다.

P001 corpus의 실제 baseline 실행 결과 네 파일, 전체 테스트 명령·출력, 실패·수정·재검증 기록, 재현 안내를 `docs/verification/p002/`에 커밋한다. 최초 실패 기록을 지우지 않는다. 결과 요약에는 관측한 검색 지표, 근거 없음 질문의 검색/빈 결과 비율, 가능한 경우 누락·혼동 사례 최대 3개와 실제 청크 근거를 남긴다. 실패가 없으면 없다고 적고 사례를 발명하지 않는다. 숫자를 답변 정확도·보류 정확도 또는 일반 한국어 검색 품질로 해석하지 않는다.

최소 Recall 등 제품 품질 합격선은 두지 않는다. 이 카드의 통과 기준은 계산·데이터 경계·재현성·평가 연결의 정확성이다. Dense 비교 전까지 이 측정값은 소규모 합성 corpus 기준선이다.

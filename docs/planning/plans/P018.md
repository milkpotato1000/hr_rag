# P018 — 정식 하네스 기준 업데이트와 plan/dev 역할·직접 인계 정비

> 준비: 준비 완료
> 실행: 진행 중
> 우선순위: 66
> 선행: P017
> 승인 근거: 2026-10-30 사용자 하네스 최신 버전 확인·업데이트 및 “계획은 plan 구현은 dev” 요청. 메인 plan의 확인 질문에 사용자가 “P018 확정 후 dev에 전달·착수”로 직접 승인. docs/planning/reviews/P018-readiness.md의 릴리스·차이·역할 검토에 따라 등록.

## 목적과 기준 버전

HR RAG 프로젝트의 legacy 하네스를 공개 **v0.1.0** 기준에 맞추고, 기존 제품 계약과 실행 이력을 보존한다. 정식 릴리스는 `https://github.com/milkpotato1000/plan-dev-harness/releases/tag/v0.1.0`, peeled commit `803d658a8c61dc6aa007645a98d4160b16746faa`다. 2026-10-30 확인한 개발 브랜치 `6b77a5d6cc10b3345a510c50bdff88336998de8c`의 0.2.0 Unreleased는 설치 대상으로 삼지 않는다. 작업 중 새 릴리스가 생겨도 이 계약의 버전을 조용히 바꾸지 않는다.

[소스 비교](../reviews/p018/source-comparison.json)는 현재 파일/릴리스 hash와 기존 미커밋 네 파일의 보존 기준이다. 이는 설치 소유권 manifest가 아니다. 현재 `.harness/installation.json`이 없으며 `install_harness.py --upgrade` 미리보기는 기존 변경 파일 충돌로 쓰기 전에 거부됐다. `--apply` 강행·manifest 위조·훅 우회·보호 경로 해제는 금지한다.

## 범위와 역할

**plan**은 P카드/요구/범위/준비 검토, AGENTS·CLAUDE·workspace 진입 규칙·인계 절차·보호 정책을 소유한다. **dev**는 실제 업데이트 제안 작성, 실행/검증, 로컬 적용, adoption, 증거와 완료 기록을 담당한다. 일반적인 “계획 후 진행/작업 시작/이어가자”는 같은 plan 채팅의 dev 역할 전환 허가가 아니다. 기존 별도 dev 채팅을 사용한다.

이 프로젝트는 런타임 하네스 스크립트와 테스트도 보호 중이므로 dev가 직접 수정하면 guard와 충돌한다. 다음 두 단계로 처리하며 보호 규칙을 약화하지 않는다.

### S1 — dev의 변경안·검증

1. 이 READY 계획의 정확한 SHA를 통합·adopt·커밋하고 guard/큐를 확인한다. P017 결과·기존 미커밋 작업·실패 로그를 보존한다.
2. 실제 업데이트 후보는 `scripts/plan_cards.py`, `scripts/plan_intake.py`의 ISO timestamp 끝 `Z`를 `+00:00`으로 정규화하는 릴리스 수정 각 1곳이다. 릴리스 파일과 hash를 확인하여 **임시 복사본**에 적용하고, 제안 diff/후보 hash/검증 결과를 `docs/feedback/dev/p018/` 및 `docs/verification/p018/`에 작성·커밋한다. 실사용 보호 파일은 이 단계에서 수정하지 않는다.
3. 릴리스와 동일한 guard/queue/hooks/template은 유지한다. intake 문서의 HR 전용 `/tmp/hr-rag-request.txt` 예시는 보존한다. 설치·배포 도구 전체나 upstream `.harness/policy.json`을 그대로 덮어쓰지 않는다.
4. 의미 있는 검증은 현재 HR intake 회귀, Z 및 +09:00 입력 성공·무시간대 거부, P카드 append-only/최신 PASS/허위 완료 거부, dev 보호 파일 변경 거부, 정확 adoption, 큐의 dev 완료 표시다. 테스트는 disposable Git fixture에서 수행한다. 기존 제품/모델/서버는 실행·재시작하지 않는다.
5. 보호 테스트 추가가 필요하면 같은 제안 경로에 작성하고 plan 검토 대상에 포함한다. unprotected 경로의 단순 테스트·증거 작성은 가능하다. 사용 중인 HR 훅은 절대 끄지 않으며 fixture 초기 bootstrap과 실제 프로젝트 훅 우회를 구분한다.

### S2 — plan 배포 후 dev 적용·최종 검증

1. plan은 커밋된 제안·실패/최종 PASS를 읽고 고정 릴리스와 byte/diff를 대조한다. 승인된 보호 파일/테스트만 plan에 **검토된 배포본으로 반영·커밋**한다. plan이 대신 개발·모델 실행을 하거나 dev 이력 전체를 병합하지 않는다. 제안에 새 의미/범위가 있으면 별도 검토한다.
2. plan은 그 정확한 후속 SHA를 기존 dev에 직접 전달한다. 이번 사용자 승인에는 P018의 S1→검토→S2 인계가 포함되며 같은 범위에 재승인을 요구하지 않는다. dev는 후속 SHA를 통합·adopt하고 검증한다. S1 adoption만으로 업데이트 완료라 하지 않는다.
3. `docs/process/workspace-AGENTS.md`의 확정 내용을 외부 workspace의 `AGENTS.md`로 동기화하고, 프로젝트 로컬 `CLAUDE.md`의 AGENTS import를 확인한다. 로컬 진입점은 Git 외부이며 원격 push에 포함되지 않는다고 기록한다. 기존 로컬 전용 지시가 추가돼 있으면 보존·통합한다.
4. 최종 출처/적용 파일 hash/보존한 커스텀 차이/검증 commit을 dev 증거에 기록한다. legacy manual integration임을 명시하고 installer-managed 설치나 개인 스킬 업데이트로 표기하지 않는다.
5. guard worktree/index/HEAD, 실행 가능한 기존 훅/core.hooksPath, 정확 adoption, 큐/기존 완료 카드·로그, plan/dev 정상 push를 확인한다. 공용 hooksPath를 새 방식으로 변경하거나 main을 승격하지 않는다.

## 그라운드 룰과 전달 기록

[직접 인계 규칙](../../process/direct-handoff.md)을 적용한다. plan READY+commit은 준비 상태이고, 실제 전송 성공·수신·adoption·구현 완료는 각각 별도 증거다. 사용자의 이번 HR RAG plan→기존 dev 전달·착수 지시는 같은 P018 후속 인계에 사용한다. 다른 프로젝트·새 채팅 생성·역방향 자동 답신·모든 미래 작업의 무조건 실행으로 확대하지 않는다.

v0.1.0에는 자동 전송 CLI가 없다. 프로젝트 문서 규칙과 호스트 메시징 도구로 처리하고, `workflow_control.py` 등 미출시 0.2.0 런타임을 몰래 가져오지 않는다. 전달 기록은 plan의 `docs/planning/handoffs/`에 사람이 읽을 수 있는 문서로 남긴다. 원격 공개 문서에는 채팅 별칭을 쓰고 raw 대화/개인 경로/내부 채팅 ID는 기록하지 않는다. 수신 확인은 호스트 read/wait 관찰로 가능하며 dev의 역발송을 요구하지 않는다.

## 보존 및 제외

- 기존 P001~P017 요구·완료 체크·실행 로그·P007 공식 실험·P017 사용자 실험·Naive·원문·모델 ledger는 변경하지 않는다. P013/P014 구현·실험, 하네스 프로젝트 P002, 글로벌 Codex/Claude 스킬, Git 원격·권한·main은 제외한다.
- plan의 기존 네 미커밋 평가 문서 변경은 내용과 hash를 보존하고 이 P의 커밋에 섞지 않는다.
- `.harness/policy.json`의 기존 보호 경로를 유지하고 `CLAUDE.md`와 `.harness/installation.json`을 추가 보호한다. adoption 파일은 dev 소유로 유지한다. 없는 installer manifest를 생성하지 않는다.
- 사람 승인이 필요한 미결정/명시 중지/실패를 숨기지 않는다. 새 중지 지시가 오면 해당 범위의 발송·실행을 멈춘다. 이번 등록은 다른 작업의 중지를 해제하지 않는다.

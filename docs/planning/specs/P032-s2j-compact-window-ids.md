# P032 S2j · 청킹 요청의 구간 번호 실험

## 준비 검토

S2i 첫 창은 원문 762자, 단위 20개였다. 입력 2,171토큰, 출력 4,096토큰에서 잘려 경계를 얻지 못했다. 저장된 사용자 메시지에서 긴 단위 ID만 창 안의 문자열 번호 1~20으로 치환하면 UTF-8 크기는 3,963바이트에서 2,674바이트로 줄어든다. 이는 사용자 메시지의 크기 차이다. 추론 토큰 수와 출력 잘림의 원인은 이 측정만으로 결정할 수 없다.

## 실행 범위

1. S2i 종료 기록을 커밋한 뒤 정확 채택한다. LLM 청킹에서 선택 가능한 번호 표현을 추가한다. 각 창에서 원래 순서대로 문자열 번호를 부여해 모델에 보여 주고, 같은 창에서 받은 끝 번호를 실제 단위 ID로 복원한다. 원문·위치·순서와 전체 문서의 영속 ID는 보존한다. 누락·범위 밖·중복·역순·잘못된 자료형을 암묵적으로 고치지 않는다.
2. 제품 preflight, 실제 build, 저장 결과 읽기와 재검증에서 같은 버전·매핑을 사용한다. 기존 설정과 저장된 이전 버전은 기존 긴 ID로 요청을 재구성한다. 버전이나 설정 변경은 요청·실험 식별자에 반영한다. 표시 번호와 영속 ID가 혼동되지 않게 학습 보고서에 함께 표시한다.
3. 모델 없이 이전 버전 재생, 두 창에서 같은 번호의 서로 다른 실제 ID 매핑, 경계 유효성·192자 제한·원문 피복, 여러 창 전체 빌드, 오류 후 중단을 검사한다. 제품 경로에서 재현된 w000에 대해 사용자 메시지의 id 값 이외 필드, 원문, 모델 digest, 설정, 출력 상한, 시스템 지시가 S2i와 동일한지 비교하고 새 설치·입력·실행 제어를 커밋한다.
4. S2i와 격리된 새 실행에서 같은 첫 창만 로컬 4B로 한 번 호출한다. S2i의 단일 호출·자동 재시도 0·HTTP 480초·watchdog 510초·전체 12분·RSS 8GiB·소유권과 정리 기준을 유지한다. 토큰·시간·메모리, 유효한 끝 번호·원문 구간, 의미상 경계를 이전 결과와 대조한다. 실패는 그대로 기록하고 나머지 33개 창을 호출하지 않는다. 검색 인덱스와 답변의 변경, Drive·평가기는 이번 실행 범위 밖이다.
5. 보고서를 학습 목차에 연결하고 dev 결과를 정상 push한다. 첫 창의 통과만으로 전체 청킹이나 검색 품질을 판정하지 않는다.

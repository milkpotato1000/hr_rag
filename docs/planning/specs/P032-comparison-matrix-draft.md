# P032 비교 행렬과 작업량 초안

2026-11-28 DRAFT. 실행 승인/인계가 아니며 P031 최종 도구 및 준비 검토 후 확정한다. [실사용 설계](P032-live-rag-validation-design.md)의 모든 선택 축을 유지하되 무제한 Cartesian product를 만들지 않는다.

## 공통 입력

고정23쪽 규정집의 새 generic snapshot과 기존10개 질문을 사용한다. 원문 fact/span과 청크 qrels를 별도로 준비한다. 첫 기준선은 fixed size256/overlap64, candidate_k20, final K5, context budget2000문자, RRF60 후보로 둔다. 수치는 품질 최적값이 아니라 통제 실험 시작값이다. 각 입력의 실제 tokenizer 길이를 확인하며512토큰을 넘는 청크/질문·쌍을 조용히 자르지 않는다. 실패 시 원본 설정 결과를 보존하고 바뀐 설정은 새 실험으로 분리한다.

첫 smoke는 gt01/gt02, 전체 결과는 gt01~gt10이다. 전체10개 실행은 smoke 출력·자원·출처 검사 이후에만 수행한다. 같은 결과를 재사용할 수 있으면 중복 호출 대신 artifact identity를 기록한다. 재사용 불가능하면 별도 요청으로 집계하고 총량을 다시 확인한다. 현재 표는 성공 경로의 업무 수이며 metadata/제어 요청과 실패 시 작업량은 별도다.

의미 경계용 unit embedding은 완성 청크 색인과 별도1개 작업이며 단위 수·문자·토큰·실제 SDK를 기록한다. LLM 경계는 단일 규정집이라도 여러 window를 처리하므로1회로 세지 않는다. P007의35window는 과거 구현의 관찰값이며 새 P030 window 수는 실제 preview에서 다시 산출한다. window 상한은 현재 계약의64 이내이며 모델 출력 retry0이다. 두 번의 경계 실행으로 품질 안정성을 검증하지 않은 결과를 재현성 검증으로 부르지 않는다. 저장 경계 replay의 동일성과 실제 LLM 재호출의 변동성은 다르다.

smoke를 전체 실행의 일부로 재사용하지 못할 경우 추가 workload를 계획 manifest에 명시한다. 모델 전환·worker startup·색인 재사용·원문 파싱·토큰 확인 시간을 서로 분리한다. cold worker 결과를 warm server 처리량처럼 해석하지 않는다. 위 수는 실제 실행 상한의 최종 승인이 아니며, 누적 상한/전체 deadline/중단 기준과 선택 profile을 READY에서 확정한다.

## 파일과 자원 준비

네 pinned recipe 원본 합은5,572,099,173bytes다. 원본+export를 모두 보존하고 가장 큰 모델의 임시 사본 및1GiB 여유를 더한 사전 추정은14,511,255,971bytes다. 이는 디스크 준비 추정이며 메모리 요구량 또는 실제 peak가 아니다. P031의 개별 작업 디스크 검사와 별도로 누적 보존 공간을 확인한다. 이전 다운로드나 다른 프로젝트 캐시를 삭제해 조건을 맞추지 않는다.

기존 runtime은 owned CPU worker를 작업마다 띄우므로 실제 peak/RSS와 종료 여부를 기록할 수 있지만 현재 구현만으로 OS pressure 기반의 전 구간 중단을 보장하지 않는다. P032 READY 전 실제 모니터가 어느 프로세스·기간을 관찰하고 종료할 수 있는지, HTTP 서버 측 작업은 어떻게 미확정 처리하는지 확정한다. P013 runner/grant를 가져오지 않는다. M1에서 큰 모델이 실패하면 작은 모델의 성공으로 대체 표기하지 않으며 해당 프로필의 지원/검증 한계를 남긴다.

## 지표와 해석

검색·리랭커는 Recall@K/MRR/nDCG 및 candidate/top-K/context fact 회수를 보고한다. fact가 없는 gt09/gt10은N/A이며 올바른 보류 여부를 별도로 검토한다. 결과 비교는 같은 질문·정답·artifact identity가 맞는 쌍만 계산하고 실패/누락/분모를 노출한다. 여러 청크가 한 fact를 지지해도 fact는 한 번만 센다.

답변은 승인된 필수·보충 기준과 원문을 대조해 누락·지원되지 않은 추가 주장·인용 일치·보류를 기록한다. 자동 LLM/NLI 평가기나 새 Faithfulness/Correctness 수치를 생성하지 않는다. 검토 주체·방식·한계를 표시하고 공개 학습10개에서의 관찰을 독립 일반화 성능으로 보고하지 않는다.

## 첫 답변의 통과 조건 후보

생성 smoke는 gt01/gt02에 대해 JSON/응답 완료만 보지 않는다. 선택된 실제 profile과 전달 문맥을 기록하고 아래 내용을 원문·승인 기준과 직접 대조한다. 이 조건도 READY 전에 고정하며 결과를 본 뒤 통과하기 쉽게 바꾸지 않는다.

- gt01은 승인된 필수6개(입사 후3개월 경과, 매년1일, 수습 제외, 생일이 속한 달, 근무일 사용, 사용3영업일 전 신청)를 조건/예외를 유지하여 답한다. 승인된 보충 정보의 생략 자체를 실패로 보지 않는다. 포함한 보충 정보는 원문과 대조한다.
- gt02는 최대5일 이월·다음 해3월31일 기한·생일 특별휴가 제외의 필수3개를 구분한다. 다른 휴가 제도의 기간/기한과 혼동하지 않는다.
- 실제 인용 ID가 전달 문맥 안에 있고 코드가 붙인 quote/page가 원문과 일치해야 한다. 인용 형식의 유효성과 해당 주장을 지지하는 의미 관계를 별도로 검토한다.
- 질문에 없는 임의 금액·조건·승인 예외를 새로 덧붙이지 않는다. 빈 답변·잘린 응답·실패를 성공으로 포함하지 않는다.

모든 필수 내용이 전달 문맥에 없으면 생성 모델의 실패로 단정하지 않고 검색 후보→K→문맥 예산 단계에서의 누락을 먼저 기록한다. 충분한 문맥을 사용한 생성 단독 비교는 별도 고정 context artifact로 수행하고 end-to-end 결과와 구분한다. smoke가 실패하면 호출을 자동 확대하지 않고 그 실패와 원인을 남긴다. 수정한 prompt/config로 재시험할 때는 별도 실험 ID와 요청 수를 사용하며 재시도/예산을 새로 무한정 열지 않는다.

전체10개에서는 같은 검토 기준을 유지한다. 특히 gt09/gt10은 규정에 없는 지원 한도/유류비 단가를 발명하지 않고 근거 부재를 밝혀야 한다. 원문 회수율만으로 이 답변의 보류가 옳다고 결론내리지 않는다. 모델별 개선 여부와 제품 연결 성공을 분리하여, 실제로 성능이 나아지지 않은 옵션도 그대로 보여준다.

사용자에게 실제 생성 검증을 기존 로컬4B/API/추가 보류 중 어느 경로로 시작할지 질문했다. 답변 전에는 선택과 실행을 확정하지 않는다. Drive 링크 요청도 별도 대기이며 로컬 PDF 시험이 실제 계정 연결 검증을 대신하지 않는다.

# P032 S18 · 청킹 후보 ID를 제한한 구조화 출력

## 준비 검토

dev c24bb38에서 S17은 202자의 같은 원문에 대해 141자·103자 분할 후보를 만들었고 435토큰을 입력했다. 유효한 응답 없이 출력 4,096토큰 한도에 도달했다. 현재 llm.core.preview는 Ollama generation 역할에서만 JSON Schema를 format 필드에 넣고, chunking 역할에는 일반 JSON 형식을 지정한다. 설치된 모델이 제한된 스키마에서 끝 번호를 반환할 수 있는지 단일 변경으로 시험한다. [Ollama 구조화 출력 설명](https://docs.ollama.com/capabilities/structured-outputs)

## 구현 및 판정

1. Ollama의 candidate_choice 전용 선택 옵션으로 실제 창에서 생성한 후보 ID만 허용하는 JSON Schema를 요청한다. candidate_id는 필수 문자열 enum, 추가 필드는 허용하지 않는다. 기존 생성 스키마 지원을 재사용하고 역할·provider·설정 호환을 확인한다. 기존 청킹과 S17 저장 결과의 재생 및 단일 후보의 호출 생략을 유지한다. 지원하지 않는 조합에서 제약을 적용했다고 표시하지 않는다.
2. 설치본에서 S17과 동일한 합성 PDF·두 후보·순서·원문·모델 digest·메시지·thinking 및 생성 옵션을 대조한다. 요청 body에서 format만 달라야 한다. 미리보기·단독 실행·통합 실행의 실제 요청 및 지문을 대조하고 스키마를 적용해도 수신 결과의 ID·피복·길이·잘림 검증을 유지한다.
3. 기존 종료 ledger와 구분되는 새 실행으로 사전 대조가 통과한 경우에만 동일 Qwen 4B에 최대 1회 전송한다. S17의 서버 소유권·자원/시간 제한·정리·자동 재시도 0 조건을 재사용한다. 유효 ID가 관찰되면 어느 후보가 선택되었는지, 제1조 제목과 조건의 동시 보존 여부 및 BM25가 S16 질문의 원문을 몇 위에서 찾는지 기록한다. 유효 응답이 없으면 잘림·오류·사용량만 기록하고 선택 결과를 추정하지 않는다. 스키마는 형식을 제한하며 의미상 좋은 선택을 보장하지 않는다.
4. 설치 가이드에 실험 차이와 결과를 연결하고 기존 데이터·다른 제공자·모델 없는 실패 검증과 dev 정상 push를 확인한다. 성공·실패 모두 공개 검증 기록으로 남기고 자동으로 다음 실험을 실행하지 않는다. 긴 문서·추가 모델·Drive·유료 API·평가기 보류.

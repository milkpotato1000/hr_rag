P번호는 식별자이고 실행 순서는 의존성·우선순위로 정한다. 현재 순서는 **P015 원문 PDF 재작성 → P007 청킹·검색 실험 → P013 기본 평가기 → P014 NLI 비교 → P008 답변 비교 UI → P010 Hybrid**다. P015는 완료된 P006/P012가 선행이다. 하네스는 별도 프로젝트에서 계속 관리하며 HR RAG 작업번호를 부여하지 않는다. 후속 하네스 버전 개발 전체를 제품 착수의 무기한 선행으로 두지 않는다. P015만 준비 완료이며 후속 초안은 해당 산출물로 상세 계약을 준비한다. Cross-Encoder Reranking·thinking·Human-in-the-Loop·서빙·실제 Drive/Slack은 후속 후보로 유지한다.

새 큰 단계는 이전 단계에서 필요한 코드·데이터·테스트를 복사·선별해 시작한다. 이전 폴더는 비교 기준으로 보존하고 README/stage-manifest에 원본 커밋·경로·hash와 변경 이유를 남긴다. 단계 폴더만 복사해도 실행 가능해야 한다. [큰 단계 규칙](../architecture/stage-layout.md)을 따른다.

학습은 이미 작동하는 Naive RAG/LangChain 기준선에서 현실적인 원문으로 돌아간다. 원문 작성·PDF 추출(P015)을 먼저 검증하고 청킹/검색 실험(P007)으로 입력을 고정한 다음 답변 평가기(P013/P014)를 만든다. P006 fixed 청킹 완료와 여러 방식의 비교 실험 완료는 다르다. P007은 기존 검색/fact-span 평가와 원문·청크·검색 비교 UI를 제공하므로 답변 평가기 없이 화면에서 실험할 수 있다.

Generation Evaluation은 B의 여러 RAG 단계가 내보낸 답변·실제 전달 문맥을 읽는 별도 모듈이다. P013에서 원문 기반 Ground Truth 초안→사람 승인→버전 고정, claim 추출 공통 사용, LLM 검증/매칭과 Python Faithfulness/Factual P/R/F1을 구현한다. 현재 생성 Qwen3-4B는 유지하고 제안 Qwen3-8B는 평가 역할 후보로 별도 검토한다. 실제 사람 승인과 Codex 대조를 구분한다. B의 평가기 선택/버전은 이후 Hybrid·청킹 후보의 최종 답변 비교에서 고정해 사용하며 P008은 결과 화면을 연결한다. 평가 모듈 때문에 B의 큰 RAG 단계 번호를 추가하지 않는다. A/B의 독립 개발 이후 C에서 전문 Agent 조율을 학습한다.

## 2단계: 현실적인 원문에서 청킹 비교

HR 원문 업로드 장소는 Google Drive 지정 폴더로 가정한다. 현재는 명시된 가상 snapshot/로컬 캐시를 사용한다. 실제 Drive 동기화는 별도 계약이다.

1. **P015 — 독립된 가상 규정 원문 작성:** 정답 청크를 먼저 쓰고 이어 붙이지 않는다. 대상·조건·예외·신청 절차를 자연스러운 문서 구조로 작성하고 기존 정책 의미·수치를 보존한다. 제목/섹션은 원래 위치에만 둔다.
2. **P015 — 학습 해설 분리:** 기존 source-v2의 답변 요령·평가 해설은 새 원문에서 제외하고 가이드/평가 파일에 둔다. 가상 안내는 문서 앞부분과 UI에 두되 실제 원문에 포함된 안내는 추출 시 보존한다. 본문·제목 메타데이터·제목을 검색 입력에 보강하는 설정을 구분한다.
3. **P015 — PDF 추출 검증:** PDF 화면과 추출 텍스트·페이지/offset을 대조해 줄바꿈·제목·페이지 경계·누락을 확인한다. 추출 오류와 분할 오류를 분리한다. 새 corpus/원문 평가 근거를 버전으로 고정하고 과거 15청크/source-v2는 보존한다.
4. **P007 — 청킹 비교:** 고정 크기, recursive(구분자 우선순위), 제목/섹션 기반, semantic(의미 변화) 분할을 비교한다. overlap은 인접 청크의 겹침 설정으로 별도 변화시킨다. 크기 200/400/800자·overlap 0/20%는 P007의 초기 후보이며 최적값이 아니다.
5. **검색 평가 후 답변 평가:** P007에서 query→top-k를 평가하고 고정 입력/후보를 P013에 인계한다. 원문·청크·검색 비교 UI는 P007부터 사용한다. P013/P014에서 평가기를 검증한 다음 P008에서 같은 화면에 실제 생성·답변 점수 비교를 추가한다. 제목 없는 후속 청크, 다른 청크에 나뉜 조건/예외, 생일 포인트와 휴가 혼동을 관찰한다. 점수를 높이려고 원문을 정답에 맞게 재배치하지 않는다.

원문 개정과 청킹 변화는 각각 별도 비교로 기록한다. 청킹 실험 안에서는 snapshot·추출 텍스트·질문·임베딩·검색기·생성 설정을 고정하고 한 번에 한 변수만 바꾼다. 원문 변경 시 기존 offset/qrels를 그대로 재사용하지 않고 새 원문의 fact/span으로 다시 검토한다. OCR·복잡한 표/다단·토큰 기반 청킹·부모 문맥 확장은 별도 후속 후보다.

## 3단계: 검색 결합만 바꿔 보기

P010에서는 기존 corpus·청크·질문·임베딩·생성 모델·프롬프트·문맥 예산·ID-only 인용 계약을 고정한다. BM25, Dense, Hybrid를 같은 질문으로 비교한다. RRF 후보 수·상수·동점·중복 ID·결과 부족/실패 처리는 상세 준비 검토에서 확정한다.

먼저 검색 Recall@K·Precision@K·MRR·nDCG와 질문별 top-k를 확인하고, 실제 전달 근거와 답변의 조건 누락·오답·보류·인용 지지를 대조한다. reranker나 새 원문을 동시에 넣지 않는다. P015/P007에서 고정한 가상 corpus의 규모·정책 범위 한계도 기록한다.

## 구분해서 볼 평가

| 관찰 구간 | 평가 요소 | 해석할 때 구분할 것 |
| --- | --- | --- |
| PDF → 추출 텍스트 | 내용 보존, 페이지·위치 매핑, 누락·읽기 순서 | 추출 문제와 청킹 문제 |
| 원문 → 청크 | 경계의 조건/예외 보존, 길이 분포, 중복 | overlap의 정보 보존과 비용 |
| 질문 → top-k | 필수 fact/span 회수율, 전체 필수 근거 회수 성공, 전략별 qrels 지표 | 중복 근거로 점수 부풀리지 않기; 청크별 분모 변화 |
| 후보 → 전달 문맥 | 실제 전달 근거 회수율, 예산 때문에 제외된 근거 | 검색 성공과 전달 성공 |
| 문맥 → 답변/인용 | 정확성, 조건 누락, 근거 충실성, 인용 구조/의미, 과도 보류 | ID/원문 일치와 주장 지지 |
| 전체 파이프라인 | 문서 구축/임베딩/색인/검색/생성 시간·분량·오류 | cold/warm, 구축 비용과 질문당 비용 |

같은 K 비교와 같은 전달 분량 비교는 따로 한다. 근거 없는 질문은 검색 Recall 분모와 분리해 적절 보류를 본다. 기존에 본 질문은 tuning 자료이며 확인용 holdout으로 부르지 않는다. 정확한 정답·산식·비교 설정은 해당 P카드 준비 검토에서 확정한다.

청크 크기, top-k, 검색 근거 최대 분량(현재 8000문자), Qwen 실행 num_ctx(현재 8192토큰), 출력 여유는 서로 다른 값이다. 8000/8192는 초기 설정이며 최적값이나 모델 고유 사양이 아니다. 문자 수를 정확한 토큰 수로 표시하지 않는다. 현재 문맥 선택은 청크 전체 단위이므로 후순위 후보가 예산에 따라 제외될 수 있다.

## 학습 진행 방식

**예상 → 관찰 → 실패 위치 분류 → 한 변수 실험 → 해석** 순서로 진행한다. 사용자는 필요한 근거와 기대 답변을 예상하고, Codex는 구현·실행·검증·실패 기록을 담당한다. 사용자는 원문부터 결과까지 확인하며 검색 실패·문맥 제외·생성 누락·잘못된 인용을 구분한다.

P012까지 완료됐다. P015는 범위·정책 보존·PDF/추출 검증·독립 복사·증거 계약을 준비 완료로 등록했으며 dev는 정확한 plan 통합·채택 후 착수한다. 이 기획 변경은 PDF 구현 완료가 아니다. 이후 P007 → P013 → P014 → P008 → P010은 각 선행 산출물을 검토해 상세 계약을 준비한다. 과거 계획·실행/실패 증거는 Git 이력과 기존 P카드에 보존한다.

# RAG 구현과 학습 순서

2026-10-22 사용자 요청: 구현·테스트·수정·실행은 Codex가 맡고, 사용자는 동작 의미·평가·최적화 포인트를 중심으로 학습한다. Naive 기준선은 `1. Naive RAG/`에 보존한다. P번호는 세부 작업 단위이며 학습 단계 번호와 별개다.

## 현재 학습 순서 — 2026-10-28 사용자 결정

1. **Naive RAG:** 기존 BM25/Dense 각각의 검색→문맥→답변·인용·보류를 관찰한다. P001~P006/P009 구현은 비교 기준으로 보존한다.
2. **검색 고도화 / Hybrid RAG:** BM25와 Dense 결과를 결합하는 실험을 먼저 한다. [P010](plans/P010.md)은 초안이며, RRF 결합과 단독 검색 비교의 상세 계약을 이후 준비한다. reranker는 별도 후속 후보로 두고 함께 바꾸지 않는다.
3. **PDF 원문·청킹 실습:** 실제 사내 규정처럼 작성한 가상 PDF→PDF parser/reader로 텍스트·페이지 정보 추출→청킹→색인→검색·답변 비교 순서다. [P007](plans/P007.md)/[P008](plans/P008.md)은 이 단계로 미룬다.

문서 처리 파이프라인에서는 추출·청킹이 검색보다 앞서지만 학습은 완성된 RAG를 관찰한 후 청킹으로 돌아가도 된다. 기존 P006의 fixed400/overlap80 구현은 참고 기준이며 청킹 비교 학습 완료를 뜻하지 않는다. 아래 날짜별 항목은 당시 계획 이력이고 현재 우선순위는 이 절을 따른다. 이번 요청은 학습 계획 추가·순서 조정이며 구현 착수 요청이 아니다.

### 청킹 단계에서 비교할 내용

- 실제 규정 형태의 문서: 제목/섹션은 원문 위치에만 배치하고 조건·예외·신청 절차를 자연스러운 본문으로 구성한다. 가상 안내는 문서 앞부분과 UI에 두고 모델 답변법/평가 해설은 원문 밖 학습 자료로 분리한다. 기존 정책 의미와 과거 corpus를 보존하고 새 원문 버전을 사용한다.
- PDF 읽기: 화면에서 본 PDF와 parser 추출 텍스트를 대조한다. 줄바꿈·페이지 경계·제목·누락을 먼저 확인한다. 추출 오류와 청킹 오류를 구분하며 OCR/복잡한 표 처리는 별도 범위다.
- 고정 크기: 동일 크기로 자른 경계에서 조건/예외가 갈리는지 관찰한다.
- overlap: 인접 청크의 겹침을 0/일부로 바꿔 정보 보존과 중복 비용을 비교한다. 독립적인 분할 알고리즘이라기보다 청킹에 적용하는 설정으로 다룬다.
- recursive: 문단/줄/문장 등 구분자 우선순위와 최대 크기로 분할하는 방식을 비교한다.
- semantic: 문장 사이 의미 변화로 경계를 정하는 방식을 비교한다. 임베딩 비용·임계값을 함께 기록한다.
- 제목/섹션 기반 분할도 보조 비교한다. 원문 본문과 제목 메타데이터를 구분한다.

같은 원문·질문·검색기·생성 모델을 고정해 청킹만 바꾸고, 청크 경계/원문 위치, 필수 근거 회수, 중복·분량, 조건 누락·오답·보류, 처리 시간을 평가한다. 2단계에서 검색기를 바꾼 효과와 3단계에서 문서/청킹을 바꾼 효과를 섞지 않는다. 구현·테스트는 Codex가, 가설·관찰·해석은 사용자가 담당한다.

후속 카드를 미리 실행하거나 초안을 자동승인하지 않는다. 각 작업은 구현→검증→수정→재검증→증거·상태커밋→정상push를 마친 뒤 다음 작업을 실행한다. plan은 고정된 선행계약을 바탕으로 다음 독립 과제를 미리 준비할 수 있으며 선행 완료·실제 인터페이스를 대조한 뒤 착수한다. 새로운 외부 계정·유료자원·업무결정이 없으면 매 단계 인계허가를 반복해서 묻지 않는다.

## 학습 방식

1. 먼저 같은 질문의 원문, 검색된 청크, LLM에 전달된 문맥, 답변·인용을 따라간다.
2. 결과를 보기 전에 예상한다. 필요한 청크는 무엇이며, 문서에 없으면 어떻게 끝나야 하는지 적는다.
3. 실패 원인을 문서·청킹·검색·문맥선택·생성·인용·기대정답으로 나눈다. 검색 실패를 프롬프트만 바꿔 고치려 하지 않는다.
4. 한 번에 한 설정만 바꾸고 같은 질문 묶음으로 비교한다. 변한 설정과 지표·실제사례·지연을 함께 본다.
5. 구현은 Codex에 요청하고 사용자는 가설과 결과 해석에 집중한다. “top-k를3/5/10으로 바꾸되 corpus·모델·프롬프트는 고정해 비교하고 실패사례를 보여줘”처럼 요청한다.

초기 최적화 순서는 검색 top-k·한국어표현·문맥량, 그다음 답변프롬프트·보류·인용, 이후 모델크기·서빙지연이다. Hybrid·reranker·Agentic은 Naive기준선 완성 후 별도 큰 단계로 비교한다.

## 구분해서 볼 평가

- 검색: Recall@K·MRR·nDCG, 필요한 모든 근거가 실제 생성문맥에 들어갔는지.
- 답변: 사실정확성·조건누락·근거충실성·인용정확성. 문서ID가 맞는 것과 답변주장이 근거에 지지되는 것은 별개다.
- 보류: 근거없는 질문에서 허구답변을 하지 않는지, 근거가 있는데 과도하게 보류하는지.
- 성능: 임베딩·검색·모델로드·생성·전체시간, cold와warm조건을 구분한다.
- 회귀: 정상질문·복수근거·근거없음·표현변형·잘못된인용·모델/색인장애.

최종 가이드는 P005에서 실제실행 명령·화면·구체질문·비교방법과 연결해 제품폴더 안에 작성한다. 이 문서는 학습순서이며 아직 구현되지 않은 답변품질이나 성능의 달성을 주장하지 않는다.

# Naive RAG E2E 구현과 학습 순서

2026-10-22 사용자 요청: 구현·테스트·수정·실행은 Codex가 맡고, 사용자는 동작 의미·평가·최적화 포인트를 중심으로 학습한다. 큰 구현 폴더는 계속 `1. Naive RAG/`다. P번호는 그 안의 작업 단위다.

| 작업 | 결과 | 진행 기준 |
| --- | --- | --- |
| P001 | 합성 문서·질문·검색 평가기 | 완료 |
| P002 | BM25 검색·평가 연결 | 완료 |
| [P003](plans/P003.md) | 로컬 실행 환경·BGE-M3·Qdrant Dense와 BM25 비교 | 완료: 실제 모델·53개 테스트와 커밋된 증거 확인 |
| [P004](plans/P004.md) | 검색 한 번과 LLM 한 번을 연결한 답변·인용·보류 | 준비 완료: P003 완료 증거 검토 |
| P005 예정 | 질문 화면·실행 추적·E2E 회귀·학습/실험 가이드 | P004 실제 결과 검토 후 P문서 준비 |

후속 카드를 미리 실행하거나 초안을 자동승인하지 않는다. 각 작업은 구현→검증→수정→재검증→증거·상태커밋→정상push를 마친 뒤 다음 P계약을 준비한다. 새로운 외부 계정·유료자원·업무결정이 없으면 매 단계 인계허가를 반복해서 묻지 않는다.

## 학습 방식

1. 먼저 같은 질문의 원문, 검색된 청크, LLM에 전달된 문맥, 답변·인용을 따라간다.
2. 결과를 보기 전에 예상한다. 필요한 청크는 무엇이며, 문서에 없으면 어떻게 끝나야 하는지 적는다.
3. 실패 원인을 문서·청킹·검색·문맥선택·생성·인용·기대정답으로 나눈다. 검색 실패를 프롬프트만 바꿔 고치려 하지 않는다.
4. 한 번에 한 설정만 바꾸고 같은 질문 묶음으로 비교한다. 변한 설정과 지표·실제사례·지연을 함께 본다.
5. 구현은 Codex에 요청하고 사용자는 가설과 결과 해석에 집중한다. “top-k를3/5/10으로 바꾸되 corpus·모델·프롬프트는 고정해 비교하고 실패사례를 보여줘”처럼 요청한다.

초기 최적화 순서는 검색 top-k·한국어표현·문맥량, 그다음 답변프롬프트·보류·인용, 이후 모델크기·서빙지연이다. Hybrid·reranker·Agentic은 Naive기준선 완성 후 별도 큰 단계로 비교한다.

## 구분해서 볼 평가

- 검색: Recall@K·MRR·nDCG, 필요한 모든 근거가 실제 생성문맥에 들어갔는지.
- 답변: 사실정확성·조건누락·근거충실성·인용정확성. 문서ID가 맞는 것과 답변주장이 근거에 지지되는 것은 별개다.
- 보류: 근거없는 질문에서 허구답변을 하지 않는지, 근거가 있는데 과도하게 보류하는지.
- 성능: 임베딩·검색·모델로드·생성·전체시간, cold와warm조건을 구분한다.
- 회귀: 정상질문·복수근거·근거없음·표현변형·잘못된인용·모델/색인장애.

최종 가이드는 P005에서 실제실행 명령·화면·구체질문·비교방법과 연결해 제품폴더 안에 작성한다. 이 문서는 학습순서이며 아직 구현되지 않은 답변품질이나 성능의 달성을 주장하지 않는다.

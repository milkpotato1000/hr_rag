# 후보 번호를 출력 형식으로 제한하면 청킹이 완성될까?

교육휴가 규정 PDF 1쪽의 같은 202자를 두 후보로 나눴습니다. **후보 1**은 제1조 제목과 ‘직무 관련 자격시험 응시자는 연 1일 교육 휴가를 신청할 수 있다’는 본문을 같은 청크에 둡니다. **후보 2**는 제목 직후에 끊어 본문을 다음 청크로 보냅니다. [두 후보의 원문과 경계](frozen.json)

| 실험 조건 | S17 | S18 |
| --- | --- | --- |
| 후보·순서 | 141자에서 나누는 1번, 103자에서 나누는 2번 | 동일 |
| 모델·설정 | 로컬 Qwen 4B, thinking 켬, seed 42, 출력 상한 4,096토큰 | 동일 |
| 메시지 | 규정과 대상·조건·예외를 함께 보존하는 후보 선택 | 동일 |
| Ollama 요청의 format | 일반 JSON | candidate_id 필수, 문자열 1·2만 허용, 추가 필드 금지 |

S17에서 실제 전송한 요청 해시를 설치본에서 재현하고, S18의 format을 S17 값으로 되돌렸을 때 두 요청 본문이 완전히 일치하는지 검사했습니다. 단독 청킹과 통합 파이프라인에서 시험용 전송 본문과 지문을 대조했습니다. 수신 결과의 잘림, 후보 범위와 필드 검사도 유지했습니다. [설치본 입력 대조](experiment.py) · [청킹 회귀 21건](chunk-tests-final.log) · [제공자·전송 회귀 18건](transport-regression.log)

**실제 결과는 잘림이었습니다.** 입력 435토큰, 출력 4,096토큰, 서버 처리 시간 약 230초로 기록됐습니다. S17과 S18 모두 같은 출력 상한에서 끝났고 검증 가능한 후보 ID를 얻지 못했습니다. 이 문서와 설정에서는 출력 형식만 바꿔도 문제가 해결되는지 시험했고, 두 실행 모두 청크를 완성하지 못했습니다. 모델이 어느 경계를 선호했는지, 제1조가 보존됐는지, BM25에서 근거가 몇 위인지 모두 미측정입니다. [실제 결과](review.json) · [이전 실행](../p032-s17/README.md)

# 같은 문서를 청킹하면 무엇이 달라지나

[청킹 경계 보고서](../../verification/p032-s2a/report.html)는 S1에서 사용한 가상 규정집 23쪽·38,582자를 그대로 나눈 결과다. 고정·재귀·제목/섹션 방식은 실제 청크를 만들었다. 의미·LLM 방식은 입력과 요청 미리보기까지만 준비했다. 이번에는 검색과 답변을 실행하지 않았다.

| 방식 | 최대 크기 / overlap | 실제 청크 수 | 길이 중앙값 | 중복 문자 합계 |
| --- | --- | --- | --- | --- |
| 고정 | 256 / 64자 | 201 | 256자 | 12,800자 |
| 재귀 | 256 / 64자 | 257 | 218자 | 16,371자 |
| 제목/섹션 | 256 / 64자 | 264 | 215자 | 16,064자 |

숫자가 같아도 overlap의 적용 위치는 다르다. 고정 방식은 256자를 담고 192자씩 이동한다. 재귀 방식은 문단·문장·공백을 우선해 최대 192자의 기본 구간을 정한 다음, 앞의 원문을 최대 64자 붙인다. 제목/섹션 방식은 제목 구간 안에서 이 재귀 분할을 적용하며 이전 섹션으로 overlap하지 않는다. 현재 제목 인식은 장/조와 Markdown 제목 규칙이다. 모든 PDF의 시각적 제목을 이해하는 방식은 아니다.

세 방식 모두 이번 원문 전체를 보존했고 공백만 제외된 구간도 없었다. 이것은 원문 누락 검사다. 필요한 청크가 실제 검색되는지와는 별개다. 중복 문자 합계는 청크들의 길이 합에서 원문의 고유 위치 수를 뺀 값이며, 중복이 많은 것이 항상 좋은 것도 아니다.

## 먼저 볼 세 사례

**생일휴가(gt01): 제목과 본문을 함께 본다.** 고정 청크의 원문 위치 192–448에는 목차의 출장 제목 끝과 생일휴가 본문이 함께 들어간다. 제목 metadata는 출장으로 붙었다. 재귀 방식의 178–376에는 교육휴가 제목이 붙는다. 구조 방식의 209–376은 생일휴가 장에서 시작하여 제목도 맞는다. 원문의 자격·연간 1일·수습 제외는 세 방식 모두 각각 단일 청크에 들어 있다. 구조 방식의 제목이 이 사례에서 맞았다고 검색 품질까지 좋아졌다고 단정할 수는 없다.

**재택근무(gt03): 복합 질문의 하위 항목이 어디에 모이는지 본다.** 자격·교육·제외 직무·횟수·승인·기기 조건은 각각 한 청크에 들어 있지만 같은 한 청크에 모두 들어 있지는 않다. 고정 방식에서는 자격과 교육이 청크 62, 제외 직무와 횟수가 63, 승인 기한이 64, 기기 조건이 65에 나뉜다. 재귀는 79–81, 구조는 85–87에 모인다. 여기의 청크 번호는 화면처럼 1부터 센다. 필요한 청크 수가 줄어도 검색 순위와 문자 예산이 실제로 이들을 함께 전달하는지는 후속 실험에서 확인해야 한다.

**출장 예외(gt06): 한 사실에 여러 근거 구간이 필요한 경우를 본다.** `gt06-c03`과 `gt06-c04`는 충분한 원문 구간의 합집합이 필요하다. 세 방식 모두 최소 2개 청크가 있어야 해당 사실을 지지한다. 질문당 top-k를 하나로 줄이면 이런 사실은 충분한 근거를 담기 어렵다. 보고서에서 사실을 펼치면 필요한 원문 구간과 두 청크를 함께 볼 수 있다.

## 단일 청크 포함과 검색 성공을 구분하기

38개 필수 사실 중 단일 청크만으로 충분한 사실은 고정 34개, 재귀·구조 각각 35개였다. 나머지는 모두 두 청크가 필요했다. 이는 모든 청크를 대상으로 경계를 검사한 수치이며 검색 recall이 아니다.

개별 결과도 함께 봐야 한다. 생일휴가 장애 시 승인 면제 관련 `gt07-c03`은 고정에서 1개였지만 재귀·구조에서 2개로 나뉘었다. 반대로 취소 범위 관련 `gt08-c07-a1/a2`는 고정에서 2개, 재귀·구조에서 1개였다. 경계를 자연스럽게 자르는 방식도 모든 사실을 한 청크 안에 보존하지는 않는다.

기존 S1 고정 청크와 새 고정 청크는 ID·원문 위치·텍스트·페이지·제목이 모두 동일하다. 다만 새 저장 경계 artifact는 단위·설정·실행 출처를 포함하는 별도 identity다. 기존 qrels를 다른 fingerprint에 복사하지 않았다. 다른 방식의 청크 관련성 판정은 후속 비교에서 별도로 준비해야 한다.

## 의미·LLM 청킹은 어디까지 준비했나

의미 방식은 원문을 최대 120자의 567개 단위로 나눴다. 실제 준비된 E5-small의 파일 hash를 확인했으며, 경계 계산에는 이 단위들을 임베딩하는 1작업이 필요하다. 아직 임베딩하지 않았으므로 거리·경계·최종 청크 수는 없다. 이 경계용 임베딩과 나중 검색용 청크 임베딩은 별도 작업이다.

LLM 방식은 같은 단위를 34개 window로 나눈다. 각 window는 최대 1,200자·20단위이며, 실제 preview body의 최대 크기는 local 예시 5,948byte, OpenAI Chat API 예시 5,888byte다. 둘 다 64window·16,384byte 한도 안이다. local은 `think:false`, JSON format, runtime options를, API는 JSON response format과 출력 상한을 담는다. 토큰 수는 측정하지 않아 `null`이다. 문자·byte 한도 통과가 모델의 token window 통과를 보장하지 않는다.

두 LLM 설정은 **미설정 예시**다. 모델명·digest·API 자격을 선택하거나 서버를 조회하지 않았다. LLM은 이후 허용될 경우 원문 단위의 마지막 ID만 선택하며 원문을 다시 쓰지 않는다. 현재 preview를 검색에 사용할 수 있는 청크로 표시하지 않는다.

후속 네 방식의 E5 Hybrid·후보 20·top-5·문맥 2,000자·질문 10개 비교를 모두 새로 실행하면 경계 1 + 청크 색인 4 + 질문 40 = 45개 embedding 작업을 예상한다. 기존 고정 결과를 역사적 기준선으로 참조하면 34개지만 새 artifact 실행 결과로 바꾸어 표시하지 않는다. 실제 작업량·시간·한도는 별도 실행 계약에서 확정한다.

실습에서는 다음처럼 요청하면 된다.

> 청킹 경계 보고서의 gt01, gt06, gt07을 모델 호출 없이 읽어줘. 원문 구간과 청크 경계를 대조하고, 단일 청크에 있는 사실과 두 청크가 필요한 사실을 구분해줘. 검색 성능은 추정하지 말고 이후 K·문자 예산 실험에서 확인할 가설만 정리해줘.

후속 S2b 실제 비교는 첫 의미 임베딩의 SDK 오류로 중단됐다. [중단 기록과 해석](chunk-comparison-s2b.md)을 참고한다. 위 S2a 경계 관찰은 그대로이며 검색 비교 성공으로 바뀐 것은 아니다.

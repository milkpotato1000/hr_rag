# 한 번에 한 조건을 비교하기

[학습 시작점](README.md)으로 돌아가기.

실습 전에 예상 결과를 한 문장으로 적고, 결과를 확인한 뒤 원인을 설명합니다. 코딩 도구에는 구현·기록·검증을 맡기되 “점수가 올랐으니 좋다”에서 끝내지 않습니다. 저장된 결과 관찰부터 시작하고 신규 모델 실험은 별도 승인된 범위에서 진행합니다.

## 단계별 질문과 관찰

| 학습 단계 | 먼저 답해 볼 질문 | 비교 중 고정할 것 | 관찰할 것·현재 범위 |
| --- | --- | --- | --- |
| 1. Naive RAG | 답변에 필요한 근거가 검색됐나? 전달됐나? | 질문, corpus·청크 버전, 모델·프롬프트 | 후보 ID, 순위, 전달/제외 ID, 인용, 필수 조건 누락. 기존 결과 관찰 가능 |
| 2. 검색 고도화 | 단어가 다른 질문도 찾나? | 청크·qrels·질문, 최종 K | BM25/Dense Recall@K·MRR·nDCG·지연. Hybrid RRF는 후속 P010 |
| 3. 청킹 | 조건과 예외가 같은 청크에 남나? | 원문·PDF 추출본·질문·검색 모델 | 청크 길이·수, 근거 회수율, 문맥 예산 안의 중복. P007 저장 실험 활용 |
| 4. 임베딩 교체 | 같은 청크에서 근거 순위가 달라지나? | 청크·질문·qrels·거리 계산 조건 | 새 index fingerprint, Recall@K, 지연·자원. 임의 모델 교체는 후속 |
| 5. 리랭킹 | 검색한 N개 중 정답을 K개 안으로 올리나? | 동일 후보 N개·질문·최종 K | 순위 변화·누락·추가 지연. P020 후속 |
| 6. 생성 모델 교체 | 같은 문맥에서 조건 누락이 줄었나? | 실제 전달 문맥, 질문, 프롬프트, 출력 예산 | 필수 사실 충족, 근거 지지, 과도 보류, cold/warm 시간·비용. API 비교는 후속 |
| 7. 평가기 비교 | 사람이 정한 E/N/C와 일치하나? | 고정 주장·근거·기대 라벨·매칭 규칙 | 라벨별 오판, 추출 누락·추가, 재현성. P013 미완료·보류, NLI는 P014 후속 |

학습상 Naive→고도화→청킹 순서로 읽어도 됩니다. 처리 순서는 항상 원문→청킹→색인→검색→답변입니다. 구현 순서는 채택한 로드맵과 선행 조건에 따릅니다.

고정 크기·재귀·의미 기반·제목/섹션 기반은 경계를 정하는 방식이고 오버랩은 인접 청크 사이에 내용을 중복하는 정책입니다. 개념상 조합할 수 있지만 현재 구현이 모든 조합을 지원하는 것은 아닙니다. 지원 설정은 [청킹 안내](<../../../2. Document Chunking/README.md>)와 기존 UI에서 확인합니다. 구조 경계를 넘어 임의로 문장을 붙이면 서로 다른 규정이 섞일 수도 있습니다. 오버랩을 늘렸을 때 회수율뿐 아니라 중복률·청크 수·전달 문맥을 함께 보세요.

## 생일휴가 사례로 누락 찾기

질문: “생일 휴가의 자격과 신청 기한, 사용 기간을 함께 알려 주세요.”

원문에 “입사 후 3개월 / 연 1일 / 수습 제외”가 있고 답변에는 “입사 후 3개월 / 수습 제외”만 있다고 가정합니다. 아래는 설명용 상황이며 새 모델 실행 결과가 아닙니다.

1. 검색 후보에도 “연 1일”이 없다면 검색 또는 청킹을 봅니다.
2. 후보에는 있지만 실제 전달 문맥에서 제외됐다면 문맥 예산·선택 순서를 봅니다.
3. 실제 전달 문맥에는 있는데 답변에서 빠졌다면 생성 단계의 누락입니다.
4. 인용 원문에 “연 1일”이 보이면 사용자가 대조할 수 있지만 답변 자체의 누락이 자동으로 해결되지는 않습니다.

“생일 축하 포인트”를 “휴가 자격”으로 설명하면 다른 정책을 잘못 연결한 것입니다. 관련 있어 보이는 문서의 인용만으로 그 주장이 지지되지는 않습니다. claim과 정확한 근거 문장을 대조하세요.

질문이 직접 요구하는 항목과 추가 안내를 구분해야 합니다. 현재 승인 정답은 필수·보충으로 나뉘므로 위 누락의 최종 Correctness 반영은 고정된 질문별 분류를 따릅니다. 모델 답변을 본 뒤 유리하게 정답 기준을 바꾸지 않습니다.

## 지표를 읽는 법

| 지표/상태 | 필요한 기준 | 해석 |
| --- | --- | --- |
| Faithfulness | 생성된 주장 + 실제 전달 문맥 + 유효 판정 | E/T. 말한 내용이 근거에서 지지되는가? 답변에 없는 필수 사실의 누락을 단독으로 잡지 못함 |
| Neutral / Contradiction rate | 같은 주장·문맥 | U/T, C/T. U는 neutral 개수(N 라벨), C는 명시적 모순. 정보 없음과 반대 증거는 다름 |
| Correctness P/R/F1 | 질문별 승인 GT와 필수·보충 매칭 정책 | 정답과 맞는가, 필요한 사실을 빠뜨렸는가? 새 개인 문서에 GT가 없으면 N/A |
| Recall@K / MRR / nDCG | 관련성 정답 qrels와 고정 질문 | 관련 근거를 찾았는가? GT 답변만으로 qrels가 자동 생성되는 것은 아님. qrels 없으면 N/A |
| 실패 / 미확정 | 오류·누락·판정 보류 사유 | 낮은 품질 점수와 별도. timeout·잘못된 JSON을 0점 답변으로 집계하지 않음 |

T는 평가 대상 생성 주장 수입니다. 모든 판정이 유효하고 T>0이면 E/T+U/T+C/T=1입니다. 판정 보류/실패가 있으면 확정 비율은 null/incomplete, 주장이 없으면 null/no_claims로 기록하고 coverage도 봅니다. Correctness의 부분 일치·중복·필수/보충 산식은 [P013 계약](../../planning/specs/P013-execution-contract.md)을 따릅니다. 해당 산식 구현과 실제 평가 모델 검증 완료는 서로 다른 상태입니다.

답변이 “입사 후 3개월” 한 사실만 말하고 그 사실이 근거에 있으면 Faithfulness는 높을 수 있습니다. 정답에서 요구한 다른 조건을 빠뜨렸다면 Correctness의 recall은 낮아질 수 있습니다. 근거와 답변이 모두 완전한지 각각 확인해야 합니다.

## 비교 기록 양식

| 항목 | 기록할 값 |
| --- | --- |
| 바꾼 변수 | 예: top-k 3→5. 이때 청크 크기·모델은 고정 |
| 입력 | 질문 ID, 원문 snapshot/hash, 청크 설정/hash, GT/qrels 버전 |
| 실행 | 구현 버전, provider·model revision/digest, 프롬프트, seed·생성 옵션, 환경 |
| 전달 근거 | 검색 후보 N, 최종 K, 실제 전달 ID·본문, 제외 사유, 문자·토큰 예산 |
| 결과 | 답변·인용, 누락/오판, 질문별 지표, 실패·미확정, 실행 ID |
| 자원 | cold/warm 시간, peak 메모리, API 토큰·비용 또는 미측정 |

top-k는 청크 개수, 청크 크기는 분할 단위의 길이, 입력 한도는 모델이 받아들이는 토큰 예산입니다. 문자 수와 토큰 수는 다릅니다. 검색한 top-k가 모두 LLM에 전달됐다고 가정하지 말고 저장된 실제 문맥을 봅니다.

청킹 또는 임베딩 모델/전처리를 바꾸면 새 index를 만들어야 합니다. 예전 index를 새 설정 이름으로 재사용하면 비교가 성립하지 않습니다. 튜닝 질문으로 설정을 정한 후 holdout에서 평가하며, holdout 결과를 보고 다시 선택했다면 그 자료를 더 이상 미관찰 검증셋으로 부르지 않습니다.

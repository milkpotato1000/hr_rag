# RAG 방식별 큰 구현 단계

## 사용자 결정과 단위

2026-10-22 사용자는 “지금은 간단한 나이브 RAG ... 이후 4. 에이전틱 RAG ... 큰단위 관리”라고 폴더 단위를 정정했다. P001 평가기, P002 BM25, Dense 검색 같은 세부 작업별로 번호 폴더를 만들지 않는다. 관련 작업들을 하나의 RAG 방식 또는 큰 구현 단계 안에서 이어서 개발한다.

현재 구현된 제품 코드는 저장소 루트의 `1. Naive RAG/`에 있다. 데이터·평가기·BM25·Dense·기본 답변·학습 UI·P006 원문 처리 기준선·P009 인용 개선까지 완료됐다. 이 완료 범위는 후속 Hybrid/청킹 비교/Agentic 구현까지 포함하지 않는다. 현재 상태와 예정 순서는 [로드맵](../planning/naive-rag-roadmap.md)을 따른다.

후속 큰 단계는 앞선 단계에서 필요한 코드·데이터·테스트를 복사·선별해 `번호. 제목/` 폴더에서 시작한다. 2026-10-29 최신 사용자 요청으로 현실적인 PDF 원문과 청킹 실험을 평가기/Hybrid보다 먼저 수행한다. 예정 폴더는 `2. Document Chunking/`(P015/P007/P008), `3. Hybrid RAG/`(P010)로 정정한다. 두 폴더는 아직 구현되지 않았으므로 기존 폴더를 이동하는 변경이 아니다. P015 준비 계약에서 필요한 최소 원문 처리 파일부터 확보하며 빈 폴더를 미리 만들지 않는다. Agentic의 최종 번호·범위는 별도 착수 계약에서 정한다.

| 큰 구현 단계 | 포함할 세부 작업 | 폴더 결정 |
| --- | --- | --- |
| Naive RAG | 평가 기반, BM25, Dense, 기본 검색·답변 생성, P011 동일 방식 구현 비교 | `1. Naive RAG/` |
| PDF 원문·청킹 실습 | P015 현실적인 PDF/추출, P007 고정/겹침/재귀/의미/구조 분할과 원문·청크·검색 UI, P008 답변/평가 UI 확장 | `2. Document Chunking/` 예정 |
| Hybrid 검색 고도화 | BM25 + Dense 결합과 단독 검색 비교, P010 초안 | `3. Hybrid RAG/` 예정 |
| Agentic RAG | 도구 선택, 제한된 재검색, 종료·실패 처리 등 | 사용자 예시는 `4. Agentic RAG/`; 실제 착수 계약에서 최종 확정 |

P번호는 작업 식별자이며 폴더 번호와 대응하지 않는다. 같은 큰 단계 폴더 안에서 여러 P카드를 순차 수행할 수 있다. 기획·계약·진척·검증 증거와 Git 하네스는 저장소 루트에서 유지한다.

## P011의 동일 단계 구현 비교

P011은 새 RAG 방식이 아니므로 큰 번호를 늘리지 않는다. 기존 `1. Naive RAG/` 제품 소스·데이터·프롬프트·lock·web·테스트를 보존하고 `variants/langchain/`에 필요한 파일을 복사한다. 후보 안의 direct 경로는 원본 동일 사본이며 LangChain 경로와 비교한다. 후보만 임시 위치로 복사해도 실행 가능해야 하며 부모 소스를 runtime import/symlink로 참조하지 않는다. 비교용 ignored 환경/색인은 별도로 준비하고 기존 runtime을 덮어쓰지 않는다. 기존 README/LEARNING_GUIDE/manifest의 비교 안내 추가는 P011 계약에 한해 허용한다.

P010에서 가져갈 원본은 P011의 실제 판정으로 정한다. ADOPT_LANGCHAIN이면 검증 후보, KEEP_DIRECT이면 기존 직접 구현, INCONCLUSIVE이면 직접 구현 유지와 재검토를 적용한다. 어떤 결과든 기준/후보·실패 증거는 보존하며 다음 단계 manifest에 선택 근거·commit/path/hash를 기록한다.

## 현재 단계에서 개발하기

각 큰 단계는 필요한 scripts 또는 src, data, tests, README.md, stage-manifest.json을 가진다. README에 단계 목표·현재까지 구현한 범위·실행법·세부 P작업·이전 큰 단계에서 가져온 것과 변경 이유를 적는다. manifest는 여러 관련 P번호를 기록할 수 있다.

같은 큰 단계 안에서는 코드를 추가·수정·리팩터링하고 필요한 기능을 재사용한다. BM25를 시작한다는 이유로 별도 2단계 폴더에 전체 코드를 다시 복사하지 않는다. 이후 큰 단계로 넘어갈 때 완료한 이전 큰 단계 폴더를 비교 기준으로 보존한다.

다른 큰 단계의 코드를 런타임 import·symlink·상대 경로로 참조해 복사를 대신하지 않는다. 단계 폴더만 임시 경로에 복사한 상태에서도 테스트·대표 CLI를 실행할 수 있어야 한다. 표준 라이브러리와 해당 계약에서 승인한 설치 의존성은 사용할 수 있다.

제품 상대 경로 명령은 단계 폴더에서 실행하고 공백이 있는 경로는 따옴표로 감싼다. contract_guard·work_queue는 저장소 루트, 증거는 루트 docs/verification/pNNN/에서 관리한다.

## 복사 출처와 보존

큰 단계의 최초 확보 파일은 stage-manifest.json에 source_stage, source_commit(전체 40자리 SHA), source_path, destination_path, copied_sha256을 기록한다. source_path의 기준도 명시한다. copied_sha256은 최초 복사 바이트의 hash이며 이후 개발한 현재 코드의 hash라고 표시하지 않는다.

같은 단계 안의 후속 P작업에서 코드를 개선할 수 있다. 비교용 corpus·질문·정답의 보존은 해당 계약을 따른다. 이전 큰 단계의 오류를 수정해야 하면 별도 영향 검토를 남기고 실패 기록을 지우지 않는다.

가상환경·캐시·인증정보·설치된 패키지·모델 가중치·생성 실행 결과를 새 단계 소스로 통째로 복사하지 않는다.

## P002에 즉시 적용

P001은 루트 경로에서 이미 완료됐다. 그 카드·로그·기존 검증 증거와 원래 루트 제품 파일은 과거 계약 재현용으로 보존한다. P002는 다음 순서로 적용한다.

1. P001 구현 커밋 `4225bb1d6b9bd017a06e81125c4fce9ed1d7f227`의 scripts/evaluate_retrieval.py, tests/test_evaluate_retrieval.py, data/synthetic/의 네 파일을 `1. Naive RAG/`의 같은 상대 경로에 확보한다. 최초 복사 hash와 출처, 새 단계 README·manifest를 기록한다.
2. BM25 구현·추가 테스트·사용 안내를 같은 `1. Naive RAG/` 안에서 개발한다. P002의 corpus·질문은 P001 원본 hash를 유지하며 평가 의미와 기존 독립 회귀를 보존한다. 같은 단계의 코드 정리는 이 계약 안에서 허용한다.
3. 루트 README에서 현재 제품 실행 위치를 이 큰 단계로 안내한다. 원래 루트 제품 파일에는 후속 기능을 추가하지 않으며 새 단계는 그 파일에 의존하지 않는다.
4. 직전 오해로 `1. 검색 평가 기반/` 또는 `2. BM25 검색 기준선/`에 작성한 내용이 있다면 새 `1. Naive RAG/`로 옮겨 살린다. 파일별 보존·출처를 확인한 뒤 잘못 만든 경로를 정리한다. 사용자 작업·테스트·실패 로그를 삭제하거나 재작성하지 않는다.
5. 단독 복사 실행·P001 회귀·P002 검증과 데이터 보존을 확인해 P002 증거로 남긴다. P001의 과거 증거를 새 경로에서 실행했던 것처럼 바꾸지 않는다.

직전 plan 80f667a의 세부 작업별 폴더 지시는 이 정정으로 대체한다. dev는 정정 plan을 재채택하고 기존 실행 로그에 정정·영향을 추가한다.

## Project B 내부 평가 모듈 (2026-10-29)

Project B는 HR RAG 전체이며, [내부 평가 모듈](project-b-generation-evaluation.md)은 `evaluation/project_b/`에 별도 구현할 예정이다. 평가 모듈 때문에 별도 큰 단계 번호를 추가하지 않는다. 각 단계는 평가용 run artifact를 내보내고 평가 모듈이 읽으며, 정답/평가 코드를 생성 입력에 넣지 않는다. 현재 순서는 P015 원문 PDF 재작성 → P007 청킹·검색 실험 → P013 기본 평가기 → P014 NLI 비교 → P008 답변 비교 UI → P010 Hybrid다. P007 검색 평가는 답변 평가기 없이 먼저 수행한다. 하네스는 별도 프로젝트에서 관리한다. 개별 단계의 독립 실행과 이전 구현 보존 규칙은 유지한다.

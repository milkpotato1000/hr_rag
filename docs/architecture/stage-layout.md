# 단계별 구현 폴더

## 사용자 결정과 원칙

2026-10-22 사용자 요청에 따라 저장소 루트의 `번호. 제목/` 폴더마다 독립적으로 실행할 수 있는 구현을 둔다. 다음 단계는 앞선 단계의 필요한 파일을 복사하거나 선별해 시작한다. 이전 단계의 구현을 계속 덮어써서 단계를 구분하지 않는다.

기획·계약·진척·검증 증거와 Git 하네스는 저장소 루트에 유지한다. 단계 폴더 번호는 학습·구현 단계 번호이고 P번호는 작업 식별자이므로 항상 같아야 하는 것은 아니다. 이후 한 단계의 개선 작업에도 새 P번호를 쓸 수 있다.

| 단계 | 구현 폴더 | 담당 작업 | 시작할 때 확보할 것 |
| --- | --- | --- | --- |
| 1 | `1. 검색 평가 기반/` | 완료된 P001을 P002 착수 시 보관 | 커밋된 P001의 데이터·평가기·회귀 테스트 |
| 2 | `2. BM25 검색 기준선/` | 개정 P002 | 1단계의 합성 데이터·평가기·필요 테스트와 사용 설명 |
| 3 이후 | `3. {제목}/` 등 | 후속 P카드에서 제목·선행·범위 확정 | 앞선 단계들에서 해당 작업에 필요한 코드·데이터·테스트만 선별 |

Dense 검색 비교는 3단계 후보이며 이 문서만으로 모델 다운로드나 구현 범위를 확정하지 않는다. 제목이 확정되지 않은 빈 단계 폴더를 미리 생성하지 않는다.

## 폴더 구성과 독립 실행

각 단계는 해당하는 scripts 또는 src, data, tests, README.md와 stage-manifest.json을 가진다. 필요 없는 빈 디렉터리를 만들 필요는 없다. 단계 README에 목표, 선행 단계에서 가져온 것, 이번 변경, 실행·테스트 명령과 결과 해석을 적는다.

코드·테스트·입력 데이터는 현재 단계 폴더 안에서 해석하며 이전 단계 폴더를 런타임에 참조하지 않는다. 상위 공용 제품 코드 import, 외부 단계를 향한 symlink, sys.path에 이전 단계 추가, ../1... 경로의 데이터 읽기 등으로 복사를 대신하지 않는다. 표준 라이브러리와 그 단계 계약에서 승인된 설치 의존성은 사용할 수 있다.

상대 경로 명령은 단계 폴더로 이동한 뒤 실행한다. 공백·한글 경로를 인자로 넘기면 따옴표로 감싼다. contract_guard와 work_queue는 저장소 루트에서 실행한다. 회귀는 해당 단계와 영향받은 기준 단계에서 각각 실행한다.

독립성은 단계 폴더 하나를 임시 디렉터리로 복사한 뒤 테스트와 대표 CLI를 실행해 확인한다. 이 검증은 Git 하네스나 저장소 문서까지 복사해야 한다는 뜻이 아니다.

## 복사 출처와 이전 단계 보존

stage-manifest.json에 stage_number·title·관련 P번호와 가져온 파일 목록을 기록한다. 각 파일은 source_stage(최초 P001 루트는 legacy-root), source_commit(전체 40자리 SHA), source_path, destination_path, copied_sha256을 가진다. 경로는 각 해당 저장소/단계 기준 상대 경로다. source_path가 저장소 기준인지 단계 기준인지 manifest에 명시한다. 최초 복사 바이트의 SHA-256을 기록하며 stage README에 선별·수정 이유를 설명한다.

복사 후 새 단계에서 코드를 수정할 수 있다. copied_sha256은 최초 복사 출처의 hash이며 새 코드의 현재 hash라고 표시하지 않는다. 기존 단계에서 빼온 데이터와 정답을 그대로 비교해야 하는 경우 최종 파일도 원본 hash와 일치해야 한다.

완료한 이전 단계는 기준선으로 보존한다. 다음 단계의 기능 추가·리팩터링은 새 폴더에서 한다. 이전 단계의 오류를 고쳐야 하면 별도 계획·영향 검토를 기록하며 실패 기록을 지우지 않는다. 가상환경, 캐시, 비밀정보, 설치된 패키지·모델 가중치, 생성된 실행 결과를 새 단계 소스로 통째로 복사하지 않는다. 검증 결과는 루트 docs/verification/P번호 경로 규칙을 따른다(현재 관례는 소문자 p001, p002).

## P001에서 적용하기

P001은 원래 루트 경로에서 완료됐으므로 완료 카드의 요구·체크·실행 로그·기존 증거는 그대로 보존한다. P002에서 다음을 수행한다.

1. P001 구현 커밋 `4225bb1d6b9bd017a06e81125c4fce9ed1d7f227`의 scripts/evaluate_retrieval.py, tests/test_evaluate_retrieval.py, data/synthetic/의 커밋된 네 파일을 1단계 폴더의 같은 상대 경로에 복사한다. 이 여섯 원본은 byte hash를 보존한다. 별도의 단계 README와 manifest를 추가한다.
2. 1단계의 여섯 파일을 2단계로 복사한 후 그 안에서 BM25 코드·테스트·안내를 작성한다. 복사 기준은 1단계가 담긴 실제 커밋을 사용하므로 dev는 1단계 보관과 출처 기록을 먼저 커밋한다. 새로운 테스트는 추가하며 가져온 P001 평가 의미와 독립 회귀를 유지한다.
3. 최초 루트의 P001 제품 파일은 과거 계약·증거 재현용으로 보존하고 더 이상 후속 기능을 추가하지 않는다. 새 개발 위치와 현재 명령은 루트 README에서 단계 폴더로 안내한다. 단계 실행은 이 루트 호환 파일에 의존할 수 없다.
4. 두 단계의 독립 복사 실행과 원본 hash, 이전 P001 회귀를 검증하고 P002 증거에 저장한다. 기존 P001 검증 로그를 새로운 경로에서 실행했던 것처럼 다시 쓰지 않는다.

plan은 이 문서·P002 계약만 관리하고 실제 단계 폴더의 복사·구현·검증은 새 plan SHA를 채택한 dev에서 수행한다.
